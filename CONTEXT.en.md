# Deskfolk

[简体中文](CONTEXT.md)

A single-person agent collaboration app running locally on macOS (with Windows as an experimental preview): a team of named, persistent Bots splits one job and hands it on until it is delivered, while the app keeps the plan and its done-when in view, chases what stalls and checks the delivery first. They collaborate through directs, groups, mentions and asynchronous handoffs (modelled on Grok Bot); the computer is a shared folder on this Mac, not a cloud VM.

> **WIP**: This document defines the domain language; it is not a statement that every capability has passed acceptance. Entries are written for macOS (Dock, Keychain, Finder, Trash); what stands in for them on Windows, and what Windows does not have yet, is in [Windows preview](docs/windows.md). For the current scope, see the [README](README.md); for the direction of work on agent decisions, feedback on automatic tasks, reflection after each run, and full coverage of conversation operations, see the [roadmap](ROADMAP.md).

## Language

**Bot**:
A persistent teammate with a name, a role, and boundaries. It has its own 1:1 session and profile, and it does not disappear when a task ends. When it hits an obstacle, it first investigates on its own, tries the means available, and verifies against the original goal; it does not hand technical work it can finish itself to the user, and asks for help only with permissions, credentials, information, or decisions that only the user has. Trying things on its own is still bound by approvals, denials, Stop, and the boundaries of its profile, and it does not blindly repeat actions that have side effects.
_Avoid_: Agent, child agent, subagent, assistant, Endpoint

**Roster**:
The set of all Bots on this machine. There is no limit on how many there are, and anyone can create one. A Bot is not a security boundary. In the app, the roster is a single row of letter tiles at the top of the sidebar, not a grid of cards, and it does not include you.
_Avoid_: team account, tenant, seat, roster cards, putting you in the roster row

**Group**:
A shared session of at least two Bots (with no limit on members) that has its own name: whoever creates it names it, the name cannot be empty, and it is not assembled from the names of those present. When a handoff needs to be visible, use a group rather than making a person the router. A conversation with fewer than two Bots is a direct, not a group.
_Avoid_: channel, room, workflow, plan DAG, group member limit, using the member list as the group name

**Direct**:
A one-to-one session between you and a Bot, or between two Bots. Bots can hand work to each other asynchronously by private message. In a Bot↔Bot direct, one side's closing reply for its turn wakes the other side, just as send_message does; if the other side is already working, the reply is heard by that turn (see "Mention") instead of interrupting it. The exception is a nod to a nod: when this line and the other side's line that woke its turn are both short, neither asks anything, names anyone or carries a path or file, and neither turn ran a command or an MCP tool, the line is still posted but wakes nobody, and the exchange ends there. A Bot with nothing new to say calls end_turn, which ends its turn without posting anything. Once the talk goes quiet, the Bot that opened the direct is called back to the origin session by a check-back to report the outcome (see "Check-back"). You have only one direct with a given Bot, and you keep using it; a Bot↔Bot direct is opened fresh each time, each one covers only that one matter, and none continues from the previous one. You can only read a Bot↔Bot direct; you cannot post in it.
_Avoid_: thread (thread is reserved for replies to a single message), one long-lived direct per pair of Bots

**Session**:
The conversation container of a direct or a group. Messages, turns, judgements, and spend all belong to it. A Bot↔Bot direct is also a session; you are not a participant in it, and you can open it to read but cannot post.
_Avoid_: channel, room, treating a thread as a session

**Origin**:
The message a Bot↔Bot direct was opened from: the message that woke the opening Bot for the turn in which it opened the direct. The direct's entry hangs under that message, and the direct's row in the sidebar also shows its origin and can be clicked to go back to it. Once the origin session is cleared or deleted, the direct has no origin and can still be read as usual.
_Avoid_: parent session, thread, taking the Bot's own line "I'll go ask X" as the origin

**Handoff**:
One Bot passes work to another Bot, by speaking in a group or by private message. The receiver wakes up to handle it and can reply later.
_Avoid_: assigning work, routing, dispatch, bind

**Workspace**:
One local folder at the account level. Files, artifacts, and handoff attachments all live here, and all Bots share it. Bots are not isolated from each other. The sidebar can open the whole workspace folder (on desktop it is a pane with a file tree and a preview, and it does not take over the artifact preview beside the conversation; on narrow screens and phones it is still an overlay that slides in from the right); UTF-8 text files in the workspace can be edited in the viewer and saved back to the same path.
_Avoid_: cloud computer, one folder per Bot, sandbox (unless a separate one is added later)

**Plan**:
The one thing currently being moved forward in a session, pieced together by the app itself, so you do not have to define it first; the code keeps the `tasks` table and `task_id` (historical names; comments call it a plan). It is written up with fields: Kind, Goal, Done when, Rules, Process, Progress, and Status; it also keeps the verbatim text of the request that opened it (the original request). A session has only one current plan at a time, and no clock switches things for you. When its session is cleared or deleted, a plan goes dormant rather than ending: what you said is still there (see User quote), so it can be taken up again. Details: [Behavior · Plan](docs/behavior.en.md#plan).
_Avoid_: task table, plan DAG, state machine, owner, scheduler assignment, switching things by the clock, letting a Bot edit the plan itself, requiring you to set a goal before work can start, having the model summarize the goal for you (the plan is organized facts, not a transcript summary), rewriting the original request (the verbatim text is kept separately), writing a Bot's own decisions up as rules

**Ticket**:
The smallest unit with a deliverable under a plan: number, title, description and Done when, status (To do / In progress / In review / Done / Parked), who is on it (a record, not an assignment), and artifacts. The organizer refers to existing tickets by id and writes only the fields that changed; it opens new tickets as new-N and cannot delete a ticket, only mark it Done or Parked; you change status on the flow board. Artifacts belong to tickets: a message carries a `ticket_id`, and the files it references are that ticket's artifacts; no files are moved. Details: [Behavior · Ticket](docs/behavior.en.md#ticket).
_Avoid_: assigning work, claiming, deadline, priority ranking, subtask tree, letting a Bot create or close tickets, one ticket per sentence of a message, treating mirror files as the source of truth for tickets, the app marking something Done on someone's behalf, treating omitted fields as cleared, writing progress or a Bot's don'ts into a ticket's description

**User quote**:
A copy of what you said, kept apart from the transcript: each line you send, each answer to a question, each annotation you send, and what you write on the flow board (for the goal and ticket descriptions only the clauses you changed, new Done when lines and rules whole) are copied as they are in the same write that makes them, and filed under the plan and ticket they belong to, following the line wherever it is filed later. Clearing a session's history or deleting a group deletes the transcript, not these: they only forget the message they point at (and, when a group is deleted, which session they were said in). Only when you ask for them to be erased as well is the text emptied, leaving just "erased". No model is involved, and no Bot can write one. Every turn that works in a job (in a group, a direct, a Bot↔Bot direct, a check-back or a routine alike) opens on your first 4 and latest 6 lines in that job, each with where and when you said it, and how many were left out between. Details: [Behavior · User quote](docs/behavior.en.md#user-quote).
_Avoid_: the transcript as the only record of what you said, deleting your quotes when a chat is cleared, letting a model rewrite or summarize a quote, a Bot recording quotes on your behalf

**Requirements ledger**:
What you have asked of a job, one entry at a time, each standing on your own words: its quote is a piece of what you said, beside a number (R-12), a restatement, a category, what it holds for (one ticket, the job, every job in the job's session, or every job of a kind), how many times you have said it and in how many jobs. It only grows: an entry is added or raised again, and it goes out of force only one way: by your own action; a later line of yours giving a new number for the same thing (running time, resolution, aspect ratio, frame rate) only makes a replacement for you to confirm, and the old entry stays in force. The one real delete is your purge. What goes in: what the scribe notes from your words; when it notes nothing, a complaint of yours the app keeps as it is (to confirm, never a gate); the rules and Done when lines you write on the flow board (a line added is an entry; a line taken out goes out of force for that job, and altogether once no other job holds it); and the old rules, taken in once on upgrade (the ones you wrote or that are found in your words stay in force, the rest are marked "old rules (source unverified)", for reference only). Any other change a model gives likewise only makes a replacement for you to confirm; the database checks that each entry's quote is a piece of the line it came from. In a video job, requirements about how the work is made (backgrounds that hold together, a transition at every doorway, no freeze frames to fill time), choices such as the colour grade or the voice, and what stays the same across a series (a left arm) hold for the job's session by default, so a new job in the same session inherits them from its first turn, marked with the job they came from; "Not for this job" sets one aside for a single job. When one kind of craft requirement has come up in two video jobs of the same session, a card naming their words offers to make it standing (one entry at a time when their words differ; a choice is never offered). Every turn's situation and the flow board list it: the Bots read the same list you see. Clearing a session leaves it alone. Details: [Behavior · Requirements ledger](docs/behavior.en.md#requirements-ledger).
_Avoid_: letting a model rewrite the requirements as a whole, letting a Bot write the ledger, recording a Bot's words as your requirement, deleting an old entry because a model says it is replaced, deleting requirements when a chat is cleared, taking a quote that cannot be found in what you said

**Scribe**:
A short, tool-free call on the default model, made in the background once a line of yours is filed under a job (or you answer a Bot's question). It reads the line against what the job already asks and proposes a patch to the requirements ledger: entries to add, to raise again, to change. It holds no turn back and never speaks. Each item of the patch is checked on its own: one whose quote cannot be found in your line is dropped, the rest land; with no model set or a failed call it notes nothing, and only the fallback is left. Every raw answer goes into the work log. Questions about how it is going never reach it, and once the engine level has reached holds, neither do lines that only stop or go on. Details: [Behavior · Scribe](docs/behavior.en.md#scribe).
_Avoid_: the scribe holding turns back, the scribe deleting entries or handing in a whole list, reading a Bot's words, throwing the whole patch away when one item fails, using the Bot's model

**Organizer**:
A short, tool-free call that organizes the plan and tickets on a session's behalf, running on the default model of the default endpoint. It runs at two points: after your message enters the session and before any turn opens, judging whether the message continues, moves on, or returns to an earlier plan; and again 30 seconds after all the plan's live turns have ended and gone quiet; a turn you Stop does not lead to one. A Bot saying "done" or "tests pass" does not count as evidence: marking a ticket In review requires files handed over by that ticket, and marking it Done also requires a record of a run. It no longer writes a plan's Done when or rules: what you ask goes into the requirements ledger through the scribe. The pass after the plan goes quiet only files the handover (tickets' status and who is on them, new tickets, progress, whether it is done); it leaves the Goal and existing tickets' descriptions alone and never parks the plan. It no longer looks at precedents of the same Kind: what carries from one job to the next is the requirements ledger's entries a new job inherits. Details: [Behavior · Organizer](docs/behavior.en.md#organizer).
_Avoid_: letting Bots do the organizing themselves, organizing on every step, blocking turns when organizing fails, organizing with the Bot's model, the organizer speaking or calling tools, the organizer deleting tickets, judging completion on a Bot's own claim, marking the plan done while tickets are not closed out, letting the organizer rewrite the rules or Done when, a quiet-plan pass changing the Goal or ticket descriptions, finding precedents by Kind tag

**Mirror files**:
`map.md` in the plan folder (the plan's fields plus a ticket index) and `ticket.md` in each ticket folder (that ticket's fields, with the plan's Done when and Rules attached), rewritten by the daemon after every organizing pass and after every edit you make to the plan. They are the app's own files: a Bot may read them with `read_file`, but may not edit them or hand them over, and they are not artifacts; the plan folder is created the first time the plan is written up. To change their content, edit the plan or the tickets on the flow board.
_Avoid_: editing mirror files by hand, treating a mirror file as a deliverable, having a Bot maintain them, using them as the single source of truth (the database is)

**Work dir**:
A plan's folder, under the workspace's `work/`, named after the first 12 code points of the Goal (or of the opening request) plus a short id, with no date; under it, each ticket has its own `NN-<title>/`. A turn's work dir is the folder of the ticket it is filed under, or the plan folder if it is not filed under a ticket; the shell runs in it by default, while file tool paths stay relative to the workspace root. Both levels have reserved subfolders, `tool-results/` and `scratch/`, neither ever attached as an artifact; `map.md` and `ticket.md` are the app's mirror files and likewise do not count as artifacts. Details: [Behavior · Work dir](docs/behavior.en.md#work-dir).
_Avoid_: one folder per Bot, artifact library, treating it as a sandbox, the app deleting the whole folder for you, the app moving files to archive them, switching folders by date or by idle time

**Approval**:
A dangerous action must be let through by you before it runs. Approval governs "the one step about to happen"; it cannot undo anything already done.
_Avoid_: ConsentGate, gate

**Routine**:
Recurring work attached to one Bot and triggered by the calendar. v1 has routines only, no event triggers. Each routine has a standing plan (it does not take the session's current plan and does not go through the organizer); each time it comes due, a new ticket `NN-<date>` opens under that plan, and that turn works in the ticket's directory. When it comes due, the daemon inserts a system line under that Bot's name into your direct with the Bot, "Routine '<name>': <what to do>", to wake it; as with a check-back, no message is sent in your name. A check-back is not a routine; see "Check-back".
_Avoid_: cron job (in anything user-facing), skill-pack automation, sending the routine's content in your name

**Check-back**:
A one-time wake a Bot books for itself: how many minutes from now (one minute to seven days), what to check at that point, and what to do if nothing has happened. When it comes due, the daemon inserts a system line "Check-back: <note>" into the same session to wake the Bot. That line is the Bot's reminder to itself: only the turn it wakes can read it, and the flow board draws the Bot waking itself; the session does not show it, and other Bots, the organizer, search and unread never see it, just as a person would not read their own memo aloud to everyone. That turn keeps the plan and ticket of the turn that booked it, and only works in them: it does not change the plan's status or make it the session's current plan. Its situation holds the job's plan, the ticket list, the files handed over so far and the trace. If the Bot already has a live turn there, the check-back is heard by that turn; in a direct with you, only by a turn on the same job, so two turns never do one job and write the same files at once. Otherwise a new turn starts, beside yours in a direct with you, as a second message of yours would. Use it after a handoff, or while waiting on a result outside the Bot's own control, so that someone comes back to check on handed-off work instead of relying on the other side to remember to mention the Bot again. A Bot has at most one pending check-back per session at a time, and booking another replaces it; the situation block marks the Bot's own pending check-back. It is voided if the turn that booked it is Stopped (once the engine level has reached holds, only set aside until you next speak about that job), if the session is cleared or deleted, or if the Bot is deleted; a hold over it only sets it aside until the hold is lifted; if the Bot has left the group or been archived, the check-back is only cleared when due and wakes no one. If the daemon slept through the due time or restarted, a check-back that came due without firing fires once to catch up. It does not appear on the routine calendar and is not an event trigger. The app also books one on the Bot's behalf: when a Bot↔Bot direct the Bot opened goes quiet (about 10 seconds after the last turn ends, with no live turn and no pending check-back inside), the app immediately wakes the Bot in the session that opened that direct. The check-back line says whom it talked with and who said what last (or, if the other Bot never replied, says so), so the Bot first reports the outcome there; this likewise replaces its existing pending check-back there. If nothing new has been said in the direct since the last call-back, it is not called again; for a direct opened from such a check-back, if the other Bot never replied, there is no call-back either, so two Bots do not spin back and forth over silence. When a turn in the direct is Stopped or interrupted by a restart, there is no call-back; that is for you to pick up. Plans work the same way: when a plan goes quiet (organized, no live turn, and no pending check-back inside; a turn you Stopped does not make it quiet) but still has tickets To do or In progress, the app books an immediate check-back for the Bot on the first ticket not yet closed out (or, if no one is on it, for the Bot that last spoke in this plan). The check-back lists the tickets not yet closed out and points out that Bot's own, and the turn runs in that ticket's directory. A group plan of more than one ticket that is not parked, with none To do or In progress and something handed over or done (In review or Done), whose Progress still lists work to do or held up has stopped too; held-up work counts, since a Bot's own freeze is filed there and nobody else will lift it. Once the plan has had nothing happen for ten minutes and you have not spoken in the session for ten minutes either, the app books one for the Bot that last spoke in this plan (if that Bot already has a pending check-back in the session for another plan, not yet: the plan is looked at again once that one has come due and ten quiet minutes have passed). It says first what is useful next — check each ticket In review against its Done when and give the commands run and what they showed, never passing someone else's work for them nor its own; hand what is not done yet to a Bot who can take it, by name; for what is held up, the situation records who set that pause or freeze; ask you what needs your decision or what only you can give — and then lists the tickets In review; that turn runs in the plan folder. What is still to do or held up is in the situation's Progress and is not copied again. In a direct, with a single ticket that is not parked, or with nothing to do or held up left in Progress, no one is called: that is most likely something handed over and waiting for you to look at it. A turn the call-back opens that only says again what that Bot already said in the job — identical once formatting comes off, or differing only in a few English articles or wording such as “run longer / be longer”, with numbers, negations, code, links and paths preserved in the comparison, and with no new files — ends without posting. If no ticket has moved to In review or Done after the call-back (rewording a ticket does not count) and no acceptance check has passed for the first time, the app stops calling Bots and only sends you a notification, "This plan has stopped…", so you decide whom to call; the review is not posted in the session; while you say nothing in the plan and answer none of its questions, it is called back no more times than it has tickets and acceptance checks, and never more than five, and then stops the same way. This happens only in sessions you are in. In a group, if the called-back Bot already has a live turn, the check-back is heard by that turn, just like a mention.
_Avoid_: polling, self-wake every few minutes, on the routine calendar, event trigger, central scheduler assigning work to Bots, stacking several check-backs in one session, calling the same Bot again and again after a plan has stopped

**Closing check**:
A check made before a turn hands its deliverables to you, with no model call (ADR 0037): when the message a Bot is about to send cites workspace files or says it is still doing something, you are in the session and the turn belongs to a job, the daemon looks at three things before sending: whether the job has acceptance checks that are not passing, whether a "the rest comes later" is backed by a check-back or a named handoff, and whether a "tested" is backed by a command this turn actually ran. If any is missing, the turn gets it back once; a turn is checked once, and it is a reminder with evidence, not a gate. Details: [Behavior · Closing check](docs/behavior.en.md#closing-check).
_Avoid_: checking every step, blocking the send, counting a send-back as a tool error, having the Bot's own model check itself, letting the model rewrite the closing, treating a self-written report as evidence of a run

**Acceptance check**:
A check attached to one line of a plan's Done when that the daemon runs itself on this Mac: whether a file exists, whether it contains some text or matches a regex, a command's exit code and output, or whether the parts several Bots made fit together (a report's chapters, a storyboard or a set of posters, a deck, a video's shots: the app takes both sides of every seam and a model compares them against the plan's rules). You add, edit, remove and run them on the flow board; the organizer may only add and change its own, and a command only if a turn of this job ran it successfully or you wrote it yourself; the app also offers some from the numbers you give, which count once you confirm them (see Check from your words); Bots cannot write checks. While a check fails, or has not run since it was defined, the organizer cannot mark the plan done, and when the plan goes quiet the app calls a Bot back once with the failing checks; closing a plan by hand is not held back. Details: [Behavior · Acceptance check](docs/behavior.en.md#acceptance-check).
_Avoid_: letting Bots write or edit checks, the organizer changing checks you added, the organizer inventing commands, treating checks as a gate against you, the app deciding by itself that a plan is done, moving a ticket back when a check fails, running checks with the daemon's environment, approving outside-workspace checks on your behalf, calling back without limit on check results

**Check from your words**:
When you give a job a running time, a resolution, an aspect (portrait or landscape included) or a frame rate, the app offers an acceptance check from your own words that measures the video the job finally delivers: read as soon as your line is filed under the job, by fixed rules, with no model and no waiting for the scribe. It reads narrowly: a line that asks, supposes, complains, tells how a cut came out or asks for another version, a number about one part (a shot, the opening, the logo, subtitles), or one with a no before it reads nothing. Your words never make a gate by themselves: a number read only makes a card, "Add a check from what you said: running time 108–132 s?", with Confirm, Change and No; said again in another line, the card is posted again saying "You have said it N times". An offer is bound and measured too, its result ("Unconfirmed check: 107.00 s; you said about 2 minutes") shown to you and the Bots, holding nothing back; only your Confirm makes it a gate (in F-f: the card twice, the 107-second master measured failing but not held back, and one Confirm holds it back). A check in force never changes by itself: a different target you give later (set with the word for what it measures — running time, resolution, frame rate, aspect — or a word like "cut it to", "make it") only makes a replacement card, and the check stays in force until you choose. When the words you confirmed it on are erased, it goes back to being an offer, never quietly deleted. Complaints never touch a check. "About 2 minutes" is 108–132 seconds, "2 minutes or more" holds the lower end only, "within 90 seconds" the upper end only, and any other number read is met within 10% either way. It measures the video a Bot delivered with the word MASTER in its name, else final, else under `deliverables/`; never a name naming a shot, another version, a format or a preview, nor anything in a footage or reference folder. On the flow board it can be confirmed or removed, not edited. Details: [Behavior · Check from your words](docs/behavior.en.md#check-from-your-words).
_Avoid_: waiting for the scribe before making the check, having a model read the number, making a gate without your confirm, making a gate of a number said twice, taking a part's or another version's number for the deliverable's, letting a later number rewrite a check in force, letting a complaint change a check, treating an unbound check as a gate, measuring a shot or a source clip as the final cut, editing its number on the flow board, taking one shot's length for the whole film's

**Skill**:
A named procedure attached to one Bot: a short description (when to use it) + a Markdown body (how to do it). It belongs to that Bot only; it is not shared across the roster, not a workspace file, and not MCP. Enabled skills enter the system prompt of every step of that Bot as a catalog; a body is read into the current turn's loop with a tool when needed. A skill is a procedure, MCP is a capability: the Bot looks at the skill catalog first, and on a match reads the body and follows it, calling any MCP tools the body names by name; only when no skill matches does it pick tools straight from the "MCP this turn" section. Skills add no tools and do not replace MCP. A skill can declare the names of the MCP servers its body depends on; any not connected this turn are marked in the catalog, and when the body cannot be followed, the Bot says so plainly or asks, rather than making do with other tools. When a body is read, any `mcp_` tool name written in it that is not among this turn's tools is flagged, and the Bot looks up the current name in the "MCP this turn" section and fixes the body. A Bot can add, delete and edit its own skills with tools, and you can edit them in the profile; edits insert no transcript entry. A skill cannot waive approval, cannot add tools, and cannot treat outside the workspace as inside it.
_Avoid_: skill pack, `/skill`, plugin, workflow, using the profile as a procedure, roster-wide shared skills, auto-injecting bodies by keyword

**Memory**:
A fact a Bot has noted down itself that still holds across sessions: a topic + a one-sentence conclusion. It belongs to that Bot only and other Bots cannot see it; deleting the Bot deletes it too, while archiving keeps it. The Bot writes it itself with a tool, and the learning step after a chain ends can also write one: when review blames the model, when the Bot hit tool errors but finished, or when the request was unclear and the user corrected it over more than one turn (in that case it records only the terms the user supplied — the form of the deliverable, the scope, who it is for, the defaults — and does not change skills). The learning step sees what you said afterwards and the calls that failed in that chain, and keeps only a conclusion that names something concrete. Without the call nothing is kept: it is not distilled for the Bot in the background, and the transcript is not summarized into the profile. All enabled memories enter the system prompt of every step of that Bot, with no retrieval and no relevance ranking, in the order they were last written, newest last. A memory is a past conclusion, not a source of truth: when it conflicts with this turn's transcript, the transcript wins, and one that no longer holds gets edited or deleted. Noting the same topic again overwrites it; no second entry sits beside it. When the Bot opens a new topic, it is shown its other memories from the same session in the last day, and deletes the old one if the new one revises it. The number of entries is capped, and when it is full the Bot must decide what to drop first; nothing is silently pushed out. You can view, edit, disable and delete memories, but you do not create them for the Bot; each one carries the message it was noted from, and you can jump back to it. The division of labor: the profile is who you are, a skill is how to do it, a memory is what you have learned.
_Avoid_: retrieval-based memory, vector store, feeding raw transcripts back in, background distiller, treating memory as a source of truth, memory shared across Bots, user-created memories, unlimited memory catalog

**Daemon**:
A resident TypeScript process on this Mac that runs the tool-call loop itself. Closing the window does not stop it; if the window crashes, turns keep going. On power it holds off idle sleep; closing the lid, Sleep from the menu bar, a drained battery or shutting down still puts it to sleep, and it picks up again on wake. A killed daemon is relaunched only while the window process is still alive (including when it is hidden in the tray); once the window is gone too, another crash stops it until you open the app again or next log in. Settings has an optional standalone runtime, **off by default**, which stays disabled in production until the sealed-native gate passes; while it is off, the window process remains the supervisor. The daemon also holds the terminal sessions you open, so their processes keep running after you close the window. When you quit or the daemon stops on its own, those processes stop with it, but where each terminal was open and what was on its screen are kept; on the next launch a new one opens in the same place, and the split layout reconnects to it. Only ending the terminal session forgets it.
_Avoid_: cloud computer, 24/7 server, treating the UI process as the runtime, keeps running with the lid closed, stops after one kill, standalone KeepAlive login item, closing the window kills terminals

**App window**:
The Tauri desktop window, which holds the Svelte interface (the code and the development guide call it the messenger). Closing the window hides it to the tray rather than quitting; while hidden, it stays in the Dock. At login it goes only to the Dock and the tray, and the window does not pop up. Clicking the Dock icon, Cmd-Tab, Spotlight, left-clicking the tray, or opening the app again brings the window back. Only one window process runs at a time; a second launch just wakes the existing one and connects to the existing daemon. If the window crashes, it does not come back on its own. Before it connects to the daemon, Quit works, Stop does not, and the interface shows "Can't reach the runtime". The width and height you dragged it to, and whether it was maximized, are the same when you reopen after quitting; the position is not remembered, so the window does not land off-screen after a display change. While you drag the border, the app does not ask whether the window is maximized: on macOS that query moves the window, so on release its position would differ from where you were dragging it.
_Avoid_: browser-only, no tray, hiding removes it from the Dock, window KeepAlive, grabbing the screen at login, multiple windows, treating a window crash as quitting

**Pane**:
One content area in the desktop window: a pane is a group of tabs, and a tab can be a session, a terminal, the routine calendar, the workspace, or spend. The window can be split horizontally and vertically into any number of panes; a window split into several panes is still the same window process, and a floating pane is not a second system window either. Only one pane is the current pane at a time; on narrow screens (≤680px) and phones there are no panes, and it is still one screen at a time, stacked layer on layer. Details: [Behavior · Pane](docs/behavior.en.md#pane).
_Avoid_: multiple windows, second window process, treating a floating pane as a system window, split screen on phones, visible means read, notifications rearranging the layout on their own, leaving empty panes around, settings in their own tab, top bar and tab both announcing the name in a narrow pane

**Layout**:
How the panes are divided: the horizontal and vertical splits, each pane's width and height, which ones float, which one is current, and which session each terminal pane holds. It is kept only in this Mac's localStorage, not in the daemon and not in the URL — the URL says only which session the current pane is showing. After you quit and reopen, it is as it was before; if a session or terminal it refers to is gone, it cleans that up on its own; before resetting to the default single pane, it asks about unsaved changes.
_Avoid_: layout in the database, layout in the URL, syncing layout across devices, layout that follows you to another machine, reset discarding unsaved changes outright

**Quit**:
Ends this run of the app. Under window supervision (the default), both the window process and the daemon stop, and the tray and Dock icons both disappear. If the standalone runtime is on, quitting closes only the UI and jobs keep going; stopping them takes an explicit stop (written `runtime.stop`). Turns in progress are marked Interrupted, and the processes in the terminal sessions you opened stop with it; next time you open the app, each terminal that was still open reopens in its original place, and the split layout reconnects to it. It is not closing the window. Only ending the terminal session forgets it. It leaves the Launch at login preference alone. Shutting down and logging out are also treated as Quit for turns. The same rule applies in development mode. In production the standalone runtime is still gated, and the default is still window supervision.
_Avoid_: treating closing the window as quitting, closing only the window by default and leaving a headless daemon, treating Quit as turning off launch at login, Cmd+Q closing only the window in development mode, treating the gated standalone mode as enabled

**Launch at login**:
Optional, on by default. At login it starts only the window process, into the Dock and the tray, and the window does not pop up; the window process then makes sure the daemon is running. Turning it off affects only the next login and does not kill the current run; at the next login neither the window nor the daemon comes up. Quitting does not clear this switch either. The daemon is not a login item of its own.
_Avoid_: window popping up at login, turning it off kills the current run immediately, daemon as its own login item, quitting clears launch at login, turning off launch at login but leaving jobs that start themselves

**Tray**:
The menu bar icon of the window process. Left-click brings the window back. Right-click: Show window, Stop (the most recently active turn when the window is not open), Quit. There is no Hide and no Pause daemon. If the window crashes, the tray is gone too.
_Avoid_: tray badge, a second interface, the daemon running its own tray

**User**:
The one person running this Mac. There are no multiple users and no share links. You are in every group; you and any Bot in a group can bring others in and remove them. Removing a Bot does not delete it. You appear in sessions, transcripts and the present members, but not on the roster's row of letter tiles.
_Avoid_: member, tenant, organization, Bot-only group without you, you in the roster

**Model endpoint**:
An OpenAI-compatible HTTP interface (base URL + API key). The app does not ship with any model of its own. You can configure several endpoints; one of them is the default. A completion goes to the endpoint its model belongs to. You add endpoints in Settings, and Bots can add them with a tool too. Creating an endpoint or changing an existing one's URL is a dangerous action. The default endpoint's URL and key cannot be changed, and it cannot be deleted.
_Avoid_: provider catalog, Binder, late binding, per-Bot endpoints

**Model**:
A completion name that a given endpoint recognizes; each endpoint has its own list and its own default. The thinking level is pinned together with the model and never exists on its own: either neither is pinned and the app picks both for each message, or a model is pinned and its level is set along with it. Each time a turn starts, an agent first picks once, looking at the message, the Bot's profile, the candidate list and recent review conclusions, and answers with a model, a thinking level and a one-sentence reason; the user does not pick for each turn. Details: [Behavior · Model](docs/behavior.en.md#model).
_Avoid_: provider catalog, a different model name for judgement, picking per turn, thinking level only ever chosen by the app, pinning a thinking level without a model, pinning a model without setting its thinking level, roster-wide shared routing experience, recognizing model feedback by keyword, one remark pinning a model forever, a scoring formula for model choice

**Setup wizard**:
The empty state of Settings: it is complete once the workspace path, the endpoint URL and a saved key are all in place. It has no route of its own; it slides out over the sidebar only and does not take over the main transcript.
_Avoid_: /setup, full-screen onboarding, making Settings the main transcript

**MCP**:
Roster-level servers: stdio (command / args) or HTTP / Streamable HTTP (url + optional headers). Every Bot can call the configured tools. You add servers in Settings, and Bots can also add, edit and remove them with tools. Adding a server or changing its command·args / url / headers is a dangerous action. An HTTP server's Authorization is pasted on the approval card and goes into the Keychain, never into tool arguments. Deleting an MCP server is not a dangerous action. The app records the usage instructions a server ships with; you or a Bot can also write a usage note for each server (what it does, when to use it, when not to), which goes into every step's "MCP this turn" section ahead of the server's own instructions. Leave it blank when the server's instructions are enough. Editing the note is not a dangerous action, and changing the connection does not clear it. All tools of an enabled, successfully connected server stay available to every Bot, direct, group and routine; they are never filtered out by message keywords or language. After a server is added, changed or re-enabled, the current turn's next step and other Bots' later completions can use it; once it is disabled or deleted, it can no longer be called. To hand an image from the workspace to a parameter that only accepts an image URL or data URI, the Bot writes `workspace://<path relative to the workspace root>` in the argument, and the app replaces it with the image's data URI before sending (shrinking the image first if it is over half a megabyte); the transcript and the next step still show the short reference. A remote server can't read this Mac's disk, and the model can't copy out a whole image's base64.
_Avoid_: per-Bot MCP, Bot as a tool permission boundary, hiding configured capabilities by keyword, available only in the turn that installed it, stdio only, hand-editing a server's own instructions

**Participation**:
When a message from you or a Bot arrives in a group's main transcript, whoever is mentioned must join in. Only your plain messages (no `@` / `@everyone`) have each of the other present Bots make one judgement (join in or sit out). If you mentioned someone, or a Bot sent the message, those not mentioned do not judge. The app does not decide on anyone's behalf who speaks, and it does not cut off loops with step-count or member-count circuit breakers. Asking you something is an ask inside the turn after joining in, not a third outcome of judgement.
_Avoid_: central arbitration, Dispatcher, routing, anti-loop cap, asking for help during judgement, judging again on every Bot message in a group

**Judgement**:
A short call made to each group member who wasn't mentioned, only when you post a main-transcript message in a group without mentioning anyone. It has no tools and returns join in or sit out as structured output. A judgement is not a turn; sitting out leaves nothing in the main transcript; a failed call counts as sitting out. A mention (including one by a Bot) skips judgement and starts turns only for those mentioned. Judgement sees the work the group is doing: the plan's Goal, Done when and Rules, the ticket list and who is on each ticket, the ticket this message was filed under, the files handed in so far, and the trace. What it decides is whether anyone is doing the part of the work that falls within its own role, not just whether this one message sounds like its business.
_Avoid_: a turn for every bystander, asking during judgement, joining in by default on failure, judging again on Bot messages, looking at the one message and not the work behind it

**Mention**:
`@Bot` names a teammate who must join in (skipping judgement); `@everyone` makes every Bot in the current group except the author join in, and pulls in no one outside the group. Without a mention, each Bot judges for itself under Participation. When that Bot already has a turn in progress in the group: if another Bot mentions it, the message is heard by that turn. It goes into the turn's inbox and is read at the start of the next step, and the turn carries on without being interrupted; if the turn wraps up before reading it, a new turn starts from that message after the wrap-up, so nothing is lost. A line of yours in a direct with a Bot that is already working is heard by that turn too, and the composer stays open. If you mention it in a group, that is still a redirect (a group has no Stop; when you speak, you want it to turn around right away), but the redirect hands it the files the old turn wrote, its last few steps and any messages not yet read as the first line of the new turn. It no longer spawns a second copy of itself. A name written as an abbreviation that uniquely identifies a present member (such as "Storyboard" for "Storyboard Artist") is treated as that member. A name that matches no one wakes no one: `send_message` first rejects it once so the Bot can correct it, and the group is finally left with a system notice. An `@` in a path, link or URL is not a mention: one glued to an ASCII letter, digit, `_` or `-`, one after `/` or `\` that starts a path segment or part of a URL (`work/2026-01-05-@Reviewer-continue-ab12/…`, `https://…/@name`), and any inside a markdown link target wake no one, and the app does not draw them as mentions; names joined by a slash (`@A/@B`) name both. `@Name` after Chinese text, a space, a bracket, a quote or other punctuation still counts, as in `(@Editor)` or `please @Editor`, and so does one glued to Chinese text or full-width punctuation.
_Avoid_: assign, dispatch work, cloning itself when mentioned in a group, a teammate's @ interrupting work in progress

**Thread**:
A quoted reply to one message in the main transcript: `parent_id` points to the quoted message, and the reply stays in the main transcript. Clicking Reply automatically `@`-mentions the original sender (when the sender is a Bot); if the message already has a mention or `@everyone`, it isn't added again. Threads are one level deep: you can't quote a reply. Bots use the same mechanism through `send_message`'s `parent_id`.
_Avoid_: thread as a group (a group is a separate session), quoted replies tucked into a sidebar, auto-@user when quoting the user

**Reaction**:
A lightweight acknowledgment of a message, picked from a fixed set of emoji; custom ones aren't allowed. It never carries changed instructions or security decisions; those require a written reply or an approval. In v1 only you add reactions; Bots don't react.
_Avoid_: emoji as approval, custom emoji, ✅/❌ as allow or deny

**Always allow**:
A saved roster-level rule (kind key + scope): from then on, dangerous actions of the same kind go through without asking. It exists alongside "Allow once". Some kinds always require approval and can't be made Always allow.
_Avoid_: allow everything, bypass, per-Bot rule

**Search**:
Lookup across Bots, groups, files and routines that jumps back to the spot in the original session. In v1 it is a local search on this Mac, not another Bot.
_Avoid_: semantic memory layer

**Stop**:
An immediate stop that you issue. It applies to turns in progress; actions already done are not rolled back. A command still running stops along with everything it started: it is asked to exit, and whatever is still running 3 seconds later is killed. A Stop is not the job going quiet: it does not get the plan organized, and it calls nobody back; an organizing or a second look the job already had lined up is cancelled too. With the UI open, it hits the turn in the **current pane** (which must be a direct). When several sessions are laid out at once, the current pane is the one that has the keyboard, or the one you last clicked or scrolled in. From the menu bar with no UI open, it hits the turn in the most recently active direct. Until the engine level reaches holds, groups have no Stop; to stop group work, say "stop" in the group (see Control line). Once it has, each Bot's reply being written in a group has a Stop of its own, which stops only that Bot's turn while the other Bots go on, and the menu bar's item becomes "Stop everything" (see Hold); a Stop is also a hold: on that Bot's work in that plan only (on just that turn when it has no plan), so the check-backs it booked are set aside rather than voided and nothing else wakes it back; your next line to it about that job — "continue" included; in a group, one naming it, answering it or naming nobody, not one only to another Bot; and not one you sent before pressing Stop — lifts it, and the Bot goes on from that line, with no note of the app's; for a job it was doing where you cannot speak (its direct with another Bot, say), say "continue" in its direct or naming it in a group, and the stopped turn starts again on a note. Clearing history, archiving, or deleting a group still ends that session's live turns, and is no hold. There is no step-count, roster or group-size circuit breaker.
_Avoid_: stopping the turns in every pane at once, deciding by the topmost floating pane, stopping only the shell itself

**Hold**:
A stop of yours, recorded as a row of its own rather than as a "parked" label a model can set back. It has a scope — everything, one Bot, one session, one plan, one ticket, one Bot's work in one plan, or one turn — and may carry more it covers, fixed when it was made (the work that Bot handed on and has not had back). Only you lift it, with a line of yours or a button; the record is never deleted, not even by clearing a chat or deleting a group. In the same step it is made, the running turns it covers end (with their commands' processes and MCP calls), and where each had got to is recorded on the hold, which is what the receipt is written from. A hold on a plan or a session shows the plans it covers as parked, and neither the organizer nor a resume can set them back to In progress; the check-backs it covers are set aside; lifting it puts both back, and each turn it ended starts again on a note. A hold on a Bot, a ticket, a turn or on everything leaves plan status alone. Nothing it covers is woken: no turn opens, a held Bot's own line wakes nobody, and a call with an effect does not run; what you say to a held Bot only opens a read-only turn to answer you; each wake it turns away is recorded in the work log, with the cause and the holds. Triggers in the database add a last layer, so not even an older build opens a turn a hold covers. Besides a line, a stop can come from a stop menu: while a Bot is at work in a conversation, the menu beside Stop or Send offers "Stop all of X's work", "Stop this job" and "Stop every Bot", and in a group also "Stop the work in this group"; the flow board offers "Stop this job" and "Stop every Bot"; the tools menu and the menu bar offer "Stop everything". A stop from a menu gets a receipt in the conversation you are in too. The holds in force are listed above the conversation list, each with a Lift; a group you stopped and a direct whose Bot you stopped read "Stopped" in the list; the flow board lists the holds over its job. Holds exist only once the engine level has reached them (see Schema gate). Details: [Behavior · Hold](docs/behavior.en.md#hold).
_Avoid_: taking parked for the hold itself, a Bot or the organizer lifting a hold, deleting a hold, parking a whole plan because one Bot in it was stopped, clearing holds with the chat history, a held Bot woken by another Bot, a check-back or a routine, letting a held turn run a command or send a message, letting a running turn finish its step after a stop

**Control line**:
A line of yours that only says stop ("stop", "stop what you're generating", "stop all your work"), go on ("continue"), or that the work has not stopped ("you haven't stopped") is carried out by the app itself: it is read by fixed word lists right after the status question check and before any filing, and counts only when nothing is left once its control words and a short list of fillers are taken out — no model call, no turn, no organizer. Words in quotes, brackets, strikethrough, a block quote or code, or beside a laughing, smirking or doubting emoji (😂🙄🤔), do not count; a question counts as a stop only when it asks the Bot to stop ("can you stop for a moment?"), while "how could you stop" or "who can stop" asks about it, and "can it stop?" gets the app's answer with a stop button; a Bot's name without an @ counts as said to it only when a comma, "you" or "too" follows it ("Reviewer: stop" is a line of a script). A stop makes the hold and ends the running turns it covers at once, then the app posts a receipt in the conversation you said it in: which turns it ended and where each had got to, how many check-backs it set aside, which plans it parked, who is still working beside it in the job, and what is running now — written only from what the hold recorded. Where it applies comes from the words and the place: in a direct, the Bot on the other side, with the work it handed on and has not had back (three handoffs down); in a group with nobody named, the group; with a singular "you", the Bot you are answering (or the only one that spoke to you in the last ten minutes) and the group; each Bot named; "all Bots" or "stop, all of it", everything, routines too — unless the line also says "you", names a Bot, says in the group or in the direct, or says "this job", which wins as the narrower scope. "Continue" lifts those holds — never wider than its words: "@X continue" in a group lifts X's own, not the group's — and each stopped turn starts again on a note with your words and what it was doing, a note for that Bot alone that the conversation does not show, like a check-back's own line; with nothing held it is an ordinary line, and after a Stop it is the next line about the job that lifts the Stop's hold, even with the job elsewhere when said to that Bot; "all Bots continue" counts for every Stop you pressed before it, and one said to a Bot leaves the other Bots' Stops alone; held by something wider it cannot lift (everything, the group, a job stopped in the group), the app says so and offers buttons. "Has it stopped?" and "you haven't stopped" are answered from what is running, and anything found still running under a hold is ended there and then and recorded. A line with a control word and more in it ("stop, and make shot 3 a night scene") goes to the Bot as usual, only carrying the buttons; "never mind" alone gets the buttons too. Each button is pressed once: Undo on a receipt lifts that stop, the stopped work starts again, and a line that was read as the stop goes to the Bot as the line it was (in your direct with the Bot, that line is what reaches it, not a second turn beside the stopped one; in a group the line wakes only whom it names, so the stopped work starts again all the same); "Stop every Bot"; "Stop “…” too" stops the plan other Bots were still working in; "Only “…”" narrows a stop on all of a Bot's work to that one job, and the rest of its work starts again on a note; "Drop this job" records the stop as dropping the job, and lifting it reopens the job. "Only X goes on" splits the wider hold in its way into one per other Bot and lets only X go; "All go on" lifts that hold too. "Stop" on a line with buttons makes the stop that line meant, and its receipt quotes the line. Exists only once the engine level has reached holds. Details: [Behavior · Hold](docs/behavior.en.md#hold).
_Avoid_: a model deciding whether a line is a stop, a stop line going through the organizer, taking "don't pad it with frozen frames again" for a stop, swallowing a request and acting only on the stop in it, a receipt that says what did not happen, swallowing "continue" when nothing is held or only a Stop holds the job, lifting the whole group's stop with "@X continue", a Stop on a Bot's job elsewhere quietly left in force after "continue" to that Bot, a Stop quietly left in force after "all Bots continue", taking a "stop" in quotes, in code or beside a 😂 for a stop, swallowing the line that was read as a stop after Undo, letting the other Bots go too on "Only X goes on", a line to another Bot in a group lifting this Bot's Stop

**Status question**:
A line of yours that only asks how things stand ("how's it going", "done yet", "any update" and their Chinese equivalents — the whole line, with no @, no attachment, not a quote-reply) is answered by the app itself: it posts a status line in the session saying first what is waiting on you (an action to approve, a question to answer), then who is working on the job, for how long and what they last ran, where each ticket stands, who booked a check-back and when, the latest files handed over and the acceptance checks' results — however many Bots and sessions the job spans — with no model call, and without waking or redirecting any Bot. If nobody is working, it says so and calls nobody back: asking how things stand should not set going again what you stopped. The status line is for you: it does not enter Bots' context and does not go through the organizer, and it shows as the app's own line (the Deskfolk mark and name), not under the face and name of the Bot it is filed under. To hear it from a Bot, @ it.
_Avoid_: waking the whole group for a "how's it going", interrupting a working Bot to ask for status, filing "how's it going" as a new job, having a model write the status, taking a line with an instruction for a status question

**Turn**:
A Bot, woken by a message, a mention, a handoff or a routine, working until it produces a reply, an ask or an approval card. A failed completion also ends the turn, and its final state is still completed, not interrupted. In a group, the same Bot has at most one turn in progress at a time; when another Bot mentions it or a check-back it scheduled comes due, that is heard by the current turn, and when you mention it or it judges to join in, the turn is redirected (see "Mention" and "Redirect"). Directs, routines and your explicit "Fork a turn" can still run several turns at once. Transcripts interleave by time. Spend is recorded per call; the app has a separate spend view, sessions show no numbers, and nothing is stopped because of spend. When a turn keeps calling tools without delivering a result, every 40 steps the loop asks it whether it is stuck (if it is stuck, it calls no tools and replies directly with where it is stuck and what it needs; if it is making progress, it carries on). At 160 steps its tools are put away, and its next reply is the end of the turn.
_Avoid_: workflow step, Planner step, the same Bot running several turns in a group, a failed completion as a fifth final state, letting a turn call tools forever

**Archive**:
Removes a Bot from the roster's main list; its sessions, profile and routines remain, and it can be restored. Only deleting removes the Bot from the roster (files in the shared workspace are left untouched).
_Avoid_: hide as pause (archiving is not Stop)

**Dangerous action**:
Needs approval before it runs: reading or changing anything outside the workspace, outbound network access (except model calls), adding or changing MCP servers (including command·args / HTTP url·headers), creating an endpoint or changing an existing endpoint's URL, and an unconstrained shell. Reading / writing / deleting inside the workspace, calls to configured MCP servers, the workspace shell, and adding or changing model names on an existing endpoint's list simply go ahead. Deleting an MCP server is not a dangerous action. The default endpoint's URL and key cannot be changed, and it cannot be deleted.
_Avoid_: gate, ConsentGate

**Outside the workspace**:
A path that, after `realpath`, does not fall under the workspace root prefix. A symlink inside the workspace follows its target: if the target is outside the workspace, so is the symlink.
_Avoid_: string prefix only, judging by inode / hard link

**Workspace shell**:
A `shell` run that passes the pre-launch path check: its cwd is inside the workspace, and no path visible in the command leaves the workspace. It makes no difference what characters a path name is written in; URLs (except `file://`) and devices such as `/dev/null` and the standard streams don't count as paths. It just runs. It is not a kernel jail.
_Avoid_: whole-machine shell, sandbox, seatbelt, App Sandbox container as the workspace root

**Unconstrained shell**:
A `shell` spawn judged to go out of bounds. That process and its descendants skip the workspace path check; the next `shell` is judged afresh. One exception: a recursive search (`grep -r/-R`, `rg`, `find`, `du`, `ls -R`) whose resolved root is your whole home folder or `/` skips the approval card entirely and is refused before it runs, with a suggested rewrite; the judgment follows the resolved path (`cd`, `~`, `$HOME` included), not the command string, a shell comment does not count, and a command it cannot parse — a pipe, a subshell, `eval` — is left alone; so is a search held to a few levels (`find -maxdepth N`, `rg --max-depth N`, N at most 3), which does not walk the whole tree. The same search scoped to the workspace root or a task directory still runs unapproved.
_Avoid_: permanent lift, kernel jail release, an always-allow rule bypassing this refusal

**Terminal**:
A shell session you open yourself on this Mac, held by the daemon; it has the same rights as Terminal.app, with its cwd starting in the workspace by default but not confined to it, and needing no approval. Bots can't see it, can't use it, and don't know it exists; on the desktop one terminal tab is one session, and phones and narrow screens gather all sessions on the Terminal page as its tabs. To stop one, you must explicitly choose "End session" and confirm. Details: [Behavior · Terminal](docs/behavior.en.md#terminal).
_Avoid_: treating it as the workspace shell, a terminal for Bots, approval cards for terminal commands, killed when the window closes, closing a tab kills the process, pane tabs as the session list, a row of sessions inside one terminal tab, two tabs pointing at the same shell, surviving a daemon restart, cloud computer

**Command stream**:
The live push of stdout / stderr while a Bot runs a `shell`, so the call can be seen while it runs. It is visibility only and doesn't change what the call is: stdin is still closed, the timeout is still ten minutes, and paths are still judged per call. It is not a terminal, has no input, and stays out of the main transcript: while running it hangs under that message bubble, when done it folds into one line, and to look back at it you use the turn view in the work dir.
_Avoid_: input for the command stream, treating it as a terminal session, letting it change approval granularity, putting it in the main transcript, a new message kind

**Ask**:
A Bot asks you about something that needs your judgment (not a tool approval). The question appears in the transcript, and the turn continues once you answer. When the possible answers can be listed, the Bot offers options: single choice when only one can hold, multiple choice when several can hold at once, with the recommended one first; you can always skip the options and write your own answer, or pick one and add a sentence. Your answer is recorded on the ask itself, not sent as a separate message from you: the card keeps what you picked and what you wrote, and later turns, the organizer and search all read it from there. Each ask is answered only once.
_Avoid_: making the ask an approval card, sending the answer as a separate message from you, adding an "Other" option, changing the answer after answering

**Interrupted**:
When the daemon dies, is killed and relaunched, or when you quit, shut down or log out, the turns in progress are marked interrupted. Commands those turns still had running (and everything they started) are asked to exit; any still running when the daemon next starts, because it died or quit before they were done, are stopped then, after checking that the process number still belongs to that same process, so a program that has since been given the number is left alone. In the transcript that line carries an avatar and name like any other Bot message, and "Continue" sits right after the "Interrupted" bubble: it opens a new turn whose trigger is that interrupted line, and does not retry the call that was cut off; that Bot's next turn (in any session) sees "the last turn was cut off", once only. Work a restart cut off gets one line per job once the daemon is back, in the conversation the job belongs to where you are: why it started again (a deliberate stop, an unexpected exit, a development run restarting), where each turn stopped, and that nothing picks up on its own; the line carries Continue and Leave it, and one notification. Details: [Behavior · Interrupted](docs/behavior.en.md#interrupted). Closing the lid or system sleep is not an interruption: the turn freezes and carries on after wake. Time asleep does not count as being stuck, nor toward a command timeout; a request cut off by sleep waits after wake for the network to come back (about a minute), then is resent in full. An app window crash is not an interruption: the daemon keeps going. Completion timeouts, stalled streams and endpoint 4xx/5xx errors are not interruptions. A health check that fails temporarily while the daemon process is still running is not an interruption either: the window does not launch a second copy, and a second copy that cannot get the port does not touch the database.
_Avoid_: resuming tool calls from the break point, leaving the interruption only in a Bot↔Bot direct you are not in, resubmitting the last review or render after a restart without asking you, killing a previous run's process by its number without checking, treating sleep as an interruption, treating shutdown as sleep, treating a window crash as an interruption, keeping "the last turn was cut off" on the profile forever, treating a completion timeout as an interruption, treating an endpoint error as an interruption, treating a health-check timeout as an interruption

**Completion**:
One streaming HTTP Chat Completions request to the endpoint within a turn. A turn's tool loop can make several completions. A failed completion is not an interruption, and it does not replay earlier tool calls. Every completion has an output cap (the model's `max_output` in its endpoint's list, 32,768 tokens when unset) and a time limit that counts only the completion itself. One that starts repeating itself, is only a canned one-line refusal, breaks off before it is finished or runs past its time limit has failed and is not a reply: nothing of it is posted, it wakes nobody, and it is tried again; if that fails too the turn ends as failed. One cut off at the output cap without repeating is carried on once. Details: [Behavior · Completion](docs/behavior.en.md#completion).
_Avoid_: treating one completion as a turn, treating a completion timeout as an interruption, posting a cut-off or repeating reply as the closing line, treating half a stream as a reply, counting streamed output as the turn making progress

**Redirect**:
On a turn already in progress, abandon its unfinished remaining actions (its status becomes redirected) and open a new turn on the new message. In a group, when the Bot already has a live turn, your mention and a judgement to join in both go through a redirect, like a person turning to hear what you just said; the new turn's first line states the files the old turn wrote, its last few steps and the messages it had not yet read, so it does not start from zero. Mentions from other Bots and check-backs do not redirect; they are heard by that turn (see "Mention"). In a direct, use Stop when you need to halt a turn in progress right away; groups have no Stop, so to stop one you send a message.
_Avoid_: forcing the user to choose redirect or fork by hand on every turn, overwriting the trigger on the same row and carrying on, one user message clearing every live turn in the group

**Fork**:
Open another turn alongside one already in progress; the old turn continues. In a direct, a new user message forks by default (it redirects only when you ask for that explicitly); a routine forks in the direct between you and that Bot. In a group, when the Bot already has a live turn, a mention or a judgement to join in does not spin up another copy of it; it forks only when you explicitly choose "Fork a turn" in the group. A Bot↔Bot direct has no user, so the other Bot's second message is heard by this turn rather than forking, the same as how Bots are handled in a group.
_Avoid_: a manual-intervention scheduling switch, a routine redirecting a turn in a group, a group mention cloning another copy of the Bot

**Pull-in**:
@-mentioning, in a group, a Bot that is not in the group but is on the roster and not deleted: it is added to the group first, then joins in. A name that is not on the roster does not create a new Bot; the message is still sent.
_Avoid_: @-mentioning without joining the group, implicitly creating a Bot for an unknown name

**Artifact**:
A workspace-relative path, or an `http`/`https` link, referenced in a message; the file itself lives in the workspace (or at the remote URL), and files written during a turn appear in its final message automatically. Opening one shows it in the preview panel to the right of the chat (image / audio and video / PDF / text / single-file HTML / Word / Excel / PowerPoint); other kinds offer a download or opening with the default app. In a handoff, the path goes into the message to the other party, with no separate kind; artifacts inside the workspace can be annotated (see "Annotation"). Details: [Behavior · Artifact](docs/behavior.en.md#artifact).
_Avoid_: asset library, Artifact table, snapshot copy, per-Bot artifact folder, `@file`

**Annotation**:
A remark you write about one spot in an artifact, attached to a workspace-relative path, an anchor, and the message that delivered the artifact. It starts as a draft the Bot cannot see; drafts collect into a batch sent all at once as one reply that quotes the delivering message and @-mentions the Bot that delivered it; once sent it is "Pending", and a Bot or you mark it "Resolved", and a resolved one can be reopened. An annotation is not a snapshot of the artifact: it records only the quote, position and file hash at the time and does not keep the old file; only files inside the workspace can be annotated, and link artifacts cannot. Details: [Behavior · Annotation](docs/behavior.en.md#annotation).
_Avoid_: comment (kept for a possible multi-person future), review, a new message kind, annotations storing old versions, waking once per annotation, a Bot annotating for you

**Attachment**:
A file **you** drop into the chat, copied into the workspace's `inbox/`, with a link to that copy kept on the message. A remote connection also has a session just for sending files: files sent there also go into `inbox/`; you can send text there too, and the text stays only in that session; that session has no Bot and wakes no one. A file sent in an ordinary session still wakes that session. When a Bot attaches a file already in the workspace as an artifact, it uses the same attachment rows, but nothing is copied and nothing goes into `inbox/`; so does a file or folder you drag from the file tree into the composer, which goes out as its own path (the file-drop session does not take these). The workspace is the computer; attachments are not a second file system. Raster images that enter a turn's window are sent to the model as pixels, but a turn carries at most 20 images and 20 MB: they are taken from newest to oldest starting at the trigger message, and older images that do not fit keep only their path; a large image is first scaled down to 1568 on its long edge, and an opaque one is converted to JPEG before it is sent. When a Bot itself reads a PNG / JPEG / GIF / WebP in the workspace with `read_file`, the image is scaled the same way and attached as an image after that step's tool result: at most 12 images and 8 MB per step; these images take their share of the turn's 20 images and 20 MB first, and the transcript window gets what remains; when later-read images do not fit, earlier-read ones are moved out in the order they were read, keeping only their path, and to see one again the Bot reads it again. Other files are given only as paths; reading them goes through `read_file`.
_Avoid_: a ghost file that exists only on the message

**Profile**:
A Bot's name, role description, boundaries and avatar. A Bot can change its own name, role, boundaries and avatar, and no profile-change line is inserted into the transcript when it does; you can change them again at any time. Names of Bots that are not deleted must be unique. The avatar is a generated image or a raster image, not memory. Changes in the Bot panel save automatically (they are written once you pause for a moment, and anything unsaved is sent before you switch or close the panel); there are no save or close buttons, and the panel has only a single ✕ in the top-right corner. In settings, the workspace, endpoints, and MCP names / notes are likewise written as soon as you change them; adding an MCP server or changing its command / args / URL / headers still needs confirmation, and there is no Always allow.
_Avoid_: writing memory into the profile, a save button on the profile panel, a save button in settings

**Catch-up**:
After the daemon comes back (on wake, relaunch after a crash, reopening after quitting, or startup), each missed routine runs only its most recent due run once, without running every missed cycle back to back. After waking from sleep it waits a minute before catching up: with the lid closed the system wakes itself for a few seconds, and the network is often not back yet at that point.
_Avoid_: skipping whatever was missed, running once for every missed run, catching up after sleep but not after quitting

**Context window**:
What the model actually sees in a turn: the profile, the catalog of enabled skills, the system instructions, the "MCP this turn" section, this Bot's memory, the situation block, the most recent stretch of the transcript, and this turn's tool loop. The full history exists only in the database, for you to browse and for search; it is not stuffed into the model wholesale, and judgement calls use a separate, shorter window without images. For an oversized tool result, the full JSON is first saved in the workspace, and the window holds only a bounded preview and full_result_path. Details: [Behavior · Context window](docs/behavior.en.md#context-window).
_Avoid_: automatic summaries into the profile, a semantic-retrieval memory layer, a background distiller, estimating by token count, feeding earlier turns' tool results back in

**Spend**:
An append-only ledger of calls on this machine; eight kinds of endpoint call each record one row: turn completion, judgement, model routing before a turn opens, correction-chain review, each learning step after a review, input suggestions, organizing, and acceptance checks. A call that shares its kind with others also records its purpose and gets a line of its own in the view (the scribe bills under organizing, an acceptance check's calls that look at frames are picture judgements). When the provider returns `cost_in_usd_ticks`, the call is recorded as reported; with no reported cost, it is estimated when both input and output tokens are present and a billing price is configured. The app has a separate spend view; the session top bar, list rows, settings and the model choice log show no spend figures. Details: [Behavior · Spend](docs/behavior.en.md#spend).
_Avoid_: budget circuit breaker, daily limit, automatic shutdown, treating estimates as reported or merging them into one amount, estimating missing tokens with a tokenizer, folding judgement into turns, MCP tools' own bills

**Local API**:
The HTTP + WebSocket interface the daemon serves on `127.0.0.1` for the app window, protected by the local token. Changes go over HTTP; the transcript stream goes over a receive-only WebSocket. Through it the window reads and writes the roster, sends messages and subscribes to the transcript stream.
_Avoid_: treating the UI process as the runtime, cloud API, two-way command channel, workspace files as HTTP resources, putting the local token in the URL

**Local token**:
A random secret the daemon mints fresh every time its process starts, used to authenticate requests to the Local API. HTTP sends it as `Authorization: Bearer`; the WebSocket sends it in the first message after connecting, never in the URL. A window crash does not change it; after the daemon exits or crashes, the next process mints a new one. It is not the endpoint API key, and it goes into neither SQLite nor the repository.
_Avoid_: API key, a long-lived key installed once, writing it into .env, putting it in the WebSocket query

**Judgement log**:
The record of join-in / sit-out decisions, visible in the current conversation's settings. It does not go into the main transcript.
_Avoid_: treating judgements as turns, flooding the main transcript

**Model choice log**:
The model and thinking level picked when a turn opens, which category the message counts as, how the turn ended (a failed completion carries its failure kind), how long it took and how many steps it made, plus the model feedback that later lands on that turn, the review of its correction chain, and the lessons recorded. It sits on that turn's card on the flow board and no longer has a separate entry point or page: a line at the bottom of the Bot card shows the model, thinking level and category, with a separate mark for feedback, for blame placed on the model, and for a failed completion; clicking that line expands everything below the card, and clicking a piece of feedback jumps back to the original words. The flow board toolbar can light up the cards that have feedback or whose review blamed the model and dim the rest, without changing the shape of the whole job. It is viewed by job, not by session: when a job spans several sessions, all of its choices are on the same board. It does not go into the main transcript and shows no tokens or spend; the Local API can still list it per session.
_Avoid_: routing log, a separate model choice log page, a log button on the session top bar, going into the main transcript, stuffing it into the current conversation settings, putting spend statistics here, treating criticism of the content as model feedback

**Schema gate**:
The check the daemon runs when it opens the database: if the database's `schema_min_compatible` is above `SCHEMA_LEVEL`, what this build understands, it refuses to open, writes why to daemon.log, and exits — instead of running on and misreading semantics it does not know. `engine_level` is the paired integer switch, standing in for a pile of separate feature flags, and only ever moves forward in order: every time the daemon starts it tries to take it up to this build's level, raising the database's floor to what that level needs in the same step (1, for holds). But while an installed app sharing the default data folder does not read the gate yet (or its version cannot be read; off a Mac there is no telling which one is installed, which counts the same), a source run leaves the level where it is, writes why to daemon.log and runs at the level it has — such an older app would open the database whatever its floor says. A developer can accept that on their own machine (`engine_gate_optin`: `POST /v1/capabilities/raise` on the local API, or `apps/daemon/scripts/engine-level.ts --accept-older-app`; never from a phone), taking on that the older app, opened without this daemon running, would ignore holds; the level then goes up at once (at the next start when no daemon runs), and taking the opt-in back never lowers it. `GET /v1/capabilities` reports both numbers, plus which features are on, to whoever calls it — including a phone, since the Mac may be running an older packaged daemon while the messenger's source tree has already moved on.
_Avoid_: treating schema_min_compatible as the app's version number, raising engine_level before both conditions hold (the gate itself shipped, and the installed app's own version is already new enough) when no developer explicitly accepted an older one, a setting a user would ever see

**Organizer run log**:
Every organizer call that actually reached the model, whether or not it landed, gets one row: the raw answer it read, the decision it parsed out, the candidates it could pick from (which plans it could resume or join, which acceptance checks it could edit — as read when the call went out) alongside the ones the answer actually picked (as the model wrote them, before validation — when a named resume/join target no longer qualifies, the decision falls back to continue, but the row still keeps what it named; a resume/join target only counts as named beside the decision that uses it. Whenever the written decision is not the one that applies — a target that no longer qualifies, no target at all, a word that is none of the four, anything but continue from a settle — the row says why), the same candidate sets re-read once the call returned (compare the two to see whether they shifted while it was out), whether it landed, why not when it didn't, notes on a clean apply that still held part of the answer back (a settle that called a parked plan active, a field a settle kept because it only files the handover, tickets that kept a plan called done still active), and which ledger row this call was billed as. `GET /v1/debug/organizer-runs?task_id=` reads a plan's rows, local only — never on the remote whitelist, never reachable from a phone; each session keeps only its newest batch, and clearing history or deleting a group takes this log with it (unlike spend, which is kept on purpose). Only when the window spawns the source daemon itself does its stderr land in `daemon-dev.stderr.log` in the data directory (rotated once by size, checked only at each spawn) — `pnpm dev`'s own daemon is pnpm's child and never passes through that code; where the window has no console at all this used to go straight to `/dev/null`, and under `tauri dev` it was already visible in the terminal and just moves into the file instead.
_Avoid_: something a Bot or you ever see, the main transcript, the remote whitelist, a packaged build also writing this stderr file (only the source-run dev daemon does), the `pnpm dev` daemon writing it too (it never runs through this code path)
