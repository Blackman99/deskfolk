# Deskfolk

[简体中文](CONTEXT.md)

A single-person agent collaboration app running locally on macOS (with Windows as an experimental preview): you hand a multi-day, multi-step job that needs rework to named, persistent Bots (one or several) and walk away; the model does the work and the app holds it to account — your words are not lost, done has a definition, a stop is a state, and a supervisor chases what stalls. Those rules are code and do not change with a prompt; how Bots work is in the built-in prompts, the defaults of a way of working that you and your Bots can change. Bots collaborate through directs, groups, mentions and asynchronous handoffs (modelled on Grok Bot); the computer is a shared folder on this Mac, not a cloud VM.

> **WIP**: This document defines the domain language; it is not a statement that every capability has passed acceptance. Entries are written for macOS (Dock, Keychain, Finder, Trash); what stands in for them on Windows, and what Windows does not have yet, is in [Windows preview](docs/windows.md). For the current scope, see the [README](README.md); for the direction of work on the kernel of plans, tickets and done-when, and on full coverage of conversation operations, see the [roadmap](ROADMAP.md).

## Language

**Bot**:
A persistent teammate with a name, a role, and boundaries. It has its own 1:1 session and profile, and it does not disappear when a task ends. When it hits an obstacle, it first investigates on its own, tries the means available, and verifies against the original goal; it does not hand technical work it can finish itself to the user, and asks for help only with permissions, credentials, information, or decisions that only the user has. Trying things on its own is still bound by approvals, denials, Stop, and the boundaries of its profile, and it does not blindly repeat actions that have side effects. It says only what matters: a sentence whose removal or addition changes nothing in what it means to convey is filler, and it leaves it out (opening acknowledgements, restating the request, self-praise, sign-offs, ending by asking you to confirm or to say if anything should change); long content you asked for is written in full.
_Avoid_: Agent, child agent, subagent, assistant, Endpoint, "Got it!", "So sorry", "Thanks for the correction", "Let me know if you need anything"

**Roster**:
The set of all Bots on this machine. There is no limit on how many there are, and anyone can create one. A Bot is not a security boundary. In the app, the roster is a single row of letter tiles at the top of the sidebar, not a grid of cards, and it does not include you.
_Avoid_: team account, tenant, seat, roster cards, putting you in the roster row

**Group**:
A shared session of at least two Bots (with no limit on members) that has its own name: whoever creates it names it, the name cannot be empty, and it is not assembled from the names of those present. When a handoff needs to be visible, use a group rather than making a person the router. A conversation with fewer than two Bots is a direct, not a group.
_Avoid_: channel, room, workflow, plan DAG, group member limit, using the member list as the group name

**Group lead**:
The Bot you confirmed to receive unaddressed messages in this group; handoff records may suggest one, but a suggestion is not an appointment. A job's own lead takes precedence when present in that group. Details: [Behavior · Group lead](docs/behavior.en.md#group-lead).
_Avoid_: appointing the top count automatically, a Bot appointing itself, a lead lifting your holds

**Direct**:
A one-to-one conversation between you and a Bot or between two Bots; your direct with a Bot is reused, while the Bots' collaboration direct belongs to the job they are working on. You read a Bot↔Bot direct, not speak as a third participant. Details: [Behavior · Direct](docs/behavior.en.md#direct).
_Avoid_: mixing unrelated jobs in one collaboration direct, user as a speaker in a Bot↔Bot direct, every private line must wake the other side

**Session**:
The conversation container of a direct or a group. Messages, turns, judgements, and spend all belong to it. A Bot↔Bot direct is also a session; you are not a participant in it, and you can open it to read but cannot post.
_Avoid_: channel, room, treating a thread as a session

**Origin**:
The message a Bot↔Bot direct was opened from: the message that woke the opening Bot for the turn in which it opened the direct. The direct's entry hangs under that message, and the direct's row in the sidebar also shows its origin and can be clicked to go back to it. Once the origin session is cleared or deleted, the direct has no origin and can still be read as usual.
_Avoid_: parent session, thread, taking the Bot's own line "I'll go ask X" as the origin

**Handoff**:
One Bot passes work or a result to another Bot; delegation is the kind that explicitly requests handling and records an expected result, while an ordinary note is not automatically a delegation. Waking and waiting depend on the form of handoff.
_Avoid_: every private message is a delegation, speaking means delivery is complete, a note as a work request

**Delegation**:
A named request from one work item to another Bot's work item, recording the shared job, the ask, whether it expects a deliverable/review/answer, and whether it has been replied to or cancelled. It relates a request to a result, not an ordinary chat message or permanent assignment of an entire Bot or conversation. Details: [Behavior · Delegation](docs/behavior.en.md#delegation).
_Avoid_: private message means delegation, ordinary acknowledgment means result, the whole Bot belongs to the sender, saying approved means a completed review

**Workspace**:
One local folder at the account level. Files, artifacts, and handoff attachments all live here, and all Bots share it. Bots are not isolated from each other. The sidebar can open the whole workspace folder (on desktop it is a pane with a file tree and a preview, and it does not take over the artifact preview beside the conversation; on narrow screens and phones it is still an overlay that slides in from the right); UTF-8 text files in the workspace can be edited in the viewer and saved back to the same path.
_Avoid_: cloud computer, one folder per Bot, sandbox (unless a separate one is added later)

**Plan**:
One job pursued around a goal and a deliverable, holding tickets, user quotes, requirements and artifacts, and continuing across conversations, days and rework; its home conversation is where it belongs, not the only place it can be worked on. Opening another job does not stop this one, and dormancy is neither acceptance nor abandonment. Details: [Behavior · Plan](docs/behavior.en.md#plan).
_Avoid_: one message is one job, only one job in a conversation, every rework opens a new plan, rewriting the original request, writing a Bot's decisions as user rules

**Ticket**:
A unit of work under a plan with defined delivery content, a title, a description, who is on it and related artifacts; it is neither an execution segment nor a message. Every ticket has to meet its plan’s Done when lines, rules and what you asked for, and may have requests and checks of its own; the plan’s Progress is the organizer’s written account, and a ticket’s state is its own. A ticket being In review does not mean its delivery has passed a review. From engine level 5 it has a stage (to do, in progress, submitted, in review, rework, approved, dropped) that only submissions, reviews, the supervisor and your board edits move — never the organizer — its old status written alongside; the parts (shots) the lead declares with plan_items each have a stage too, a hand-over naming the ones it covers (a file's name makes none), and the board says "11/12 approved"; from level 5 the lead can lay out tickets, makers, reviewers and dependencies with plan_items in one call. Details: [Behavior · Ticket](docs/behavior.en.md#ticket).
_Avoid_: one ticket per sentence, ticket as work item, handing over a file as acceptance, mirror files as a ticket's source of truth, letting a Bot write a ticket's stage, guessing parts from file names

**Large job**:
A job only done well in several parts with a sample shown to you first, such as a video of several minutes or a book or report of many chapters. Found by the reader from your words, or when segments go by with nothing approved; you can say it needs no laying out. Until it is laid out nothing is generated or handed over on it; then the rest wait for the sample, and the sample and the last part are yours to approve. Details: [Behavior · Large jobs](docs/behavior.en.md#large-job).
_Avoid_: making a large job as one ticket in one go, judging size by word count or keywords, filling time with still pictures as a cheaper form, a reading overriding your "no need"

**Sample**:
The part of a large job made first, to the whole job's standard, for you to approve; until then the other parts do not start, and once approved each is compared with it when handed over (a standard check). A job has one at a time; when you turn down the direction it set, the lead lays the job out again around a new one (you can move it on the board too), the checks held to the old one come down, and you approve the new one. Details: [Behavior · Large jobs](docs/behavior.en.md#large-job).
_Avoid_: a sample as a cut-down preview, a reviewer Bot approving the sample, several samples in one job, holding a new direction to the old sample

**Submission**:
From engine level 5, one hand-over of a ticket's work: which files (by content hash), the checks the app ran on them at once, and the reviews it got. A Bot hands work over with `submit` (files of the plan's folder outside other tickets' folders, or the shared `assets/`); when it does not, new-hash files in the ticket's folder that the segment's lines cited are submitted for it when the segment ends (or on `end_turn(done)`) — the implicit submission, made for the ticket's producer only, never of a reviewer's notes. A ticket whose work is words hands those words over only through its producer's explicit `end_turn(done, answer)` — a plain-text closing reply is never inferred as one any more, and the words themselves must still pass a check (not an empty remark or a question, not a bare ack like "got it"/"sure"/"noted", not a bare claim like "done" with nothing else behind it; the length floor is only 2 code points, not the safety line — this check and the card below do the real work); failing that, the call is refused and the Bot hears to hand the words themselves over, or, if the work is a file, to keep working until it exists. The organizer's "done" on a ticket nothing was ever handed over on counts as a submission too. With a reviewer set, either kind goes to it like any other, but **its approve does not approve either one** — nobody actually made the words or the reading, so a clean approve only moves the submission to awaiting you, carrying the reviewer's own verdict; with no reviewer, a failing gate sends it back and the ticket does not move, and passing never approves an answer or an organizer's reading on its own — it still waits on a card asking you to approve it or send it back. A file hand-over is approved on its checks only when at least one check you wrote or confirmed backs it and every gate passes (the organizer's checks still block when they fail, but their pass backs nothing); with none of yours bound, it ends on the same card instead, open to the files themselves. A requirement you said twice, or about the picture, that nothing backs brings it to that card as well: one card per hand-over, listing those requirements, and approving counts them as met. Saying more about the job while it waits, which its Bot then works on, holds it — no card, one already up taken down — and what the Bot hands over next is what you are asked about; with nothing new handed over, this one comes back to you. A routine's runs never get this card: what a run hands over is approved once its gates pass. Nor does a file hand-over made in one go: on a job of one ticket that was never put to you or has had a hand-over approved, handed over by the only segment since it opened (or was last approved), it is approved, such requirements with nothing behind them included. Details: [Behavior · Submission](docs/behavior.en.md#submission).
_Avoid_: treating a cited path as a submission, moving a ticket to review without running its checks, submitting the same bytes twice, submitting into another ticket's folder, taking a reviewer's notes for a submission, leaving a ticket with no file unable to close, approving on the organizer's, an answer's or a reviewer's own say with nobody's work behind it, approving a file hand-over no check of yours backs, treating a status line as the answer handed over, letting a Bot that is not the owner hand over words

**Review**:
From engine level 5, another Bot's verdict on a submission, given with `review`: pass, fail, unknown or n/a for each required item (anything you said twice or more, anything about the picture), a pass with its evidence, then approve or reject. With a reviewer set only it may review, otherwise only a Bot in the plan's conversation. Before an approval the app runs the checks again, and it is refused while a gate fails (an unconfirmed proposal never blocks); a pass on anything about the picture needs an image of this job's folder read after the submission; a reviewer on the producer's own model is marked, and its pass on anything you said twice needs a passing check you confirmed, or your word — without either, it moves to your approve/reject card, which lists those items (approving counts them as met), and the ball is yours; an unconfirmed proposal that passes is only shown on the card, beside the ledger's own words. A rejection sends the ticket to rework and wakes the producer. An approval of words or an organizer's reading does not approve either, nor one of files no check you wrote or confirmed backs when the reviewer runs on the producer's own model (or either model is unknown) or gave no evidence — each moves to your approve/reject card instead, with the verdict shown there. "Approved" in words moves nothing. Details: [Behavior · Review](docs/behavior.en.md#review).
_Avoid_: reviewing your own submission, approving with an "APPROVED" in words, a review overruling a failing gate, passing the picture without reading frames, letting an unconfirmed number block an approval, sending a Bot to rework to a number you have not confirmed, treating a reviewer's approve of words or an organizer's reading as the actual approval

**Review miss**:
From engine level 5, the mark a review gets when it approved a hand-over and your complaint then sent that hand-over back to rework (at once, when the reader reads the fault; it used to take a press on a card) (`review.miss`, once per hand-over and reviewer). It goes into the reviewer's calibration record: its situation lists the approvals you overturned in that conversation (newest five, with your words), to judge the same kind of thing harder. Undoing the complaint's rework drops it. Details: [Behavior · Review](docs/behavior.en.md#review).
_Avoid_: treating misses as a score to punish a Bot, counting your Send back on a card as a miss, keeping a miss after you undid the complaint

**Capability ceiling**:
From engine level 5, a part (else the whole ticket) that, since you last answered a ceiling card about it, failed the same requirement three hand-overs in a row or failed more than six hand-overs stops and asks you: the part reads Blocked, nothing more is handed over for it, the ball is yours and the supervisor wakes nobody for it; the card offers Another way, Change the plan, Relax this requirement (pressing it confirms the requirement no longer holds) and Take it as it is. Details: [Behavior · Review](docs/behavior.en.md#review).
_Avoid_: letting a Bot try the same way again once stuck, relaxing a requirement without asking you, treating a stuck part as a parked plan

**External job**:
From engine level 6, one render a media server accepted (a paired `submit_<x>` / `check_<x>`, such as `submit_video` / `check_video`): registered when submitted and polled by the daemon itself, so a Bot's own check reads what the app last heard without reaching the server; done, failed or still pending after three hours, it wakes the Bot that submitted it and every Bot that checked on it. The same arguments within half an hour get the same job back; a part with a job running, or a result not handed over yet, takes a reason before it is submitted again. Details: [Behavior · External job](docs/behavior.en.md#external-job).
_Avoid_: a Bot polling with one-minute check-backs, submitting the same arguments twice, treating a job as a Bot's turn

**Quality event**:
From engine level 8, a work-log event that says something went wrong, filed by its type alone: `execution` (checks failed, a reject, a send-back, a complaint, a command timing out), `unclear` (a requirement that first came up after the hand-over), `model` (a reply that loops, declines, hits its cap), `pipeline` (a failed render, a part at the capability ceiling), `review_miss` (an approval you overturned), `orchestration` (a stall, a crash; for the maintainer only). No model is asked whether the model was at fault; you can mark a turn as the model's problem on its board card. A retrospective reads them for root causes, and what it writes into memories is a way of working, never the events themselves. Details: [Behavior · Quality event, Lesson](docs/behavior.en.md#learning).
_Avoid_: asking a model afterwards whether to switch models, counting a stall as the model's fault, writing quality events into memories

**Lesson**:
From engine level 8, a rule the app learned from a failure and checks itself, of two kinds. One: once the timeout kills a search that walks a tree, that kind of call is held back once with a warning, and blocked when a Bot insists and it times out again — for every Bot. Another comes from the narrowed reflection: after an overturned approval or a capability ceiling, the Bot involved proposes a checklist item or a check, which holds once you adopt it on its card. Settings' Lessons page shows, switches and retires them. Unlike a memory, which is text a Bot reads, a lesson on a kind of call is enforced by the app before the call; a checklist item is read in the Bot's situation, and an adopted check is run by the app. Details: [Behavior · Quality event, Lesson](docs/behavior.en.md#learning).
_Avoid_: leaving "don't search like this" to a memory, the same kind of command timing out again and again, having a model write detectors

**Retrospective**:
From engine level 8, once a job you accepted has been delivered and has stayed quiet for half an hour, each Bot that handed something over in it looks back once: on its own model (or the one chosen for Retrospective under Settings → Roles) it reads the job's record (your words, every hand-over and what became of it, complaints after an approval, the requirements ledger, what went wrong for it, and its current memories and skills), never the transcript; it writes down where it tripped up, which of its ways made you send work back and what to do again, then works the conclusions into its own memories and skills — the same subject overwritten, two about one thing merged, a wrong one corrected or deleted; a skill only gains a sentence after a passage, a passage at its end, or one sentence corrected, and loses none of its commands or names. The app checks each change before writing it and keeps what each replaced. It posts nothing, shows no card and asks you nothing: the board's side panel lists it under Retrospective, with an undo for each change. A Bot nothing went wrong for in the job does not look back, nor does a routine's job; it amends the line of ADR 0050 that stopped after-the-fact reviews, yet reviews no chain and asks nothing about the model. Details: [Behavior · Quality event, Lesson](docs/behavior.en.md#learning) and [ADR 0062](docs/adr/0062-retrospective-after-delivery.md).
_Avoid_: a retrospective after every turn, summarizing the transcript, copying the requirements ledger into memories, rewriting a skill wholesale, a card asking you after the retrospective, asking a model whether the model was at fault, a retrospective touching another Bot's memories

**Work item**:
One Bot's work on a plan and an optional ticket: “Bot × plan × ticket”; without a plan, a desk work item belongs to “Bot × conversation”. The work item is the work's identity and a turn is one execution segment; one Bot cannot execute two segments on the same plan at once. Details: [Behavior · Work item](docs/behavior.en.md#work-item).
_Avoid_: work item as message or turn, doing the same job once per conversation, correct ticket attribution in place of plan-level unique execution

**Desk segment**:
An execution segment before the Bot has chosen which job to work on, able to read, answer and ask; choosing its work must precede acting on that job. There is one only when neither a reference nor the reading placed the line; for a line read as new, its first call with an effect opens a job for the line unless it chose another first. It is distinct from a held Bot's read-only answer, which cannot become work. Details: [Behavior · Desk segment](docs/behavior.en.md#desk-segment).
_Avoid_: another Bot, a side call before a turn opens, acting before filing, bypassing a hold through a desk

**Attribution**:
The relationship between a message and the plans, tickets or parts it concerns: it may name several targets, remain undetermined, or be explicitly left unfiled by you; a line of yours filed under the wrong job can also be made a new job of its own, by you. What the line points at comes first (your choice, an annotation, a quoted reply, a path, bound work); without that a model reads which job it is about (ADR 0057), and what it cannot place the Bot chooses at its desk. Attribution is not where a message was sent and does not move an entire plan into another job. Details: [Behavior · Attribution](docs/behavior.en.md#attribution).
_Avoid_: one line can concern only one job, undetermined means no work exists, correction rewriting execution history, correction moving files, the one job left by default, guessing new work from an opening word, matching parts by numbers in the words

**User quote**:
A verbatim copy of words you wrote, kept apart from the transcript and able to belong to several jobs they concern. Clearing the transcript does not erase it; only your explicit request empties its text, and a model's restatement cannot replace it. When you change a line you already sent, the clauses you changed are kept as another copy and the original stays ([ADR 0063](docs/adr/0063-edit-a-line-and-lines-in-order.md)). Details: [Behavior · User quote](docs/behavior.en.md#user-quote).
_Avoid_: transcript as the only source, clearing chat erases quotes, a model's summary replaces the words, multi-attribution keeping quotes only for the primary job, changing a line rewrites its quote

**Requirements ledger**:
What you have asked of a job, one entry at a time, each standing on your own words: its quote is a piece of what you said, beside a number (R-12), a restatement, a category, what it holds for (one ticket, the job, every job in the job's session, or every job of a kind), how many times you have said it and in how many jobs. It only grows: an entry is added or raised again, and it goes out of force only one way: by your own action; a later line of yours giving a new number for the same thing (running time, resolution, aspect ratio, frame rate) only makes a replacement for you to confirm, and the old entry stays in force. The one real delete is your purge. What goes in: what the scribe notes from your words; when it notes nothing, a complaint of yours the app keeps as it is (to confirm, never a gate); the rules and Done when lines you write on the flow board (a line added is an entry; a line taken out goes out of force for that job, and altogether once no other job holds it); and the old rules, taken in once on upgrade (the ones you wrote or that are found in your words stay in force, the rest are marked "old rules (source unverified)", for reference only). Any other change a model gives likewise only makes a replacement for you to confirm; the database checks that each entry's quote is a piece of the line it came from. One you say every job should keep to ("every film from now on", "this series always"), as the scribe reads it, holds for the job's session, so a new job in the same session inherits it from its first turn, marked with the job it came from; "Not for this job" sets one aside for a single job. One said of this job only stays with it, even when it sounds like general craft or taste (from 2026-10-10; before, a video job widened such requirements to the session). Old rules get no card asking whether you said them: you confirm them one by one in the flow board's "unverified" group; nor does a kind of requirement you raised in several jobs get a card offering to make it standing. Every turn's situation and the flow board list it: the Bots read the same list you see. Clearing a session leaves it alone. Details: [Behavior · Requirements ledger](docs/behavior.en.md#requirements-ledger).
_Avoid_: letting a model rewrite the requirements as a whole, letting a Bot write the ledger, recording a Bot's words as your requirement, deleting an old entry because a model says it is replaced, deleting requirements when a chat is cleared, taking a quote that cannot be found in what you said, dropping your change because its category does not match, keeping words you took out without asking

**Scribe**:
A short, tool-free call on the scribe's model (the default model when none is chosen), made in the background once a line of yours is filed under a job, when it arrives or later (a desk opening a job for it, `work_on`, your correction), each line once (or you answer a Bot's question). It reads the line against what the job already asks and proposes a patch to the requirements ledger: entries to add, to raise again, to change. It holds no turn back and never speaks. Each item of the patch is checked on its own: one whose quote cannot be found in your line is dropped, the rest land; with no model set or a failed call it notes nothing, and only the fallback is left. Every raw answer goes into the work log. Questions about how it is going never reach it, and once the engine level has reached holds, neither do lines that only stop or go on. Details: [Behavior · Scribe](docs/behavior.en.md#scribe).
_Avoid_: the scribe holding turns back, the scribe deleting entries or handing in a whole list, reading a Bot's words, throwing the whole patch away when one item fails, using the Bot's model

**Line reading**:
Before the app acts on a line, one tool-less short call reads what it means (ADR 0055): a line of yours, for whether it tells the Bots to stop or go on, whether it only asks where the work stands, and which of its clauses object to delivered work, and, with no reference in it, which job it is about (ADR 0057, read at the same time; this one has no word lists to fall back on, and a line it cannot place goes to the Bot's desk); a Bot's line, for whether it says the work is still going or more will follow, whether it claims a run, and whether it is only "nothing to do" or a bare status, and a question of its to you for whether it only asks your OK to go on (no word lists stand in for that one: unread, the question reaches you as before). A stop, a go on and a send-back to rework are carried out only on a reading, and none of them when the line cannot be read ([ADR 0070](docs/adr/0070-the-app-stays-out-of-the-conversation.md)); otherwise a reading is only understanding: a bounce or a card is still decided by the rules as before, and a quoted sentence must be words of the line. Each line is read once, on the model chosen for Reading under Settings → Roles (the default model otherwise), at its lightest thinking level; with no model, an error, more than 20 s or an unreadable answer, the old fixed word lists read it, and the work log says so. Your line wakes no Bot, and no stop is carried out, until it is read (a line read as nothing but a stop goes ahead of lines still being read), so pick a fast model for it. Billed as its own "Line reading" line. Details: [Behavior · Line reading](docs/behavior.en.md#line-reading).
_Avoid_: fixing a miss by adding words to a list, a reading writing state itself, using a quoted sentence that is not in the line, treating an unread line as unsaid instead of falling back to the lists, a stop, go on or send-back carried out on the word lists' reading

**Organizer**:
Background organizing of a conversation's plan notes and ticket handovers, not a working Bot and not the source of user requirements. The new work-item path does not use it to choose message attribution; older migration-compatibility paths and quiet-plan handover organizing remain. Details: [Behavior · Organizer](docs/behavior.en.md#organizer).
_Avoid_: every message waiting for organizing first, retained compatibility code described as deleted, organizer rewriting user requirements, a Bot's claim treated as acceptance, a hand-over you sent back written up as passed, a passing sample check taken as your approval

**Built-in models**:
The model chosen on its own for each call the app makes on its own: reading, the organizer, the scribe, the picture judge, the composer, and, as a Bot, joining in, reflection, retrospective and compaction (ADR 0075, ADR 0077). They are on the Roles page of Settings (ADR 0082): a map draws the nine calls and the Bot's own turn by when they run, and opening a call sets its model and the built-in prompts it runs with in one place. Each can be an endpoint's model or a Claude model run through your own Claude Code; with none chosen a call runs as before (the default model, the composer on the default endpoint's flash, mini, lite or fast model, the as-a-Bot calls on the Bot's own model). Only a chosen model is told how hard to think: the lightest for the ones you wait on, low for the scribe and compaction, high for the organizer, the picture judge, reflection and retrospective. The organizer reads the whole plan and writes it back, so pick a strong model for it: on Opus one settle is about 20k tokens in and 6k out; a picture judge on an endpoint's model uses it only when it is marked as taking pictures, and the default model otherwise (every Claude model takes pictures). A Claude model spends your Claude plan's usage, billed under the same kind and purpose as before; a Bot can move these only to an endpoint's model or to none. Details: [Behavior · Model](docs/behavior.en.md#model).
_Avoid_: a built-in call that can only follow the default model with no way to name its own, a model that cannot see pictures judging against a sample, the scribe at the highest thinking level, the reading model taken for the organizer's, a Bot moving a built-in call onto your Claude model

**Mirror files**:
`map.md` in the plan folder (the plan's fields plus a ticket index) and `ticket.md` in each ticket folder (that ticket's fields, with the plan's Done when and Rules attached), rewritten by the daemon after every organizing pass and after every edit you make to the plan. They are the app's own files: a Bot may read them with `read_file`, but may not edit them or hand them over, and they are not artifacts; the plan folder is created the first time the plan is written up. To change their content, edit the plan or the tickets on the flow board.
_Avoid_: editing mirror files by hand, treating a mirror file as a deliverable, having a Bot maintain them, using them as the single source of truth (the database is)

**Work dir**:
A plan's folder, under the workspace's `work/`, named after the first 12 code points of the Goal (or of the opening request) plus a short id, with no date; under it, each ticket has its own `NN-<title>/`. A turn's work dir is the folder of the ticket it is filed under, or the plan folder if it is not filed under a ticket; the shell runs in it by default, while file tool paths stay relative to the workspace root. Both levels have reserved subfolders, `tool-results/` and `scratch/`, neither ever attached as an artifact; `map.md` and `ticket.md` are the app's mirror files and likewise do not count as artifacts. Details: [Behavior · Work dir](docs/behavior.en.md#work-dir).
_Avoid_: one folder per Bot, artifact library, treating it as a sandbox, the app deleting the whole folder for you, the app moving files to archive them, switching folders by date or by idle time

**Approval**:
A dangerous action must be let through by you before it runs. Approval governs "the one step about to happen"; it cannot undo anything already done.
_Avoid_: ConsentGate, gate

**Routine**:
Recurring work attached to one Bot and triggered by the calendar. v1 has routines only, no event triggers. Each routine has a standing plan (it does not take the session's current plan and does not go through the organizer); each time it comes due, a new ticket `NN-<date>` opens under that plan, and that turn works in the ticket's directory. When it comes due, the daemon inserts a system line under that Bot's name into your direct with the Bot, "Routine '<name>': <what to do>", to wake it; as with a check-back, no message is sent in your name. A routine runs unattended by design: what each run hands over is approved once its gates pass, with no card asking you to approve it; when a result is wrong, say so, and a line read as finding fault still sends it back to rework at once. A check-back is not a routine; see "Check-back".
_Avoid_: cron job (in anything user-facing), skill-pack automation, sending the routine's content in your name, a daily card asking you to approve what a routine handed over

**Check-back**:
A one-time timer reminder a Bot books for itself, recording when to return, what to check and its original work; not an event wait for another Bot's result. Reminders of different work items must not replace one another; a hold can suspend one, while clearing/deletion can void it. Details: [Behavior · Check-back](docs/behavior.en.md#check-back).
_Avoid_: guessing delegation results from a timer, reminders of different work items replace each other, a timer reminder is a supervisor

> **Level-0–2 legacy behavior**: the conversation-replacement and quiet-callback detail below is retained as migration reference, not level-3 waiting rules. Level 3 deduplicates by work-item/key; see the behavior details above.
A one-time wake a Bot books for itself: how many minutes from now (one minute to seven days), what to check at that point, and what to do if nothing has happened. When it comes due, the daemon inserts a system line "Check-back: <note>" into the same session to wake the Bot. That line is the Bot's reminder to itself: only the turn it wakes can read it, and the flow board draws the Bot waking itself; the session does not show it, and other Bots, the organizer, search and unread never see it, just as a person would not read their own memo aloud to everyone. That turn keeps the plan and ticket of the turn that booked it, and only works in them: it does not change the plan's status or make it the session's current plan. Its situation holds the job's plan, the ticket list, the files handed over so far and the trace. If the Bot already has a live turn there, the check-back is heard by that turn; in a direct with you, only by a turn on the same job, so two turns never do one job and write the same files at once. Otherwise a new turn starts, beside yours in a direct with you, as a second message of yours would. Use it after a handoff, or while waiting on a result outside the Bot's own control, so that someone comes back to check on handed-off work instead of relying on the other side to remember to mention the Bot again. A Bot has at most one pending check-back per session at a time, and booking another replaces it; the situation block marks the Bot's own pending check-back. It is voided if the turn that booked it is Stopped (once the engine level has reached holds, only set aside until you next speak about that job), if the session is cleared or deleted, or if the Bot is deleted; a hold over it only sets it aside until the hold is lifted; if the Bot has left the group or been archived, the check-back is only cleared when due and wakes no one. If the daemon slept through the due time or restarted, a check-back that came due without firing fires once to catch up. It does not appear on the routine calendar and is not an event trigger. The app also books one on the Bot's behalf: when a Bot↔Bot direct the Bot opened goes quiet (about 10 seconds after the last turn ends, with no live turn and no pending check-back inside), the app immediately wakes the Bot in the session that opened that direct. The check-back line says whom it talked with and who said what last (or, if the other Bot never replied, says so), so the Bot first reports the outcome there; this likewise replaces its existing pending check-back there. If nothing new has been said in the direct since the last call-back, it is not called again; for a direct opened from such a check-back, if the other Bot never replied, there is no call-back either, so two Bots do not spin back and forth over silence. When a turn in the direct is Stopped or interrupted by a restart, there is no call-back; that is for you to pick up. Plans work the same way: when a plan goes quiet (organized, no live turn, and no pending check-back inside; a turn you Stopped does not make it quiet) but still has tickets To do or In progress, the app books an immediate check-back for the Bot on the first ticket not yet closed out (or, if no one is on it, for the Bot that last spoke in this plan). The check-back lists the tickets not yet closed out and points out that Bot's own, and the turn runs in that ticket's directory. A group plan of more than one ticket that is not parked, with none To do or In progress and something handed over or done (In review or Done), whose Progress still lists work to do or held up has stopped too; held-up work counts, since a Bot's own freeze is filed there and nobody else will lift it. Once the plan has had nothing happen for ten minutes and you have not spoken in the session for ten minutes either, the app books one for the Bot that last spoke in this plan (if that Bot already has a pending check-back in the session for another plan, not yet: the plan is looked at again once that one has come due and ten quiet minutes have passed). It says first what is useful next — check each ticket In review against its Done when and give the commands run and what they showed, never passing someone else's work for them nor its own; hand what is not done yet to a Bot who can take it, by name; for what is held up, the situation records who set that pause or freeze; ask you what needs your decision or what only you can give — and then lists the tickets In review; that turn runs in the plan folder. What is still to do or held up is in the situation's Progress and is not copied again. In a direct, with a single ticket that is not parked, or with nothing to do or held up left in Progress, no one is called: that is most likely something handed over and waiting for you to look at it. A turn the call-back opens that only says again what that Bot already said in the job — identical once formatting comes off, or differing only in a few English articles or wording such as “run longer / be longer”, with numbers, negations, code, links and paths preserved in the comparison, and with no new files — ends without posting. If no ticket has moved to In review or Done after the call-back (rewording a ticket does not count) and no acceptance check has passed for the first time, the app stops calling Bots and only sends you a notification, "This plan has stopped…", so you decide whom to call; the review is not posted in the session; while you say nothing in the plan and answer none of its questions, it is called back no more times than it has tickets and acceptance checks, and never more than five, and then stops the same way. This happens only in sessions you are in. In a group, if the called-back Bot already has a live turn, the check-back is heard by that turn, just like a mention.
_Avoid_: polling, self-wake every few minutes, on the routine calendar, event trigger, central scheduler assigning work to Bots, duplicate check-backs in one session at old levels (not different level-3 work items), calling the same Bot again and again after a plan has stopped

> The two the app booked for a Bot above (the call-back after a quiet direct, the plan call-back) run only at levels 0–3; from level 4 the [supervisor](docs/behavior.en.md#supervisor) takes over, and ones still pending from before are voided when they come due.

**Supervisor**:
From engine level 4, every 15 seconds the daemon checks the work that is not closed: waits whose object is gone, segments interrupted or failed, tickets nobody is moving. From records in the database it wakes the ball holder or picks up from where things stopped, within limits; when those run out, or it must not go on by itself (an external call with no known outcome, you pressed Not now), it leaves a line in a conversation you are in, with a notification; work it picks up on its own gets no notification or card when a turn of it fails or a restart cuts it. No model calls and no in-process timers, so a restart loses no deadline; after a restart it goes on by the restart's cause (a clean stop, a crash, a development restart). Details: [Behavior · Supervisor](docs/behavior.en.md#supervisor).
_Avoid_: polling every Bot on a timer, in-process call-back timers, counting an edited description as progress, picking up work under a stop, repeating an external call with no known outcome after a restart

**Ball holder**:
Who an open ticket is waiting on right now: the recipient of an unanswered request; you, when a question of the job awaits your answer, it is blocked, a stop covers it (or a ticket it depends on), or it awaits your review; from level 5 you while its approval waits on your answer to a card, its reviewer while it is in review, and the app (taking it on at the next tick) when it was handed over with no reviewer; otherwise the ticket's owner, then the plan's lead, and with neither, nobody (unclaimed, yours). The supervisor wakes only the ball holder. Details: [Behavior · Ball holder](docs/behavior.en.md#ball-holder).
_Avoid_: calling the Bot that spoke last, picking the worker of the first open ticket, letting the lead reassign held work

**Closing check**:
A check made before a turn hands its deliverables to you, with no model guessing what is missing (ADR 0037): when the message a Bot is about to send cites workspace files or says it is still doing something (whether it promises more, and whether it claims a run, is read by line reading), you are in the session and the turn belongs to a job, the daemon looks at three things before sending: whether the job has acceptance checks that are not passing, whether a "the rest comes later" is backed by a check-back or a named handoff, and whether a "tested" is backed by a command this turn actually ran. If any is missing, the turn gets it back once; a turn is checked once, and it is a reminder with evidence, not a gate. A Bot that says it is still working and then ends with nothing owed on the work is turned back once more by the ending contract, and if it ends that way anyway the conversation tells you it stopped (see Behavior · Delegation). Details: [Behavior · Closing check](docs/behavior.en.md#closing-check).
_Avoid_: checking every step, blocking the send, counting a send-back as a tool error, having the Bot's own model check itself, letting the model rewrite the closing, treating a self-written report as evidence of a run

**Acceptance check**:
A check attached to one line of a plan's Done when that the daemon runs itself on this Mac: whether a file exists, whether it contains some text or matches a regex, a command's exit code and output, or whether the parts several Bots made fit together (a report's chapters, a storyboard or a set of posters, a deck, a video's shots: the app takes both sides of every seam and a model compares them against the plan's rules). You add, edit, remove and run them on the flow board; the organizer may only add and change its own, and a command only if a turn of this job ran it successfully or you wrote it yourself; the app also offers some from the numbers you give, which count once you confirm them (see Check from your words); Bots cannot write checks. While a check fails, or has not run since it was defined, the organizer cannot mark the plan done, and when the plan goes quiet the app calls a Bot back once with the failing checks; closing a plan by hand is not held back. Details: [Behavior · Acceptance check](docs/behavior.en.md#acceptance-check).
_Avoid_: letting Bots write or edit checks, the organizer changing checks you added, the organizer inventing commands, treating checks as a gate against you, the app deciding by itself that a plan is done, moving a ticket back when a check fails, running checks with the daemon's environment, approving outside-workspace checks on your behalf, calling back without limit on check results

**Check from your words**:
When you give a job a running time, a resolution, an aspect (portrait or landscape included) or a frame rate, the app offers an acceptance check from your own words that measures the video the job finally delivers: read as soon as your line is filed under the job, by fixed rules, with no model and no waiting for the scribe. It reads narrowly: a line that asks, supposes, complains, tells how a cut came out or asks for another version, a number about one part (a shot, the opening, the logo, subtitles), or one with a no before it reads nothing. Your words never make a gate by themselves: a number read is only an offer, listed on the flow board, with no card asking whether you want it (you just said it; you are not asked again); said again in another line, it is the same offer. An offer is bound and measured too, its result ("Unconfirmed check: 107.00 s; you said about 2 minutes") shown to you and the Bots, holding nothing back; only your confirm (on the flow board, or on the card that asks you about a requirement you said twice when a hand-over has nothing behind it) makes it a gate (in F-f: the 107-second master measured failing but not held back, and one confirm holds it back). From level 5 it still holds nothing back; when a same-model review passes something you said twice, what it measured is written on the card that asks you. A check in force never changes by itself: a different target you give later (set with the word for what it measures — running time, resolution, frame rate, aspect — or a word like "cut it to", "make it") makes a replacement card, with Confirm, Change and No, and the check stays in force until you choose — the one time an offer gets a card, since until you answer the Bots are held to the old number; said again, the card is posted again saying "You have said it N times". When the words you confirmed it on are erased, it goes back to being an offer, never quietly deleted. Complaints never touch a check. "About 2 minutes" is 108–132 seconds, "2 minutes or more" holds the lower end only, "within 90 seconds" the upper end only, and any other number read is met within 10% either way. It measures the video a Bot delivered with the word MASTER in its name, else final, else under `deliverables/`; never a name naming a shot, another version, a format or a preview, nor anything in a footage or reference folder. On the flow board it can be confirmed or removed, not edited. Details: [Behavior · Check from your words](docs/behavior.en.md#check-from-your-words).
_Avoid_: waiting for the scribe before making the check, having a model read the number, making a gate without your confirm, making a gate of a number said twice, a card asking whether you want the number you just said, taking a part's or another version's number for the deliverable's, letting a later number rewrite a check in force, letting a complaint change a check, treating an unbound check as a gate, measuring a shot or a source clip as the final cut, editing its number on the flow board, taking one shot's length for the whole film's

**Skill**:
A named procedure attached to one Bot: a short description (when to use it) + a Markdown body (how to do it). It belongs to that Bot only (from engine level 8 you can share a copy of it with every Bot, which is then a project skill); it is not a workspace file, and not MCP. Enabled skills enter the system prompt of every step of that Bot as a catalog; a body is read into the current turn's loop with a tool when needed. A skill is a procedure, MCP is a capability: the Bot looks at the skill catalog first, and on a match reads the body and follows it, calling any MCP tools the body names by name; only when no skill matches does it pick tools straight from the "MCP this turn" section. Skills add no tools and do not replace MCP. A skill can declare the names of the MCP servers its body depends on; any not connected this turn are marked in the catalog, and when the body cannot be followed, the Bot says so plainly or asks, rather than making do with other tools. When a body is read, any `mcp_` tool name written in it that is not among this turn's tools is flagged, and the Bot looks up the current name in the "MCP this turn" section and fixes the body. A Bot can add, delete and edit its own skills with tools, and you can edit them in the profile; edits insert no transcript entry. From engine level 8 a retrospective may change the Bot's own skill too: only a sentence added after a passage, a passage appended, or one sentence corrected, with none of its commands, file names or names in backticks lost, and each change yours to undo. A skill cannot waive approval, cannot add tools, and cannot treat outside the workspace as inside it.
_Avoid_: skill pack, `/skill`, plugin, workflow, using the profile as a procedure, sharing without your confirmation, auto-injecting bodies by keyword

**Project skill**:
From engine level 8, the copy of one Bot's skill you shared with every Bot: it is in every Bot's skill catalog (marked with whose it was), read by name and followed, but no Bot can change it; the owner's later edits reach it only when you share it again on the Project skills card. A Bot with a skill of its own by the same name uses its own. Details: [ADR 0052](docs/adr/0052-project-skills.md).
_Avoid_: a Bot sharing its own skill, edits syncing to everyone on their own, treating a project skill as one Bot's private skill

**Memory**:
A fact a Bot has noted down itself that still holds across sessions: a topic + a one-sentence conclusion. It belongs to that Bot only and enters only its own context (other Bots can read it through the records, but never into their context, and cannot write it); deleting the Bot deletes it too, while archiving keeps it. The Bot writes it itself with a tool. From engine level 8 (the default) there is no learning step: what goes wrong becomes a quality event, and lessons are enforced by the app, the events themselves never written into memory; once a job you accepted is delivered, the Bots that made it hold a retrospective, which may write, rewrite, merge and delete their own memories (at most three written and three deleted at a time, each one yours to undo on the board) — ways of working, defaults and preferences that hold across jobs, not the job's requirements. Below level 8, the learning step after a chain ends can also write one: when review blames the model, when the Bot hit tool errors but finished, or when the request was unclear and the user corrected it over more than one turn (in that case it records only the terms the user supplied — the form of the deliverable, the scope, who it is for, the defaults — and does not change skills). The learning step sees what you said afterwards and the calls that failed in that chain, keeps only a conclusion that names something concrete, and without the call keeps nothing. A memory is not distilled from the transcript for the Bot in the background, and the transcript is not summarized into the profile. All enabled memories enter the system prompt of every step of that Bot, with no retrieval and no relevance ranking, in the order they were last written, newest last. A memory is a past conclusion, not a source of truth: when it conflicts with this turn's transcript, the transcript wins, and one that no longer holds gets edited or deleted. Noting the same topic again overwrites it; no second entry sits beside it. When the Bot opens a new topic, it is shown its other memories from the same session in the last day, and deletes the old one if the new one revises it. The number of entries is capped, and when it is full the Bot must decide what to drop first; nothing is silently pushed out. You can view, edit, disable and delete memories, but you do not create them for the Bot; each one carries the message it was noted from, and you can jump back to it; one a retrospective wrote names the job it came from. The division of labor: the profile is who you are, a skill is how to do it, a memory is what you have learned; how every Bot works is in the built-in prompts.
_Avoid_: retrieval-based memory, vector store, feeding raw transcripts back in, distilling transcripts in the background, treating memory as a source of truth, memory shared across Bots, user-created memories, unlimited memory catalog

**Built-in prompt**:
The fixed text the app sends models: every turn's System section, the notes opening the Skills, Memory and MCP sections, the Claude Agent preface, each tool's description, and the app's own calls (organizer, line readings, scribe, join judgement, composer suggestions, narrowed reflection, retrospective, seams checks, sample-standard check). They are the defaults of the developer's way of working: in Settings › Prompts you change them or restore the default, and every change can be undone; a Bot can propose one with `edit_prompt` / `reset_prompt`, which you let through on an approval card that is never Always-allowed. In the app's own calls the answer format code reads is locked; your text only says where it goes (`{format}`). A change applies to every Bot from the next call; when an update brings a newer default it is merged into your version line by line, and one that does not merge leaves yours in force, marked for you to choose. How one Bot works goes into its skills, a fact it learned is a memory, your requirements live in the requirements ledger — none of them in a prompt. The app's shell — approvals, holds, gates, checks — is code, and no prompt loosens it. Details in [Behavior · Built-in prompt](docs/behavior.en.md#built-in-prompt) and [ADR 0064](docs/adr/0064-built-in-prompts-you-and-your-bots-can-edit.md).
_Avoid_: letting a Bot change a prompt without your approval, rewriting your requirements into a prompt, loosening approvals or gates through a prompt, a System section per Bot, background self-tuning, editing the answer format code reads

**Records**:
What the app keeps on this machine: the database's messages, turns, tool calls, work log, quality events, plans and tickets, hand-overs and reviews, requirements ledger, organizer runs, judgements, spend, retrospectives, memories and skills, built-in prompt changes, and the daemon's logs. A Bot sees the tables with `describe_data`, runs one read-only SQL query with `query_data`, and reads the end of the logs with `read_data_log`, to answer "which work keeps being sent back" or "which call keeps failing to read" and propose an improvement from it. Read-only, in a child process the daemon starts, stopped at 10 seconds; no approval card, and it works under a hold. What a Bot cannot find is not for Bots: remote access's keys and receipts, push configuration and your terminals are refused, of the data folder only the two logs are read, and anything that looks like a key in them is blanked out. Only when you ask for an analysis or an improvement. Details in [Behavior · Records](docs/behavior.en.md#records) and [ADR 0065](docs/adr/0065-bots-read-this-machines-records.md).
_Avoid_: a Bot writing the database, letting a Bot read terminals or remote access's keys, reading files of the data folder besides the logs, querying on a background timer, reading another Bot's memories into its own context

**Daemon**:
A resident TypeScript process on this Mac that runs the tool-call loop itself. Closing the window does not stop it; if the window crashes, turns keep going. On power it holds off idle sleep; closing the lid, Sleep from the menu bar, a drained battery or shutting down still puts it to sleep, and it picks up again on wake. A killed daemon is relaunched only while the window process is still alive (including when it is hidden in the tray); once the window is gone too, another crash stops it until you open the app again or next log in. Settings has an optional standalone runtime, **off by default**, which stays disabled in production until the sealed-native gate passes; while it is off, the window process remains the supervisor. The daemon also holds the terminal sessions you open, so their processes keep running after you close the window. When you quit or the daemon stops on its own, those processes stop with it, but where each terminal was open and what was on its screen are kept; on the next launch a new one opens in the same place, and the split layout reconnects to it. Only ending the terminal session forgets it.
_Avoid_: cloud computer, 24/7 server, treating the UI process as the runtime, keeps running with the lid closed, stops after one kill, standalone KeepAlive login item, closing the window kills terminals

**App window**:
The Tauri desktop window, which holds the Svelte interface (the code and the development guide call it the messenger). Closing the window hides it to the tray rather than quitting; while hidden, it stays in the Dock. At login it goes only to the Dock and the tray, and the window does not pop up. Clicking the Dock icon, Cmd-Tab, Spotlight, left-clicking the tray, or opening the app again brings the window back. Only one window process runs at a time; a second launch just wakes the existing one and connects to the existing daemon. If the window crashes, it does not come back on its own. Before it connects to the daemon, Quit works, Stop does not, and the interface shows "Can't reach the runtime". The width and height you dragged it to, and whether it was maximized, are the same when you reopen after quitting; the position is not remembered, so the window does not land off-screen after a display change. While you drag the border, the app does not ask whether the window is maximized: on macOS that query moves the window, so on release its position would differ from where you were dragging it.
_Avoid_: browser-only, no tray, hiding removes it from the Dock, window KeepAlive, grabbing the screen at login, multiple windows, treating a window crash as quitting

**Pane**:
One content area in the desktop window: a pane is a group of tabs, and a tab can be a session, a terminal, the routine calendar, the workspace, spend, or usage. The window can be split horizontally and vertically into any number of panes; a window split into several panes is still the same window process, and a floating pane is not a second system window either. Only one pane is the current pane at a time; on narrow screens (≤680px) and phones there are no panes, and it is still one screen at a time, stacked layer on layer. Where each kind of window goes when it is not open yet (new tab, replace the same kind, split, neighbouring pane, floating…) is its **placement**, chosen per kind in the settings and kept on this machine; something already open is only brought forward. Details: [Behavior · Pane](docs/behavior.en.md#pane).
_Avoid_: multiple windows, second window process, treating a floating pane as a system window, split screen on phones, visible means read, rearranging the layout other than as its placement says, opening a second copy of something already open, leaving empty panes around, settings in their own tab, top bar and tab both announcing the name in a narrow pane

**Layout**:
How the panes are divided: the horizontal and vertical splits, each pane's width and height, which ones float, which one is current, and which session each terminal pane holds. It is kept only in this Mac's localStorage, not in the daemon and not in the URL — the URL says only which session the current pane is showing. After you quit and reopen, it is as it was before; if a session or terminal it refers to is gone, it cleans that up on its own; before resetting to the default single pane, it asks about unsaved changes.
_Avoid_: layout in the database, layout in the URL, syncing layout across devices, layout that follows you to another machine, reset discarding unsaved changes outright

**Quit**:
Ends this run of the app. Under window supervision (the default), both the window process and the daemon stop, and the tray and Dock icons both disappear. If the standalone runtime is on, quitting closes only the UI and jobs keep going; stopping them takes an explicit stop (written `runtime.stop`). Turns in progress are marked Interrupted, and the processes in the terminal sessions you opened stop with it; next time you open the app, each terminal that was still open reopens in its original place, and the split layout reconnects to it. It is not closing the window. Only ending the terminal session forgets it. It leaves the Launch at login preference alone. Shutting down and logging out are also treated as Quit for turns. The same rule applies in development mode. In production the standalone runtime is still gated, and the default is still window supervision.
_Avoid_: treating closing the window as quitting, closing only the window by default and leaving a headless daemon, treating Quit as turning off launch at login, Cmd+Q closing only the window in development mode, treating the gated standalone mode as enabled

**Launch at login**:
Optional, on by default. At login it starts only the window process, into the Dock and the tray, and the window does not pop up; the window process then makes sure the daemon is running. Turning it off affects only the next login and does not kill the current run; at the next login neither the window nor the daemon comes up. Quitting does not clear this switch either. The daemon is not a login item of its own.
_Avoid_: window popping up at login, turning it off kills the current run immediately, daemon as its own login item, quitting clears launch at login, turning off launch at login but leaving jobs that start themselves

**Tray**:
The menu bar icon of the window process. Left-click brings the window back. Right-click: Show window, Stop (the most recently active turn when the window is not open), Quit. There is no Hide and no Pause daemon. If the window crashes, the tray is gone too.
_Avoid_: tray badge, a second interface, the daemon running its own tray

**User**:
The one person running this Mac. There are no multiple users and no share links. You are in every group; you and any Bot in a group can bring others in and remove them. Removing a Bot does not delete it. You appear in sessions, transcripts and the present members, but not on the roster's row of letter tiles.
_Avoid_: member, tenant, organization, Bot-only group without you, you in the roster

**Model endpoint**:
A model's HTTP interface (base URL + API key) that speaks one of two formats: OpenAI-compatible (Chat Completions), or Anthropic-compatible (Anthropic's Messages, served by Anthropic and copied by many vendors and proxies). The format is chosen on the endpoint, OpenAI-compatible when none is; the app's own loop and judgements run the same on either, only what goes over the wire differs. Anthropic, Xiaomi MiMo, Qwen (Alibaba Cloud Model Studio) and DeepSeek are built-in connectors: picked when adding, they take only a key, which the app tries on each of that vendor's plan addresses in turn, keeping the one that takes it; an endpoint whose address is one of those plans shows as that vendor, with its logo. Anthropic's own address can carry an Anthropic workspace ID (`wrkspc_…`, required for a personal key not scoped to one workspace), sent with every request; it has nothing to do with the workspace the Bots work in. The app does not ship with any model of its own. You can configure several endpoints; one of them is the default. A completion goes to the endpoint its model belongs to. You add endpoints in Settings, and Bots can add them with a tool too. Creating an endpoint or changing an existing one's URL, format or Anthropic workspace ID is a dangerous action. The default endpoint's URL, format and key cannot be changed, and it cannot be deleted. Details in [Behavior · Completion](docs/behavior.en.md#completion), [ADR 0066](docs/adr/0066-anthropic-format-endpoints.md) and [ADR 0072](docs/adr/0072-built-in-connectors.md). The speech recognition service behind the message box's voice input is not an endpoint: it is set up on its own in Settings, there is one, and Bots do not use it ([ADR 0073](docs/adr/0073-speech-recognition.md)).
_Avoid_: provider catalog, Binder, late binding, per-Bot endpoints, treating an Anthropic-compatible endpoint as Claude Agent, storing a built-in connector as another kind of endpoint, putting the Anthropic workspace ID in the key field, treating the speech recognition service as an endpoint

**Default model**:
From engine level 7, the model and thinking level a Bot runs on when you have not pinned one: the first time it is needed, what it ran on most in the last 7 days among the models the endpoints still list (at the thinking level it ran that model on most), and used from then on, with no card asking you (pin a model on the Bot to change it). A card put up before [Keep it] [Use the endpoint's default] still takes its buttons: declined, nothing is inferred again and the Bot runs on the endpoint's default. It replaces a model call picking before every turn. Details: [Behavior · Model](docs/behavior.en.md#model).
_Avoid_: picking again every turn, a card asking you about a default that is not yours to decide, a default that was renamed or removed from the list

**Model**:
A completion name that a given endpoint recognizes; each endpoint has its own list and its own default. The thinking level is pinned together with the model and never exists on its own: either neither is pinned and the app settles both, or a model is pinned and its level is set along with it. The user does not pick for each turn. From engine level 7 (the default is 8) a turn's model follows a fixed order and nothing picks per turn: the model set on the ticket, else your pin, else the Bot's default model, else the endpoint's default, with which one recorded for each turn; work that needs pictures does not land on a model marked as taking none (unless pinned), and a job that keeps failing, or keeps calling tools wrongly inside a turn, steps up a thinking level; failed hand-overs past the top level climb the model ladder you ordered (a pin or a ticket's model is never switched); a rung may be a model of one of your local agents (Claude, Codex, Grok…), and a turn on it is run by that agent; a ticket's model may be an agent's too, and that agent then does the ticket ([ADR 0076](docs/adr/0076-claude-models-on-the-model-ladder.md), [ADR 0079](docs/adr/0079-local-agents.md)). Below level 7 (a data folder an older installed app that does not read the version gate holds at a lower level), an agent still picks once each time a turn starts, looking at the message, the Bot's profile, the candidate list and recent review conclusions, and answers with a model, a thinking level and a one-sentence reason. Details: [Behavior · Model](docs/behavior.en.md#model).
_Avoid_: provider catalog, a different model name for judgement, picking per turn, thinking level only ever chosen by the app, pinning a thinking level without a model, pinning a model without setting its thinking level, roster-wide shared routing experience, recognizing model feedback by keyword, one remark pinning a model forever, a scoring formula for model choice

**Claude Agent**:
One way a Bot can run: instead of the app's own loop, each of its turns is run by the Claude Code you installed and signed in to on this computer (through the Agent SDK), working with Claude Code's own tools and counting usage against the account it is signed in with (a Claude subscription or an API key). The app still keeps the workspace boundary and your approvals, Stop, the end contract, hand-overs and reviews, and hands it its own collaboration tools as `mcp__deskfolk__*`; the app's own judgements still run on endpoints. Only you switch a Bot's runner, in the Bot panel; the app offers no Claude sign-in and never touches its credentials, it only shows in Settings which credential is in use. Details: [Behavior · Claude Agent](docs/behavior.en.md#claude-agent), [ADR 0061](docs/adr/0061-claude-agent-runner.md).
_Avoid_: "Claude Code engine" (the brand is not a feature name), calling the API with a subscription token, signing in to Claude inside the app, Claude Code as a completion endpoint, a Bot switching its own runner

**Local agent**:
One way a Bot can run: each of its turns is run by an agent program you installed and signed in to on this computer — Claude Code (that is, Claude Agent), Codex, Grok, OpenCode, ZCode, Antigravity, or an ACP command you listed yourself — working with that agent's own tools and counting usage against the account it is signed in with. The app still keeps the workspace boundary and your approvals, Stop, the end contract, hand-overs and reviews: every call it can stop before it runs is decided first, and one it learns of only afterwards stops the turn if it crossed out of bounds; the app's own collaboration tools reach the agent over MCP (Codex: its dynamic tools), and Antigravity gets none, so it answers with a closing reply only. Only you switch a Bot's runner, in the Bot panel; the app offers no sign-in, never touches credentials and never changes the agent's config. Built-in calls and ladder rungs may name these agents' models too. Details: [Behavior · Local agents](docs/behavior.en.md#local-agents), [ADR 0079](docs/adr/0079-local-agents.md).
_Avoid_: an agent as a completion endpoint, signing in to an agent inside the app, rewriting an agent's config file, reading an agent's tokens, a Bot switching its own runner, pretending to hand over without the tools

**Setup wizard**:
The empty state of Settings: it is complete once the workspace path is set and there is either a usable endpoint (its URL and a saved key; an address on this computer needs no key) or a signed-in local agent on this computer with the built-in calls on its models (ADR 0078, ADR 0079). It has no route of its own; it slides out over the sidebar only and does not take over the main transcript.
_Avoid_: /setup, full-screen onboarding, making Settings the main transcript

**MCP**:
Roster-level servers: stdio (command / args) or HTTP / Streamable HTTP (url + optional headers). Every Bot can call the configured tools. You add servers in Settings, and Bots can also add, edit and remove them with tools. Adding a server or changing its command·args / url / headers is a dangerous action. An HTTP server's Authorization is pasted on the approval card and goes into the Keychain, never into tool arguments. Deleting an MCP server is not a dangerous action. The app records the usage instructions a server ships with; you or a Bot can also write a usage note for each server (what it does, when to use it, when not to), which goes into every step's "MCP this turn" section ahead of the server's own instructions. Leave it blank when the server's instructions are enough. Editing the note is not a dangerous action, and changing the connection does not clear it. All tools of an enabled, successfully connected server stay available to every Bot, direct, group and routine; they are never filtered out by message keywords or language. After a server is added, changed or re-enabled, the current turn's next step and other Bots' later completions can use it; once it is disabled or deleted, it can no longer be called. To hand an image from the workspace to a parameter that only accepts an image URL or data URI, the Bot writes `workspace://<path relative to the workspace root>` in the argument, and the app replaces it with the image's data URI before sending (shrinking the image first if it is over half a megabyte); the transcript and the next step still show the short reference. A remote server can't read this Mac's disk, and the model can't copy out a whole image's base64.
_Avoid_: per-Bot MCP, Bot as a tool permission boundary, hiding configured capabilities by keyword, available only in the turn that installed it, stdio only, hand-editing a server's own instructions

**Participation**:
Which present Bots receive a group message: mentions name recipients, otherwise an eligible lead takes precedence; only with no lead are legacy group judgements retained. Receiving a message does not mean interrupting work already under way on that job. For the routing boundary, see the Group lead behavior details.
_Avoid_: asking the whole group for every line, automatic appointment before confirmation, receiving means redirecting

**Judgement**:
A Bot's choice to join in or sit out on an unaddressed user line in an old group with no lead to receive it; it is not an execution segment and does not ask the user a question. Sitting out or failure produces no work reply, and an explicit mention needs no such judgement. For the routing boundary, see the Group lead behavior details.
_Avoid_: a segment for every bystander, joining on failure, judging every Bot line again, every group must judge

**Mention**:
A way to name a group message's recipients: one Bot or all present Bots, bypassing participation judgement but not holds, attribution or execution slots. If that Bot is already working on the same plan, the mention makes the existing segment hear the line, not redirect. Details: [Behavior · Mention](docs/behavior.en.md#mention).
_Avoid_: mention means pause, a group mention cloning itself, mention bypassing a hold, a name in a path is a recipient

**Thread**:
A quoted reply to one message in the main transcript, kept in that transcript rather than a new group or separate conversation. A delegation's collaboration thread reused for “two Bots × plan” is a direct, not this message-reply relationship.
_Avoid_: a quoted reply is a new group, replies hidden in the sidebar, auto-mentioning the user, a collaboration direct as a reply to one message

**Reaction**:
A lightweight acknowledgment of a message, picked from a fixed set of emoji; custom ones aren't allowed. It never carries changed instructions or security decisions; those require a written reply or an approval. In v1 only you add reactions; Bots don't react.
_Avoid_: emoji as approval, custom emoji, ✅/❌ as allow or deny

**Always allow**:
A saved roster-level rule (kind key + scope): from then on, dangerous actions of the same kind go through without asking. It exists alongside "Allow once". Some kinds always require approval and can't be made Always allow (a Bot changing a built-in prompt, for one).
_Avoid_: allow everything, bypass, per-Bot rule

**Search**:
Lookup across Bots, groups, files and routines that jumps back to the spot in the original session. In v1 it is a local search on this Mac, not another Bot.
_Avoid_: semantic memory layer

**Stop**:
An immediate stop that you issue. It applies to turns in progress; actions already done are not rolled back. A command still running stops along with everything it started: it is asked to exit, and whatever is still running 3 seconds later is killed. A Stop is not the job going quiet: it does not get the plan organized, and it calls nobody back; an organizing or a second look the job already had lined up is cancelled too. With the UI open, it hits the turn in the **current pane** (which must be a direct). When several sessions are laid out at once, the current pane is the one that has the keyboard, or the one you last clicked or scrolled in. From the menu bar with no UI open, it hits the turn in the most recently active direct. Until the engine level reaches holds, groups have no Stop; to stop group work, say "stop" in the group (see Control line). Once it has, each Bot's reply being written in a group has a Stop of its own, which stops only that Bot's turn while the other Bots go on, and the menu bar's item becomes "Stop everything" (see Hold); a Stop is also a hold: on that Bot's work in that plan only (on just that turn when it has no plan), so the check-backs it booked are set aside rather than voided and nothing else wakes it back; no receipt goes into the conversation (it stopped the very turn you pressed it on; where it stopped is recorded on the hold); your next line to it about that job — "continue" included; in a group, one naming it, answering it or naming nobody, not one only to another Bot; and not one you sent before pressing Stop — lifts it, and the Bot goes on from that line, with no note of the app's; for a job it was doing where you cannot speak (its direct with another Bot, say), say "continue" in its direct or naming it in a group: filed under that job, it lifts the hold, and the Bot goes on from your line where you said it. Clearing history, archiving, or deleting a group still ends that session's live turns, and is no hold. There is no step-count, roster or group-size circuit breaker.
_Avoid_: stopping the turns in every pane at once, deciding by the topmost floating pane, stopping only the shell itself

**Hold**:
A stop of yours, recorded as a row of its own rather than as a "parked" label a model can set back. It has a scope — everything, one Bot, one session, one plan, one ticket, one Bot's work in one plan, or one turn — and may carry more it covers, fixed when it was made (the work that Bot handed on and has not had back). Only you lift it, with a line of yours or a button; the record is never deleted, not even by clearing a chat or deleting a group. In the same step it is made, the running turns it covers end (with their commands' processes and MCP calls), and where each had got to is recorded on the hold, which is what the receipt is written from. A hold on a plan or a session shows the plans it covers as parked, and neither the organizer nor a resume can set them back to In progress; the check-backs it covers are set aside; lifting it puts both back, and each turn it ended starts again on a note. A hold on a Bot, a ticket, a turn or on everything leaves plan status alone. A stop is only "stop for now" (ADR 0071): nothing it covers wakes a Bot by itself — no turn opens, a held Bot's own line wakes nobody, and a call with an effect does not run — but nothing you say or do to a Bot is held: a line, a change to your line, Insert now, Send back, your answer to its question, Continue or Lift make it go on; every stop your word is about is lifted whole, one over more Bots too, though only the Bots you speak to go on (ADR 0081); a line only asking where the work stands releases nobody, and the Bot answers still stopped; only under a hold of the app's does your line open a read-only turn, where the Bot says it is still held; each wake it turns away is recorded in the work log, with the cause and the holds. Triggers in the database add a last layer, so not even an older build opens a turn a hold covers. Besides a line, a stop can come from a stop menu: while a Bot is at work in a group, the menu beside Send offers "Stop the work in this group", "Stop all of X's work", "Stop this job" and "Stop every Bot"; the flow board offers "Stop this job" and "Stop every Bot"; the menu bar offers "Stop everything". Every stop (a Stop on a card, the group menu, "Stop every Bot", the flow board, the tools menu, a "stop" you say) ends with your next line about it, and the Bots that line is said to go on from it, instead of waiting for you to lift it. A stop from a menu gets a receipt in the conversation you are in too. A stop leaves no state on screen: above the conversation list are only the stops you dropped a job with by a button, which no line ends, each with a Lift; the flow board lists its job's own parking and the holds that wait to be lifted. Holds exist only once the engine level has reached them (see Schema gate). Details: [Behavior · Hold](docs/behavior.en.md#hold).
_Avoid_: taking parked for the hold itself, a Bot or the organizer lifting a hold, deleting a hold, parking a whole plan because one Bot in it was stopped, clearing holds with the chat history, a held Bot woken by another Bot, a check-back or a routine, letting a held turn run a command or send a message, letting a running turn finish its step after a stop, a stop still on after you gave a new instruction so it only gets a read-only answer, a stop left in the list for you to Lift, a status question setting the Bot going, the app speaking for a held Bot

**Control line**:
A line of yours that line reading (a model) reads as nothing but a stop ("stop", "stop what you're generating", "stop all your work"; "you haven't stopped" too, a stop again) is carried out by the app there and then: the hold is made and the running turns it covers end, with no turn and no organizer; a line read as a go on ("continue" alone, or with more in it like "continue with episode 2, …") is not carried out by the app: it is filed under the job it is about, lifts the stops that keep the Bots it is said to from that job, and goes to the Bot like any line, which goes on from it and answers you itself. Whether a line stops or goes on is the reading's alone (from 2026-10-09, [ADR 0070](docs/adr/0070-the-app-stays-out-of-the-conversation.md)): the fixed rules no longer read first or carry anything out, and only give the scope the words name and whether a stop's receipt also offers "Drop this job" ("never mind, stop"); when the reader cannot read the line (none set, an error, a timeout, so the word lists read it), nothing is carried out and the line goes to the Bot — for a stop that cannot wait, press the composer's Stop button. The reading starts as the line arrives, so a line read as nothing but a stop still goes ahead of lines still being read. A "stop" in a script, a line or a picture ("Reviewer: stop"), a condition ("stop if it gets stuck") or a request about the work ("don't pad it with frozen frames again") is none; a question asking it to stop ("can you stop for a moment?") is a stop, while asking whether it stopped or can stop ("has it stopped?", "why is it still running?", "can it stop?") is a line for the Bot; a Bot's name without an @ counts as said to it only when a comma, "you" or "too" follows it. A stop's receipt goes in the conversation you said it in: which turns it ended and where each had got to, how many check-backs it set aside, which plans it parked, who is still working beside it in the job, and what is running now — written only from what the hold recorded. Where it applies comes from the words and the place: in a direct, the Bot on the other side, with the work it handed on and has not had back (three handoffs down); in a group with nobody named, the group; with a singular "you", the Bot you are answering (or the only one that spoke to you in the last ten minutes) and the group; each Bot named; "all Bots" or "stop, all of it", everything, routines too — unless the line also says "you", names a Bot, says in the group or in the direct, or says "this job", which wins as the narrower scope. "Continue" lifts only stops on the job it is filed under: on the Bot, on its work in that job or ticket, on one of its turns; this conversation's own stop, and a job you stopped from here, only when it is said to every Bot here; a stop on any other job stays, and only "all Bots" or "all of it" lifts every stop you made before it (Stops you pressed included); filed under no job, it lifts only stops on the Bot as a whole. Said in your direct, the Bot goes on there; stopped work the line did not wake it to starts again where it was, on a note for that Bot alone (your words, what it was doing) that the conversation does not show. With nothing held it is an ordinary line; after a Stop it is the next line about the job that lifts the Stop's hold; one said to a Bot leaves the other Bots' Stops alone; a stop that still holds (everything; a whole group or job stopped elsewhere) stays, and the Bot can only answer read-only, told the stop still holds, that it is lifted on its receipt, and not to say it is going on; a stop from a group's stop menu goes with your next line in the group, "@X continue" included, and only the Bots it names start again on a note. A go on gets no receipt: the Bot that goes on says so. A line read as a stop beside other words ("stop, and make shot 3 a night scene") goes to the Bot as usual, carrying only a Stop button, and one read as both also Continue (which still lifts by the old rule); a go on with more in it, and "never mind" alone, carry none. Each button is pressed once: Undo on a receipt lifts that stop, the stopped work starts again, and a line that was read as the stop goes to the Bot as the line it was (in your direct with the Bot, that line is what reaches it, not a second turn beside the stopped one; in a group the line wakes only whom it names, so the stopped work starts again all the same); "Stop every Bot"; "Stop “…” too" stops the plan other Bots were still working in; "Only “…”" narrows a stop on all of a Bot's work to that one job, and the rest of its work starts again on a note; "Drop this job" records the stop as dropping the job, and lifting it reopens the job. On a status line or receipt a button brings, "Only X goes on" splits the wider hold in its way into one per other Bot and lets only X go; "All go on" lifts that hold too. "Stop" on a line with buttons makes the stop that line meant, and its receipt quotes the line. Exists only once the engine level has reached holds. Details: [Behavior · Hold](docs/behavior.en.md#hold).
_Avoid_: carrying out a stop or a go on the word lists read, fixing a miss by adding words to a list, a stop line going through the organizer, taking "don't pad it with frozen frames again" for a stop, swallowing a request and acting only on the stop in it, a receipt that says what did not happen, the app answering "continue" or "has it stopped?" for the Bot, carrying out "continue" before it is filed, a "continue" lifting a stop on another job, swallowing "continue" instead of passing it to the Bot, lifting the whole group's stop with "@X continue", a Stop quietly left in force after "all Bots continue", taking a "stop" in quotes, in code or beside a 😂 for a stop, swallowing the line that was read as a stop after Undo, letting the other Bots go too on "Only X goes on", a line to another Bot in a group lifting this Bot's Stop

**Status question**:
A line of yours that only asks how things stand ("how's it going", "where is episode 2 at", "where's the final cut?" — read so by line reading) is not answered by the app: it goes to the Bot it is said to like any line — into its inbox when it is working, read at its next step without cutting it off, or waking it when it is not — and the Bot answers. When the filing reads it as new work it counts as done in place: what the Bot looks up or runs for it opens no job, so "how's it going" never becomes a job of that name. The app used to answer itself, with a status line in the conversation that woke no Bot; that went on 2026-10-09 ([ADR 0070](docs/adr/0070-the-app-stays-out-of-the-conversation.md)): that morning you asked "where's the final cut?" twice in the video director's direct and both times got a status line under its name, while the Bot heard neither line; it was not working at all, so the line could only say nobody was. A status question costs a Bot's call.
_Avoid_: the app answering for a Bot about where the work stands, putting the app's status under a Bot's name, waking the whole group for a "how's it going", interrupting a working Bot to ask for status, filing "how's it going" as a new job, taking a line with an instruction for a status question

**Turn**:
One Bot's execution segment triggered by a message or wake: working, choosing attribution at a desk, or answering read-only under a hold; waiting for your approval or answer still belongs to that segment. Ending it does not mean the job is delivered or accepted. Lines you send in a row are taken in the order they came: the first opens the turn, the next are read at its next step; one not read yet can be taken back, or inserted to be read now ([ADR 0069](docs/adr/0069-take-back-or-insert-a-line-not-read-yet.md)). Details: [Behavior · Turn](docs/behavior.en.md#turn).
_Avoid_: turn as ticket, a turn ending means acceptance, a peer line clones same-plan work, endless tool calls, a later line overtaking an earlier one as the trigger

**Archive**:
Removes a Bot from the roster's main list; its sessions, profile and routines remain, and it can be restored. Its direct moves to the archived list, and what waits there does not count toward the Dock badge until the Bot is restored. Only deleting removes the Bot from the roster (files in the shared workspace are left untouched).
_Avoid_: hide as pause (archiving is not Stop)

**Dangerous action**:
Needs approval before it runs: reading or changing anything outside the workspace, outbound network access (except model calls), adding or changing MCP servers (including command·args / HTTP url·headers), creating an endpoint or changing an existing endpoint's URL (or Anthropic workspace ID), an unconstrained shell, and a Bot changing a built-in prompt or putting it back on its default. Reading / writing / deleting inside the workspace, calls to configured MCP servers, the workspace shell, and adding or changing model names on an existing endpoint's list simply go ahead. Deleting an MCP server is not a dangerous action. The default endpoint's URL and key cannot be changed, and it cannot be deleted.
_Avoid_: gate, ConsentGate

**Outside the workspace**:
A path that, after `realpath`, does not fall under the workspace root prefix. A symlink inside the workspace follows its target: if the target is outside the workspace, so is the symlink.
_Avoid_: string prefix only, judging by inode / hard link

**Workspace shell**:
A `shell` run that passes the pre-launch path check: its cwd is inside the workspace, and no path visible in the command leaves the workspace. It makes no difference what characters a path name is written in; URLs (except `file://`) and devices such as `/dev/null` and the standard streams don't count as paths. It just runs. It is not a kernel jail.
_Avoid_: whole-machine shell, sandbox, seatbelt, App Sandbox container as the workspace root

**Unconstrained shell**:
A `shell` spawn judged to go out of bounds. That process and its descendants skip the workspace path check; the next `shell` is judged afresh. One exception: a recursive search (`grep -r/-R`, `rg`, `find`, `du`, `ls -R`) whose resolved root is your whole home folder or `/` skips the approval card entirely and is refused before it runs, with a suggested rewrite; the judgment follows the resolved path (`cd`, `~`, `$HOME` included), not the command string, a shell comment does not count, and a command it cannot parse — a pipe, a subshell, `eval` — is left alone; so is a search held to a few levels (`find -maxdepth N`, `rg --max-depth N`, N at most 3), which does not walk the whole tree. The same search scoped to the workspace root or a task directory still runs unapproved.
_Avoid_: permanent lift, kernel jail release, an always-allow rule bypassing this refusal

**Terminal**:
A shell session you open yourself on this Mac, held by the daemon; it has the same rights as Terminal.app, with its cwd starting in the workspace by default but not confined to it, and needing no approval. Bots can't see it, can't use it, and don't know it exists; on the desktop one terminal tab is one session, and phones and narrow screens gather all sessions on the Terminal page as its tabs. To stop one, you must explicitly choose "End session" and confirm. Details: [Behavior · Terminal](docs/behavior.en.md#terminal).
_Avoid_: treating it as the workspace shell, a terminal for Bots, approval cards for terminal commands, killed when the window closes, closing a tab kills the process, pane tabs as the session list, a row of sessions inside one terminal tab, two tabs pointing at the same shell, surviving a daemon restart, cloud computer

**Remote screen**:
A paired device seeing and operating this Mac's screen, on the phone's "Mac screen" page. The picture and input come from macOS's own Screen Sharing; Deskfolk captures nothing and injects nothing itself. It goes direct when the two can reach each other and through the relay otherwise. Off by default, and only the Mac window's settings can turn it on; Screen Sharing needs this Mac's account password, typed on the phone once and kept there after it gets in, so later connections sign in by themselves. It works at the lock screen, not with the lid shut, asleep, or after a restart before anyone has logged in. On Windows the picture and input come from a VNC server the user installs; the page is called "Computer screen" and asks for the VNC password. Details: [Behavior · Remote screen](docs/behavior.en.md#remote-screen).
_Avoid_: remote desktop, letting Bots drive the screen, turning the switch on from the phone, viewing this Mac from its own window, capturing the screen ourselves, keeping the Mac password on the Mac or the relay, cloud computer

**Command stream**:
The live push of stdout / stderr while a Bot runs a `shell`, so the call can be seen while it runs. It is visibility only and doesn't change what the call is: stdin is still closed, the timeout is still ten minutes, and paths are still judged per call. It is not a terminal, has no input, and stays out of the main transcript: while running it hangs under that message bubble, when done it folds into one line, and to look back at it you use the turn view in the work dir.
_Avoid_: input for the command stream, treating it as a terminal session, letting it change approval granularity, putting it in the main transcript, a new message kind

**Ask**:
A Bot asks you about something that needs your judgment (not a tool approval). The question appears in the transcript, and the turn continues once you answer. When the possible answers can be listed, the Bot offers options: single choice when only one can hold, multiple choice when several can hold at once, with the recommended one first; you can always skip the options and write your own answer, or pick one and add a sentence. Your answer is recorded on the ask itself, not sent as a separate message from you: the card keeps what you picked and what you wrote, and later turns, the organizer and search all read it from there. Each ask is answered only once. From level 2, a line you type in the conversation while the Bot waits on its question (no files attached) is your answer to it, written as your own text, and the turn continues.
From level 4, a Bot that ends a segment of work as blocked, saying what it needs from you, leaves a **work question card**: that segment has ended, the card stays in the job's conversation, and your written answer queues the job again; answering lifts no stop, and under one the answer is only held. Details: [Behavior · Work question card](docs/behavior.en.md#work-question).
A Bot's question (an ask, or the work question card a blocked ending leaves) that reads as only asking your OK to go on with what you asked for — a sign-off on work in progress, whether it may start the next step — is sent back once, and the Bot goes on; asked again, it reaches you. The app itself asks you only when you have to let something through, when it needs what only you can give, or when it has stopped and will not go on by itself; what it decided for you, what you just said and what it will go on with, it does not ask about. The list: [Behavior · When the app asks you](docs/behavior.en.md#when-the-app-asks).
_Avoid_: making the ask an approval card, sending the answer as a separate message from you, adding an "Other" option, changing the answer after answering, answering the card lifting a stop, the app asking you about what it decided for you, what you just said or what goes on by itself

**Interrupted**:
When the daemon dies, is killed and relaunched, or when you quit, shut down or log out, the turns in progress are marked interrupted. Commands those turns still had running (and everything they started) are asked to exit; any still running when the daemon next starts, because it died or quit before they were done, are stopped then, after checking that the process number still belongs to that same process, so a program that has since been given the number is left alone. In the transcript that line carries an avatar and name like any other Bot message, and "Continue" sits right after the "Interrupted" bubble: it opens a new turn whose trigger is that interrupted line, and does not retry the call that was cut off; that Bot's next turn (in any session) sees "the last turn was cut off", once only. Work a restart cut off does not pick up on its own up to level 3; from level 4 the supervisor decides by the restart's cause whether and when it does. Work that goes on by itself (or that a stop of yours holds) gets nothing more: each turn's own "Interrupted" line says enough. Work that does not (level 3 and below, an external call with no known outcome, development restarts in a row, a turn on no job) gets one line per job once the daemon is back, in the conversation the job belongs to where you are (where you last spoke about it first): why it started again (a deliberate stop, an unexpected exit, a development run restarting), and where each turn stopped; the line carries Continue and Not now, and one notification. Work that was to go on by itself but was cut off again by another start before it could is told by that later start. Details: [Behavior · Interrupted](docs/behavior.en.md#interrupted). Closing the lid or system sleep is not an interruption: the turn freezes and carries on after wake. Time asleep does not count as being stuck, nor toward a command timeout; a request cut off by sleep waits after wake for the network to come back (about a minute), then is resent in full. An app window crash is not an interruption: the daemon keeps going. Completion timeouts, stalled streams and endpoint 4xx/5xx errors are not interruptions. A health check that fails temporarily while the daemon process is still running is not an interruption either: the window does not launch a second copy, and a second copy that cannot get the port does not touch the database.
_Avoid_: resuming tool calls from the break point, leaving the interruption only in a Bot↔Bot direct you are not in, a Continue / Leave it card for work that goes on by itself, resubmitting a last review or render whose outcome is unknown after a restart without asking you, killing a previous run's process by its number without checking, treating sleep as an interruption, treating shutdown as sleep, treating a window crash as an interruption, keeping "the last turn was cut off" on the profile forever, treating a completion timeout as an interruption, treating an endpoint error as an interruption, treating a health-check timeout as an interruption

**Completion**:
One streaming HTTP request to the endpoint within a turn: Chat Completions, or Messages on an Anthropic-compatible endpoint. A turn's tool loop can make several completions. A failed completion is not an interruption, and it does not replay earlier tool calls. Every completion has an output cap (the model's `max_output` in its endpoint's list, 32,768 tokens when unset) and a time limit that counts only the completion itself. One that starts repeating itself, is only a canned one-line refusal, breaks off before it is finished or runs past its time limit has failed and is not a reply: nothing of it is posted, it wakes nobody, and it is tried again; if that fails too the turn ends as failed. One cut off at the output cap without repeating is carried on once. Details: [Behavior · Completion](docs/behavior.en.md#completion).
_Avoid_: treating one completion as a turn, treating a completion timeout as an interruption, posting a cut-off or repeating reply as the closing line, treating half a stream as a reply, counting streamed output as the turn making progress

**Redirect**:
Ending a segment's remaining actions and starting another from a new message, without rolling back past effects. It is a legacy migration-path behavior, not the default meaning of a group mention in the new work-item path; Stop or a hold is how to halt immediately. For the boundary, see the Turn behavior details.
_Avoid_: every new line redirects, a mention replaces a hold, one line clears the whole group's work

**Fork**:
Starting a segment beside an existing one while the first continues; two executions, not two copies of a job. The new work-item path allows bounded parallelism on different plans only, and same-plan messages enter the existing segment. For the boundary, see the Work item behavior details.
_Avoid_: bypassing same-plan uniqueness, opening a turn bypasses a hold, group mentions clone the Bot

**Pull-in**:
@-mentioning, in a group, a Bot that is not in the group but is on the roster and not deleted: it is added to the group first, then joins in. A name that is not on the roster does not create a new Bot; the message is still sent.
_Avoid_: @-mentioning without joining the group, implicitly creating a Bot for an unknown name

**Artifact**:
A workspace-relative path, or an `http`/`https` link, referenced in a message; the file itself lives in the workspace (or at the remote URL), and files written during a turn appear in its final message automatically (not those the turn deleted again). Opening one shows it in the preview panel to the right of the chat (image / audio and video / PDF / text / single-file HTML / Word / Excel / PowerPoint); other kinds offer a download or opening with the default app. In a handoff, the path goes into the message to the other party, with no separate kind; artifacts inside the workspace can be annotated (see "Annotation"). Details: [Behavior · Artifact](docs/behavior.en.md#artifact).
_Avoid_: asset library, Artifact table, snapshot copy, per-Bot artifact folder, `@file`

**Annotation**:
A remark you write about one spot in an artifact, attached to a workspace-relative path, an anchor, and the message that delivered the artifact. It starts as a draft the Bot cannot see; drafts collect into a batch sent all at once as one reply that quotes the delivering message and @-mentions the Bot that delivered it; once sent it is "Pending", and a Bot or you mark it "Resolved", and a resolved one can be reopened. An annotation is not a snapshot of the artifact: it records only the quote, position and file hash at the time and does not keep the old file; only files inside the workspace can be annotated, and link artifacts cannot. Details: [Behavior · Annotation](docs/behavior.en.md#annotation).
_Avoid_: comment (kept for a possible multi-person future), review, a new message kind, annotations storing old versions, waking once per annotation, a Bot annotating for you

**Attachment**:
A file **you** drop into the chat, copied into the workspace's `inbox/`, with a link to that copy kept on the message. A remote connection also has a session just for sending files: files sent there also go into `inbox/`; you can send text there too, and the text stays only in that session; that session has no Bot and wakes no one. A file sent in an ordinary session still wakes that session. When a Bot attaches a file already in the workspace as an artifact, it uses the same attachment rows, but nothing is copied and nothing goes into `inbox/`; so does a file or folder you drag from the file tree into the composer, which goes out as its own path (the file-drop session does not take these). The workspace is the computer; attachments are not a second file system. Raster images that enter a turn's window are sent to the model as pixels, but a turn carries at most 20 images and 20 MB: they are taken from newest to oldest starting at the trigger message, and older images that do not fit keep only their path; a large image is first scaled down to 1568 on its long edge, and an opaque one is converted to JPEG before it is sent. When a Bot itself reads a PNG / JPEG / GIF / WebP in the workspace with `read_file`, the image is scaled the same way and attached as an image after that step's tool result: at most 12 images and 8 MB per step; these images take their share of the turn's 20 images and 20 MB first, and the transcript window gets what remains; when later-read images do not fit, earlier-read ones are moved out in the order they were read, keeping only their path, and to see one again the Bot reads it again. Other files are given only as paths; reading them goes through `read_file`.
_Avoid_: a ghost file that exists only on the message

**Profile**:
A Bot's name, role description, boundaries and avatar. A Bot can change its own name, role, boundaries and avatar, and no profile-change line is inserted into the transcript when it does; you can change them again at any time. Names of Bots that are not deleted must be unique. The avatar is a generated image or a raster image, not memory; a new Bot starts as Pudding, the mascot (the mustard teammate from the Deskfolk mark), its face and accessory varying with its name, acting out the Bot's status in the conversation list. Changes in the Bot panel save automatically (they are written once you pause for a moment, and anything unsaved is sent before you switch or close the panel); there are no save or close buttons, and the panel has only a single ✕ in the top-right corner. In settings, the workspace, endpoints, and MCP names / notes are likewise written as soon as you change them; adding an MCP server or changing its command / args / URL / headers still needs confirmation, and there is no Always allow.
_Avoid_: writing memory into the profile, a save button on the profile panel, a save button in settings

**Catch-up**:
After the daemon comes back (on wake, relaunch after a crash, reopening after quitting, or startup), each missed routine runs only its most recent due run once, without running every missed cycle back to back. After waking from sleep it waits a minute before catching up: with the lid closed the system wakes itself for a few seconds, and the network is often not back yet at that point.
_Avoid_: skipping whatever was missed, running once for every missed run, catching up after sleep but not after quitting

**Context window**:
What the model actually sees in a turn: the profile, the catalog of enabled skills, the system instructions, the "MCP this turn" section, this Bot's memory, the situation block, the most recent stretch of the transcript, and this turn's tool loop. The system instructions, the notes opening the skills, memory and MCP sections, and the tool descriptions are built-in prompts: what you changed applies from the next hop. The full history exists only in the database, for you to browse and for search; it is not stuffed into the model wholesale, and judgement calls use a separate, shorter window without images. For an oversized tool result, the full JSON is first saved in the workspace, and the window holds only a bounded preview and full_result_path. When a turn's loop grows past what fits (an endpoint refuses it as over the context, or it reaches 75% of a known window), its older hops are condensed into a summary by the turn's own model (or the one chosen for Compaction under Settings → Roles) and the newest stay word for word, on the editable built-in prompt "Context compaction". Details: [Behavior · Context window](docs/behavior.en.md#context-window).
_Avoid_: automatic summaries into the profile, a semantic-retrieval memory layer, a background distiller, estimating by token count, feeding earlier turns' tool results back in

**Spend**:
An append-only ledger of calls on this machine; eight kinds of endpoint call each record one row: turn completion, judgement, model routing before a turn opens, correction-chain review, each learning step after a review, input suggestions, organizing, and acceptance checks. A call that shares its kind with others also records its purpose and gets a line of its own in the view (the scribe, line reading and the retrospective bill under organizing, an acceptance check's calls that look at frames are picture judgements). When the provider returns `cost_in_usd_ticks`, the call is recorded as reported; with no reported cost, it is estimated when both input and output tokens are present and a billing price is configured. The app has a separate spend view; the session top bar, list rows, settings and the model choice log show no spend figures. Details: [Behavior · Spend](docs/behavior.en.md#spend).
_Avoid_: budget circuit breaker, daily limit, automatic shutdown, treating estimates as reported or merging them into one amount, estimating missing tokens with a tokenizer, folding judgement into turns, MCP tools' own bills

**Local API**:
The HTTP + WebSocket interface the daemon serves on `127.0.0.1` for the app window, protected by the local token. Changes go over HTTP; the transcript stream goes over a receive-only WebSocket. Through it the window reads and writes the roster, sends messages and subscribes to the transcript stream.
_Avoid_: treating the UI process as the runtime, cloud API, two-way command channel, workspace files as HTTP resources, putting the local token in the URL

**Local token**:
A random secret the daemon mints fresh every time its process starts, used to authenticate requests to the Local API. HTTP sends it as `Authorization: Bearer`; the WebSocket sends it in the first message after connecting, never in the URL. A window crash does not change it; after the daemon exits or crashes, the next process mints a new one. It is not the endpoint API key, and it goes into neither SQLite nor the repository.
_Avoid_: API key, a long-lived key installed once, writing it into .env, putting it in the WebSocket query

**Judgement log**:
The record of join-in / sit-out decisions, visible in the current conversation's settings. It does not go into the main transcript.
_Avoid_: treating judgements as turns, flooding the main transcript

**Model choice log**:
The model and thinking level a turn ran on and why (set on the ticket, your pin, the default model, the endpoint's default, and whether it stepped up or climbed the ladder), which category the message counts as, how the turn ended (a failed completion carries its failure kind), how long it took and how many steps it made; below engine level 8, also the model feedback that later lands on that turn, the review of its correction chain, and the lessons recorded. It sits on that turn's card on the flow board and no longer has a separate entry point or page: a line at the bottom of the Bot card shows the model, thinking level and category, with a separate mark for feedback, for blame placed on the model, and for a failed completion; clicking that line expands everything below the card, and clicking a piece of feedback jumps back to the original words. The flow board toolbar can light up the cards that have feedback or whose review blamed the model and dim the rest, without changing the shape of the whole job. It is viewed by job, not by session: when a job spans several sessions, all of its choices are on the same board. It does not go into the main transcript and shows no tokens or spend; the Local API can still list it per session.
_Avoid_: routing log, a separate model choice log page, a log button on the session top bar, going into the main transcript, stuffing it into the current conversation settings, putting spend statistics here, treating criticism of the content as model feedback

**Schema gate**:
The check the daemon runs when it opens the database: if the database's `schema_min_compatible` is above `SCHEMA_LEVEL`, what this build understands, it refuses to open, writes why to daemon.log, and exits — instead of running on and misreading semantics it does not know. `engine_level` is the paired integer switch, standing in for a pile of separate feature flags, and only ever moves forward in order: every time the daemon starts it tries to take it up to the highest level this build turns on by itself (`ENGINE_LEVEL_BY_DEFAULT`, since 2026-10-04 this build's top level, level 8's quality events and lessons), raising the database's floor to what that level needs in the same step (1, for holds; 6 at level 8); a level a later build brings above that starts out experimental and goes up only through a developer's opt-in, whether or not an older installed app shares the data folder. But while an installed app sharing the default data folder does not read the gate yet (or its version cannot be read; off a Mac there is no telling which one is installed, which counts the same), a source run leaves the level where it is, writes why to daemon.log and runs at the level it has — such an older app would open the database whatever its floor says. A developer can accept that on their own machine (`engine_gate_optin`: `POST /v1/capabilities/raise` on the local API, or `apps/daemon/scripts/engine-level.ts --accept-older-app`; never from a phone), taking on that the older app, opened without this daemon running, would ignore holds; the level then goes up at once (at the next start when no daemon runs), and taking the opt-in back never lowers it. The opt-in covers only the level of the build that accepted it (or, past an older installed app, with `--level`, only as far as asked — level 5 without level 6, say; with no older app in the way `--level` changes nothing, and the database goes to the default level): a later build bringing a new level asks again; an opt-in an earlier build recorded below the default level never holds a data folder no older app stands in the way of below that default. `GET /v1/capabilities` reports both numbers, plus which features are on, to whoever calls it — including a phone, since the Mac may be running an older packaged daemon while the messenger's source tree has already moved on.
_Avoid_: treating schema_min_compatible as the app's version number, raising engine_level before both conditions hold (the gate itself shipped, and the installed app's own version is already new enough) when no developer explicitly accepted an older one, a setting a user would ever see

**Organizer run log**:
Every organizer call that actually reached the model, whether or not it landed, gets one row: the raw answer it read, the decision it parsed out, the candidates it could pick from (which plans it could resume or join, which acceptance checks it could edit — as read when the call went out) alongside the ones the answer actually picked (as the model wrote them, before validation — when a named resume/join target no longer qualifies, the decision falls back to continue, but the row still keeps what it named; a resume/join target only counts as named beside the decision that uses it. Whenever the written decision is not the one that applies — a target that no longer qualifies, no target at all, a word that is none of the four, anything but continue from a settle — the row says why), the same candidate sets re-read once the call returned (compare the two to see whether they shifted while it was out), whether it landed, why not when it didn't, notes on a clean apply that still held part of the answer back (a settle that called a parked plan active, a field a settle kept because it only files the handover, tickets that kept a plan called done still active), and which ledger row this call was billed as. `GET /v1/debug/organizer-runs?task_id=` reads a plan's rows, local only — never on the remote whitelist, never reachable from a phone; Bots can query it through the records (ADR 0065); each session keeps only its newest batch, and clearing history or deleting a group takes this log with it (unlike spend, which is kept on purpose). Only when the window spawns the source daemon itself does its stderr land in `daemon-dev.stderr.log` in the data directory (rotated once by size, checked only at each spawn) — `pnpm dev`'s own daemon is pnpm's child and never passes through that code; where the window has no console at all this used to go straight to `/dev/null`, and under `tauri dev` it was already visible in the terminal and just moves into the file instead.
_Avoid_: a screen made for you, the main transcript, the remote whitelist, a packaged build also writing this stderr file (only the source-run dev daemon does), the `pnpm dev` daemon writing it too (it never runs through this code path)
