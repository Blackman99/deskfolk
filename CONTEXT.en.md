# Deskfolk

[简体中文](CONTEXT.md)

A single-person agent collaboration app running locally on macOS: a team of named, persistent Bots splits one job and hands it on until it is delivered, while the app keeps the plan and its done-when in view, chases what stalls and checks the delivery first. They collaborate through directs, groups, mentions and asynchronous handoffs (modelled on Grok Bot); the computer is a shared folder on this Mac, not a cloud VM.

> **WIP**: This document defines the domain language; it is not a statement that every capability has passed acceptance. For the current scope, see the [README](README.md); for the direction of work on agent decisions, feedback on automatic tasks, reflection after each run, and full coverage of conversation operations, see the [roadmap](ROADMAP.md).

## Language

**Bot**:
A persistent teammate with a name, a role, and boundaries. It has its own 1:1 session and profile, and it does not disappear when a task ends. When it hits an obstacle, it first investigates on its own, tries the means available, and verifies against the original goal; it does not hand technical work it can finish itself to the user, and asks for help only with permissions, credentials, information, or decisions that only the user has. Trying things on its own is still bound by approvals, denials, Stop, and the boundaries of its profile, and it does not blindly repeat actions that have side effects.
_Avoid_: Agent, child agent, subagent, assistant, Endpoint

**Roster**:
The set of all Bots on this machine. There is no limit on how many there are, and anyone can create one. A Bot is not a security boundary. In the messenger, the roster is a single row of letter tiles at the top of the sidebar, not a grid of cards, and it does not include you.
_Avoid_: team account, tenant, seat, roster cards, putting you in the roster row

**Group**:
A shared session of at least two Bots (with no limit on members) that has its own name: whoever creates it names it, the name cannot be empty, and it is not assembled from the names of those present. When a handoff needs to be visible, use a group rather than making a person the router. A conversation with fewer than two Bots is a direct, not a group.
_Avoid_: channel, room, workflow, plan DAG, group member limit, using the member list as the group name

**Direct**:
A one-to-one session between you and a Bot, or between two Bots. Bots can hand work to each other asynchronously by private message. In a Bot↔Bot direct, one side's closing reply for its turn wakes the other side, just as send_message does; if the other side is already working, the reply is heard by that turn (see "Mention") instead of interrupting it. Once the talk goes quiet, the Bot that opened the direct is called back to the origin session by a check-back to report the outcome (see "Check-back"). You have only one direct with a given Bot, and you keep using it; a Bot↔Bot direct is opened fresh each time, each one covers only that one matter, and none continues from the previous one. You can only read a Bot↔Bot direct; you cannot post in it.
_Avoid_: thread (thread is reserved for replies to a single message), one long-lived direct per pair of Bots

**Session**:
The conversation container of a direct or a group. Messages, turns, judgements, and spend all belong to it. A Bot↔Bot direct is also a session; you are not a participant in it, and you can open it to read but cannot post.
_Avoid_: channel, room, treating a thread as a session

**Origin**:
The message a Bot↔Bot direct was opened from: the message that woke the opening Bot for the turn in which it opened the direct. The direct's entry hangs under that message, and the direct's row in the sidebar also shows its origin and can be clicked to go back to it. Once the origin session is cleared or deleted, the direct has no origin and can still be read as usual.
_Avoid_: parent session, thread, taking the Bot's own line "I'll go ask X" as the origin

**Handoff**:
One Bot passes work to another Bot, by speaking in a group or by private message. The receiver wakes up to handle it and can reply later.
_Avoid_: assigning work, routing, dispatch, bind

**Workspace**:
One local folder at the account level. Files, artifacts, and handoff attachments all live here, and all Bots share it. Bots are not isolated from each other. The messenger sidebar can open the whole workspace folder (on desktop it is a pane with a file tree and a preview, and it does not take over the artifact preview beside the conversation; on narrow screens and phones it is still an overlay that slides in from the right); UTF-8 text files in the workspace can be edited in the viewer and saved back to the same path.
_Avoid_: cloud computer, one folder per Bot, sandbox (unless a separate one is added later)

**Plan**:
The one thing currently being moved forward in a session, pieced together by the app itself; you do not have to define it first. The code keeps the `tasks` table and `task_id` (historical names; comments call it a plan). It is written up as **the plan**, with these fields: Kind (used to find precedents), Goal (what exactly is to be done now), Done when (how completion is judged), Rules (the standards, constraints, and improvement notes you have set), Process (the process and who does what), Progress (done / to do / stuck), and Status (in progress / done / parked); it also keeps the verbatim text of the request that opened it (the original request). The organizer updates the plan after each of your messages and after the plan goes quiet; every revision leaves a record (which message or turn caused it, or that you made it), and you can also edit it directly on the flow board. A session has only one current plan at a time: when the organizer judges that you have moved on to a different thing, it opens a new plan and parks the old one; when it judges that you have returned to an earlier thing, it picks that plan back up; when it judges the plan done or parked, the slot is left empty. No clock switches things for you. Every turn's situation carries the plan, the ticket list, the ticket for this turn, and precedents of the same kind, and so does a turn handed off to another Bot or another session or woken by a check-back, so the original goal does not depend on whether that line is still in the transcript window. The first turn is marked in the situation; it is the only turn that can still align on the request before starting work.
_Avoid_: task table, plan DAG, state machine, owner, scheduler assignment, switching things by the clock, letting a Bot edit the plan itself, requiring you to set a goal before work can start, having the model summarize the goal for you (the plan is organized facts, not a transcript summary), rewriting the original request (the verbatim text is kept separately)

**Ticket**:
The smallest unit with a deliverable under a plan: number, title, description and Done when, status (To do / In progress / In review / Done / Parked), who is on it (filled in first from "Process" when the organizer opens the ticket, then updated from what is observed; it is a record, not an assignment), and artifacts. Both the organizer and you edit tickets. The organizer refers to existing tickets by id and writes only the fields that changed (leaving out the title, status, or who is on it means that field is unchanged); it opens new tickets as new-N; it cannot delete a ticket, only mark it Done or Parked. You change status on the flow board. The app itself also moves a ticket forward one step based on what it sees, without calling a model: when a turn filed under the ticket starts writing files or running commands, To do becomes In progress; when that turn hands over files, it becomes In review; if no one is on it, that Bot is recorded. It only moves forward, and it never marks anything Done or Parked on anyone's behalf. The organizer waits until the plan goes quiet before organizing, so this step keeps the flow board showing truthfully who is doing what even while several Bots work back to back. Each ticket has its own folder `NN-<title>/` under the plan folder; turns filed under the ticket work in it by default, and turns not filed under any ticket land in the plan folder. When a Bot is woken by a handoff, if the ticket handed over belongs to someone else while the Bot is on exactly one ticket in this plan that is not yet closed out, the turn lands on the Bot's own ticket instead of following the waking turn into someone else's ticket; if the handed-over ticket is its own, or no one is on it yet, the turn follows the handoff. Artifacts belong to tickets: a message carries a `ticket_id`, and the files it references are that ticket's artifacts; no files are moved. The ticket list sits beside the flow board, and clicking an entry lights up its cards.
_Avoid_: assigning work, claiming, deadline, priority ranking, subtask tree, letting a Bot create or close tickets, one ticket per sentence of a message, treating mirror files as the source of truth for tickets, the app marking something Done on someone's behalf, treating omitted fields as cleared

**Organizer**:
A short, tool-free call that organizes the plan and tickets on a session's behalf, running on the default model of the default endpoint. It runs at two points. First, after your message enters the session and before any turn opens, it judges whether the message continues the current plan (continue), moves on to a different thing (new), or returns to an earlier one (resume), updates the plan and tickets, and marks which ticket the message is about; once the message is stamped with a plan and ticket, every turn it opens (mentions, joining in after a judgement, forks) lands in the same place. Second, 30 seconds after all of the plan's live turns have ended and it has gone quiet, it organizes again: it files what those turns handed over under tickets and updates ticket status, who is on it, and Progress. It reads the current plan's fields and tickets (each ticket with the files that landed in its folder and have been referenced), what has happened since the last revision (who said what, what was handed over, the trace, and the commands those turns actually ran with their exit codes), the plans this session moved forward earlier, the existing Kind tags, and precedents of the same kind. A Bot saying "done" or "tests pass" does not count as evidence: marking a ticket In review requires files handed over by that ticket, and marking it Done also requires a record of a run. Done when states results you can check yourself; when the job is to build something usable, it must include "runs on this machine by following the start instructions and goes through the main flow"; when several parties each build a part that only works once combined, a separate "Integrate the parts and give the start instructions" ticket is opened. If the organizer judges the plan done while tickets are still To do or In progress, the plan does not count as done: its other changes this time are still accepted, and the plan stays in progress (marking it done yourself on the flow board is not subject to this limit). A failure changes nothing: if no default model is configured, the endpoint refuses, the answer is malformed, or the database rejects the change, the plan stays as it was and turns open as usual. No turn runs during the few seconds of organizing, but the Bots this message will wake (in a direct, that one Bot; in a group, those mentioned, or every present member if no one is mentioned) already show "Thinking" under it, and in the list and the header as well; once organizing finishes, each hands over to its own turn or judgement without a gap. Its spend is a separate category, "Organizer", under decision routing, and it belongs to no Bot.
_Avoid_: letting Bots do the organizing themselves, organizing on every step, blocking turns when organizing fails, organizing with the Bot's model, the organizer speaking or calling tools, the organizer deleting tickets, judging completion on a Bot's own claim, marking the plan done while tickets are not closed out

**Precedent**:
The Goal, Process, Rules, and outcome of the three most recent done plans of the same Kind, compressed into a few lines in the situation and looked up across the whole roster. When a Bot takes part in something, this tells it how the process for this kind of thing was settled before, what rules apply, and what counts as done, without you having to say it again; the organizer also uses it as a reference. The Kind is tagged by the organizer, which reuses an existing tag as-is when one matches.
_Avoid_: semantic search, similarity ranking, cross-machine precedent library, forcing a precedent on as a template

**Mirror files**:
`map.md` in the plan folder (the plan's fields plus a ticket index) and `ticket.md` in each ticket folder (that ticket's fields, with the plan's Done when and Rules attached), rewritten by the daemon after every organizing pass and after every edit you make to the plan. They are the app's own files: a Bot may read them with `read_file`, but may not edit them or hand them over, and they are not artifacts; the plan folder is created the first time the plan is written up. To change their content, edit the plan or the tickets on the flow board.
_Avoid_: editing mirror files by hand, treating a mirror file as a deliverable, having a Bot maintain them, using them as the single source of truth (the database is)

**Work dir**:
A plan's folder, under the workspace's `work/`, named after the first 12 code points of the Goal (or of the opening request) plus a short id, with no date (older dated folders are left as they are); under it, each ticket has its own `NN-<title>/`. A turn's work dir is the folder of the ticket it is filed under, or the plan folder if it is not filed under a ticket; the shell runs in it by default, while file tool paths stay relative to the workspace root. Who inherits it: handoffs, mentions, joining in after a judgement, Bot↔Bot directs, resuming an interrupted run, and check-backs all use the plan and ticket of the waking turn, so one piece of work stays in one place across Bots and sessions; your message is stamped with a plan and ticket by the organizer, and every turn it opens lands there. Folders are not switched by the clock: a session's current plan stays open until the organizer judges that the work has moved on to a different thing, returned to an earlier one, or is done or parked. A routine has its own standing plan and opens a new ticket each time it fires. The folder is created only when it is first actually used, so turns that only talk leave no empty folder behind. Deliverables are not forced into it: if you named a path, they are written there; if you did not, they land in this turn's ticket folder. Both levels have reserved subfolders: `tool-results/` holds large tool results saved by the daemon (cleared automatically once the plan has been closed long enough), and `scratch/` holds purely intermediate files; neither is ever attached as an artifact. `map.md` and `ticket.md` are the app's mirror files and likewise do not count as artifacts. Deleting a work dir is up to you; the app only clears `tool-results/`. In the messenger, you read the work's trace from top to bottom along who woke whom; each card shows which ticket it worked on, artifacts hang on the turn that handed them over, and clicking one opens it in the preview.
_Avoid_: one folder per Bot, artifact library, treating it as a sandbox, the app deleting the whole folder for you, the app moving files to archive them, switching folders by date or by idle time

**Approval**:
A dangerous action must be let through by you before it runs. Approval governs "the one step about to happen"; it cannot undo anything already done.
_Avoid_: ConsentGate, gate (an openbot term)

**Routine**:
Recurring work attached to one Bot and triggered by the calendar. v1 has routines only, no event triggers. Each routine has a standing plan (it does not take the session's current plan and does not go through the organizer); each time it comes due, a new ticket `NN-<date>` opens under that plan, and that turn works in the ticket's directory. When it comes due, the daemon inserts a system line under that Bot's name into your direct with the Bot, "Routine '<name>': <what to do>", to wake it; as with a check-back, no message is sent in your name. A check-back is not a routine; see "Check-back".
_Avoid_: cron job (in anything user-facing), skill-pack automation, sending the routine's content in your name

**Check-back**:
A one-time wake a Bot books for itself: how many minutes from now (one minute to seven days), what to check at that point, and what to do if nothing has happened. When it comes due, the daemon inserts a system line "Check-back: <note>" into the same session to wake the Bot. That line is the Bot's reminder to itself: only the turn it wakes can read it, and the flow board draws the Bot waking itself; the session does not show it, and other Bots, the organizer, search and unread never see it, just as a person would not read their own memo aloud to everyone. That turn keeps the plan and ticket of the turn that booked it, and its situation holds the job's plan, the ticket list, the files handed over so far and the trace. If the Bot already has a live turn there, the check-back is heard by that turn; in a direct with you, only by a turn on the same job, so two turns never do one job and write the same files at once. Otherwise a new turn starts, beside yours in a direct with you, as a second message of yours would. Use it after a handoff, or while waiting on a result outside the Bot's own control, so that someone comes back to check on handed-off work instead of relying on the other side to remember to mention the Bot again. A Bot has at most one pending check-back per session at a time, and booking another replaces it; the situation block marks the Bot's own pending check-back. It is voided if the turn that booked it is Stopped, if the session is cleared or deleted, or if the Bot is deleted; if the Bot has left the group or been archived, the check-back is only cleared when due and wakes no one. If the daemon slept through the due time or restarted, a check-back that came due without firing fires once to catch up. It does not appear on the routine calendar and is not an event trigger. The app also books one on the Bot's behalf: when a Bot↔Bot direct the Bot opened goes quiet (about 10 seconds after the last turn ends, with no live turn and no pending check-back inside), the app immediately wakes the Bot in the session that opened that direct. The check-back line says whom it talked with and who said what last (or, if the other Bot never replied, says so), so the Bot first reports the outcome there before moving on; this likewise replaces its existing pending check-back there. If nothing new has been said in the direct since the last call-back, it is not called again; for a direct opened from such a check-back, if the other Bot never replied, there is no call-back either, so two Bots do not spin back and forth over silence. When a turn in the direct is Stopped or interrupted by a restart, there is no call-back; that is for you to pick up. Plans work the same way: when a plan goes quiet (organized, no live turn, and no pending check-back inside) but still has tickets To do or In progress, the app books an immediate check-back for the Bot on the first ticket not yet closed out (or, if no one is on it, for the Bot that last spoke in this plan). The check-back lists the tickets not yet closed out and points out that Bot's own, and the turn runs in that ticket's directory. If no ticket has moved to In review or Done after the call-back, the app stops calling Bots and instead leaves a system line "This plan has stopped…" in the session and sends you a notification, so you decide whom to call; every further call-back needs a ticket to be closed out first, so there are never more call-backs than tickets. This happens only in sessions you are in. In a group, if the called-back Bot already has a live turn, the check-back is heard by that turn, just like a mention.
_Avoid_: polling, self-wake every few minutes, on the routine calendar, event trigger, central scheduler assigning work to Bots, stacking several check-backs in one session, calling the same Bot again and again after a plan has stopped

**Closing check**:
A check made before a turn hands its deliverables to you. When the message a Bot is about to send cites workspace files, or says it is still doing something unfinished ("working on it", "conclusion to follow"), and you are in the target session, and the job has a plan or an original request, the daemon makes one short tool-less call before sending (the default model of the default endpoint). It holds this turn's ticket, the plan's Done when and Rules (the original request, when no plan has been drawn up yet) against the files the job has handed over, who did what, whether this Bot has booked a check-back here, and the closing message, and lists every requirement that has been neither handed over nor accounted for in the closing. It also looks at the commands and tool calls actually run in this turn and in the job's earlier turns (with exit codes), and lists as well any claim in the closing or in this turn's handed-over files that something was run, tested, built, verified in the browser or measured to a number that does not match the record (no matching run, or that run failed). Anything that needs a browser, a real device or a person to verify, with no such call in the record, counts as a mismatch; a claim marked "not verified" with the reason does not. The turn ends as soon as the closing goes out, so "to follow" counts as accounted for only when a check-back has been booked or the work has been handed to someone by mention. If anything is listed, it goes back to the Bot once: through send_message, that call is not executed and its result is `closing_check` plus the list; for a direct reply, the list enters the loop as a one-line hint. Once the Bot fills the gaps, or says in the closing whom it hands them to and why it does not deliver them, and books a check-back first for anything it will only finish later, the next send goes through. Each turn is checked only once; the second send is not held back. It is a reminder with evidence, not a gate: with neither a plan nor an original request, with no default model configured, when the endpoint refuses, or when the answer is malformed, the message goes straight through. A send-back is not a tool error, and review does not count it as a failure; the call is charged to this turn's spend. Messages to a Bot↔Bot direct you are not in are not checked, nor are replies that cite no files and do not say work is still underway.
_Avoid_: checking every step, blocking the send, counting a send-back as a tool error, having the Bot's own model check itself, letting the model rewrite the closing, treating a self-written report as evidence of a run

**Skill**:
A named procedure attached to one Bot: a short description (when to use it) + a Markdown body (how to do it). It belongs to that Bot only; it is not shared across the roster, not a workspace file, and not MCP. Enabled skills enter the system prompt of every step of that Bot as a catalog; a body is read into the current turn's loop with a tool when needed. A skill is a procedure, MCP is a capability: the Bot looks at the skill catalog first, and on a match reads the body and follows it, calling any MCP tools the body names by name; only when no skill matches does it pick tools straight from the "MCP this turn" section. Skills add no tools and do not replace MCP. A skill can declare the names of the MCP servers its body depends on; any not connected this turn are marked in the catalog, and when the body cannot be followed, the Bot says so plainly or asks, rather than making do with other tools. When a body is read, any `mcp_` tool name written in it that is not among this turn's tools is flagged, and the Bot looks up the current name in the "MCP this turn" section and fixes the body. A Bot can add, delete and edit its own skills with tools, and you can edit them in the profile; edits insert no transcript entry. A skill cannot waive approval, cannot add tools, and cannot treat outside the workspace as inside it.
_Avoid_: skill pack, `/skill`, plugin, workflow, using the profile as a procedure, roster-wide shared skills, auto-injecting bodies by keyword

**Memory**:
A fact a Bot has noted down itself that still holds across sessions: a topic + a one-sentence conclusion. It belongs to that Bot only and other Bots cannot see it; deleting the Bot deletes it too, while archiving keeps it. The Bot writes it itself with a tool, and the learning step after a chain ends can also write one: when review blames the model, when the Bot hit tool errors but finished, or when the request was unclear and the user corrected it over more than one turn (in that case it records only the terms the user supplied — the form of the deliverable, the scope, who it is for, the defaults — and does not change skills). Without the call nothing is kept: it is not distilled for the Bot in the background, and the transcript is not summarized into the profile. All enabled memories enter the system prompt of every step of that Bot, with no retrieval and no relevance ranking, in the order they were last written, newest last. A memory is a past conclusion, not a source of truth: when it conflicts with this turn's transcript, the transcript wins, and one that no longer holds gets edited or deleted. Noting the same topic again overwrites it; no second entry sits beside it. When the Bot opens a new topic, it is shown its other memories from the same session in the last day, and deletes the old one if the new one revises it. The number of entries is capped, and when it is full the Bot must decide what to drop first; nothing is silently pushed out. You can view, edit, disable and delete memories, but you do not create them for the Bot; each one carries the message it was noted from, and you can jump back to it. The division of labor: the profile is who you are, a skill is how to do it, a memory is what you have learned.
_Avoid_: retrieval-based memory, vector store, feeding raw transcripts back in, background distiller, treating memory as a source of truth, memory shared across Bots, user-created memories, unlimited memory catalog

**Daemon**:
A resident TypeScript process on this Mac that runs the tool-call loop itself. Closing the window does not stop it; if the window crashes, turns keep going. On power it holds off idle sleep; closing the lid, Sleep from the menu bar, a drained battery or shutting down still puts it to sleep, and it picks up again on wake. A killed daemon is relaunched only while the window process is still alive (including when it is hidden in the tray); once the window is gone too, another crash stops it until you open the app again or next log in. Settings has an optional standalone runtime, **off by default**, which stays disabled in production until the sealed-native gate passes; while it is off, the window process remains the supervisor. The daemon also holds the terminal sessions you open, so their processes keep running after you close the window. When you quit or the daemon stops on its own, those processes stop with it, but where each terminal was open and what was on its screen are kept; on the next launch a new one opens in the same place, and the split layout reconnects to it. Only ending the terminal session forgets it.
_Avoid_: cloud computer, 24/7 server, treating the UI process as the runtime, keeps running with the lid closed, stops after one kill, standalone KeepAlive login item, closing the window kills terminals

**App window**:
The Tauri desktop window, which holds the Svelte messenger. Closing the window hides it to the tray rather than quitting; while hidden, it stays in the Dock. At login it goes only to the Dock and the tray, and the window does not pop up. Clicking the Dock icon, Cmd-Tab, Spotlight, left-clicking the tray, or opening the app again brings the window back. Only one window process runs at a time; a second launch just wakes the existing one and connects to the existing daemon. If the window crashes, it does not come back on its own. Before it connects to the daemon, Quit works, Stop does not, and the messenger shows "Can't reach the runtime". The width and height you dragged it to, and whether it was maximized, are the same when you reopen after quitting; the position is not remembered, so the window does not land off-screen after a display change. While you drag the border, the app does not ask whether the window is maximized: on macOS that query moves the window, so on release its position would differ from where you were dragging it.
_Avoid_: browser-only, no tray, hiding removes it from the Dock, window KeepAlive, grabbing the screen at login, multiple windows, treating a window crash as quitting

**Pane**:
One content area in the desktop window. A pane is a group of tabs; a tab can be a session (its artifact preview and flow board go with it; its own settings slide out from the right of the conversation in that tab, with an overlay that covers only this pane, and take no tab of their own), or a terminal (one shell session per tab), the routine calendar, the workspace, or spend. The window can be split horizontally and vertically into any number of panes, and both the dividers and the points where they meet can be dragged; tabs can be dragged to reorder within their own tab bar, dragged between panes, dropped on an edge to split in place, or dragged out while holding ⌥ to become a pane floating on top. Right-clicking anywhere in a pane splits off an empty pane in place, up, down, left or right; things that already have their own context menu (messages, the code editor) and input boxes keep theirs, and ⌥-right-click gives the web view's native menu; a floating pane does not split in place, and its right-click menu offers docking it back into the layout and closing the pane. An empty pane can be closed directly from its top-right corner; each pane's context menu can also close the whole pane and its tabs, asking first when the workspace or an artifact preview has unsaved edits. Closing the last tiled pane leaves one empty pane. **A window split into several panes is still the same window process**, and a floating pane is not a second system window either. Only one pane is the current pane at a time — whichever has the keyboard, and clicking or scrolling in a pane also makes it current: Stop hits that pane's turn, and clicking a notification first looks for a pane that already has that session open. When more than one pane is showing, the current one is outlined in the accent color so you can tell at a glance which it is; with only one pane there is no outline. Clicking a session in the sidebar: with only one pane, it replaces the session that pane is showing (a terminal, the workspace and the like are not pushed out; the new session opens in a tab beside them); with more than one pane, the pane that already has it open comes to the front, and if none does, a new tab opens in the current pane, replacing nothing any pane is showing. Session settings are open on only one session at a time, and opening them elsewhere closes them where they were; there is only one routine calendar at a time. Each session has only one artifact preview and one flow board: opening another file or another job from this session, from its preview's file tree or from its flow board turns that one over to it rather than opening another. The names of these two tabs are fixed and follow the session title, "<name> flow" and "<name>'s artifacts"; they do not change with the open file or the job. Switch away from a flow board tab and back, and it stays where you left it: where you dragged it, the zoom, which turns are folded or unfolded, the filters and the highlighted tickets all stay as they were; the same holds when you switch to another job in its switcher and back; it moves only when a message newly asks it to go to a card. A session pane no longer draws its own top bar: the avatar (with its status dot) and the name are always on the tab, and the top bar's second line has become the tab's tooltip; ⋯ appears only when the mouse is over the tab and holds pin, trace and settings, and right-clicking a session tab also offers these items ahead of the split options. Right-clicking any tab (also found in a session tab's ⋯) lets you close that tab, the other tabs in the same pane, the tabs to its right, or all tabs; closing all is the same as closing the last tab: the pane closes with it, asking first when the workspace or an artifact preview has unsaved edits. Other tabs (terminal, workspace, routines, spend, flow, artifacts) also always carry their own icon before the name. On narrow screens (≤680px) and phones there are no panes; it is still one screen at a time, stacked layer on layer.
_Avoid_: multiple windows, second window process, treating a floating pane as a system window, split screen on phones, visible means read, notifications rearranging the layout on their own, leaving empty panes around, settings in their own tab, top bar and tab both announcing the name in a narrow pane

**Layout**:
How the panes are divided: the horizontal and vertical splits, each pane's width and height, which ones float, which one is current, and which session each terminal pane holds. It is kept only in this Mac's localStorage, not in the daemon and not in the URL — the URL says only which session the current pane is showing. After you quit and reopen, it is as it was before; if a session or terminal it refers to is gone, it cleans that up on its own; before resetting to the default single pane, it asks about unsaved changes.
_Avoid_: layout in the database, layout in the URL, syncing layout across devices, layout that follows you to another machine, reset discarding unsaved changes outright

**Quit**:
Ends this run of the app. Under window supervision (the default), both the window process and the daemon stop, and the tray and Dock icons both disappear. If the standalone runtime is on, quitting closes only the UI and jobs keep going; stopping them takes an explicit stop (written `runtime.stop`). Turns in progress are marked Interrupted, and the processes in the terminal sessions you opened stop with it; next time you open the app, each terminal that was still open reopens in its original place, and the split layout reconnects to it. It is not closing the window. Only ending the terminal session forgets it. It leaves the Launch at login preference alone. Shutting down and logging out are also treated as Quit for turns. The same rule applies in development mode. In production the standalone runtime is still gated, and the default is still window supervision.
_Avoid_: treating closing the window as quitting, closing only the window by default and leaving a headless daemon, treating Quit as turning off launch at login, Cmd+Q closing only the window in development mode, treating the gated standalone mode as enabled

**Launch at login**:
Optional, on by default. At login it starts only the window process, into the Dock and the tray, and the messenger window does not pop up; the window process then makes sure the daemon is running. Turning it off affects only the next login and does not kill the current run; at the next login neither the window nor the daemon comes up. Quitting does not clear this switch either. The daemon is not a login item of its own.
_Avoid_: window popping up at login, turning it off kills the current run immediately, daemon as its own login item, quitting clears launch at login, turning off launch at login but leaving jobs that start themselves

**Tray**:
The menu bar icon of the window process. Left-click brings the window back. Right-click: Show window, Stop (the most recently active turn when the window is not open), Quit. There is no Hide and no Pause daemon. If the window crashes, the tray is gone too.
_Avoid_: tray badge, a second messenger, the daemon running its own tray

**User**:
The one person running this Mac. There are no multiple users and no share links. You are in every group; you and any Bot in a group can bring others in and remove them. Removing a Bot does not delete it. You appear in sessions, transcripts and the present members, but not on the roster's row of letter tiles.
_Avoid_: member, tenant, organization, Bot-only group without you, you in the roster

**Model endpoint**:
An OpenAI-compatible HTTP interface (base URL + API key). The app does not ship with any model of its own. You can configure several endpoints; one of them is the default. A completion goes to the endpoint its model belongs to. You add endpoints in Settings, and Bots can add them with a tool too. Creating an endpoint or changing an existing one's URL is a dangerous action. The default endpoint's URL and key cannot be changed, and it cannot be deleted.
_Avoid_: provider catalog, Binder, late binding, per-Bot endpoints

**Model**:
A completion name that a given endpoint recognizes. Each endpoint has its own list and its own default, and a name on the list can carry a routing reference price, an optional billing price, the thinking levels it supports, and what it is good at. The routing reference price is a relative number the app uses when it picks a model. The billing price is in USD per million tokens: input and output are set together, cached input can be set separately, and when left blank it uses the input price. The billing price is used to estimate spend when no reported amount is available; probing the model list does not fill in prices automatically. When the user's message starts a turn, the app picks the model and thinking level only from the list of the endpoint the Bot is pinned to (the default endpoint if it has none pinned); adding another endpoint in Settings does not bring its models into other Bots' choices. If the Bot has pinned a name that is still on that list, the model name is held to it; a pinned name that exists only on another endpoint is used as pinned. A Bot can also pin a thinking level (the completion's `reasoning_effort`): the level names follow that model's list (commonly none / low / medium / high, plus xhigh, max and so on when the endpoint advertises them). When probing `/models`, if an object carries thinking levels they are written into that model's `thinking_levels` automatically, and you can still edit them by hand in Settings. The thinking level is pinned together with the model and never exists on its own: either neither is pinned and the app picks both the model and the level for each message, or a model is pinned and its level is set along with it. Pinning a model without a level falls back to that model's default level (the app's order of preference for ordinary messages); switching to a model that doesn't support the current level falls back to the new model's default level; clearing the model clears the level with it; giving a level without a pinned model is rejected. You can change these with one click in the Bot panel, and a Bot can change its own with a tool. An empty pin does not mean "always use the endpoint's default model"; it means the app may pick from that endpoint's list. To use another endpoint, you must pin the endpoint explicitly. Who picks: each time a turn starts, an agent first picks once. It looks at the message, this Bot's profile, the candidate list, this Bot's recent review conclusions (each with the message and category it came from, ignored when they don't match) and recent examples that finished cleanly, and answers with a model, a thinking level and a one-sentence reason. The agent itself always runs on the default endpoint's default model; if it can't answer, or answers with something that doesn't exist, the choice falls back to rules, so the user is never stuck on model routing. Everything the user says afterward is kept verbatim (not filtered by keyword) and attached to the quoted turn, to the latest turn of the Bot that was `@`-mentioned, or to the latest visible turn in the session. Consecutive turns about the same thing form one correction chain. When the chain ends (the topic changes or things go quiet for a while), it is reviewed once; a turn with no follow-up is also reviewed once if the endpoint refused it, its reply was incomplete, or it hit at least two tool errors. The review looks at the whole chain plus what the turn actually did: was it the model falling short, the task itself being hard, or the request being unclear? Only a verdict that the model fell short is kept as this Bot's experience, together with which way to adjust: stronger / lighter / faster / cheaper. What is kept is a conclusion, not a score: there are no weights, offsets or caps. A conclusion that has been followed twice and still hasn't led to a cleaner result drops out of model routing, though its record stays. The experience belongs to the Bot itself and is deleted along with the Bot. What each turn chose, how it ended, how much it did and what feedback it received are all recorded. The user does not pick for each turn. The judgement call and the turn's completions use the same resolved result.
_Avoid_: provider catalog, a different model name for judgement, picking per turn, thinking level only ever chosen by the app, pinning a thinking level without a model, pinning a model without setting its thinking level, roster-wide shared routing experience, recognizing model feedback by keyword, one remark pinning a model forever, a scoring formula for model choice

**Setup wizard**:
The empty state of Settings: it is complete once the workspace path, the endpoint URL and a saved key are all in place. It has no route of its own; it slides out over the sidebar only and does not take over the main transcript.
_Avoid_: /setup, full-screen onboarding, making Settings the main transcript

**MCP**:
Roster-level servers: stdio (command / args) or HTTP / Streamable HTTP (url + optional headers). Every Bot can call the configured tools. You add servers in Settings, and Bots can also add, edit and remove them with tools. Adding a server or changing its command·args / url / headers is a dangerous action. An HTTP server's Authorization is pasted on the approval card and goes into the Keychain, never into tool arguments. Deleting an MCP server is not a dangerous action. The app records the usage instructions a server ships with; you or a Bot can also write a usage note for each server (what it does, when to use it, when not to), which goes into every step's "MCP this turn" section ahead of the server's own instructions. Leave it blank when the server's instructions are enough. Editing the note is not a dangerous action, and changing the connection does not clear it. All tools of an enabled, successfully connected server stay available to every Bot, direct, group and routine; they are never filtered out by message keywords or language. After a server is added, changed or re-enabled, the current turn's next step and other Bots' later completions can use it; once it is disabled or deleted, it can no longer be called. To hand an image from the workspace to a parameter that only accepts an image URL or data URI, the Bot writes `workspace://<path relative to the workspace root>` in the argument, and the app replaces it with the image's data URI before sending (shrinking the image first if it is over half a megabyte); the transcript and the next step still show the short reference. A remote server can't read this Mac's disk, and the model can't copy out a whole image's base64.
_Avoid_: per-Bot MCP, Bot as a tool permission boundary, hiding configured capabilities by keyword, available only in the turn that installed it, stdio only, hand-editing a server's own instructions

**Participation**:
When a message from you or a Bot arrives in a group's main transcript, whoever is mentioned must join in. Only your plain messages (no `@` / `@everyone`) have each of the other present Bots make one judgement (join in or sit out). If you mentioned someone, or a Bot sent the message, those not mentioned do not judge. The app does not decide on anyone's behalf who speaks, and it does not cut off loops with step-count or member-count circuit breakers. Asking you something is an ask inside the turn after joining in, not a third outcome of judgement.
_Avoid_: central arbitration, Dispatcher (an openbot term), routing, anti-loop cap, asking for help during judgement, judging again on every Bot message in a group

**Judgement**:
A short call made to each group member who wasn't mentioned, only when you post a main-transcript message in a group without mentioning anyone. It has no tools and returns join in or sit out as structured output. A judgement is not a turn; sitting out leaves nothing in the main transcript; a failed call counts as sitting out. A mention (including one by a Bot) skips judgement and starts turns only for those mentioned. Judgement sees the work the group is doing: the plan's Goal, Done when and Rules, the ticket list and who is on each ticket, the ticket this message was filed under, the files handed in so far, and the trace. What it decides is whether anyone is doing the part of the work that falls within its own role, not just whether this one message sounds like its business.
_Avoid_: a turn for every bystander, asking during judgement, joining in by default on failure, judging again on Bot messages, looking at the one message and not the work behind it

**Mention**:
`@Bot` names a teammate who must join in (skipping judgement); `@everyone` makes every Bot in the current group except the author join in, and pulls in no one outside the group. Without a mention, each Bot judges for itself under Participation. When that Bot already has a turn in progress in the group: if another Bot mentions it, the message is heard by that turn. It goes into the turn's inbox and is read at the start of the next step, and the turn carries on without being interrupted; if the turn wraps up before reading it, a new turn starts from that message after the wrap-up, so nothing is lost. If you mention it, that is still a redirect (a group has no Stop; when you speak, you want it to turn around right away), but the redirect hands it the files the old turn wrote, its last few steps and any messages not yet read as the first line of the new turn. It no longer spawns a second copy of itself. A name written as an abbreviation that uniquely identifies a present member (such as "Storyboard" for "Storyboard Artist") is treated as that member. A name that matches no one wakes no one: `send_message` first rejects it once so the Bot can correct it, and the group is finally left with a system notice.
_Avoid_: assign, dispatch work, cloning itself when mentioned in a group, a teammate's @ interrupting work in progress

**Thread**:
A quoted reply to one message in the main transcript: `parent_id` points to the quoted message, and the reply stays in the main transcript. Clicking Reply automatically `@`-mentions the original sender (when the sender is a Bot); if the message already has a mention or `@everyone`, it isn't added again. Threads are one level deep: you can't quote a reply. Bots use the same mechanism through `send_message`'s `parent_id`.
_Avoid_: thread as a group (a group is a separate session), quoted replies tucked into a sidebar, auto-@user when quoting the user

**Reaction**:
A lightweight acknowledgment of a message, picked from a fixed set of emoji; custom ones aren't allowed. It never carries changed instructions or security decisions; those require a written reply or an approval. In v1 only you add reactions; Bots don't react.
_Avoid_: emoji as approval, custom emoji, ✅/❌ as allow or deny

**Always allow**:
A saved roster-level rule (kind key + scope): from then on, dangerous actions of the same kind go through without asking. It exists alongside "Allow once". Some kinds always require approval and can't be made Always allow.
_Avoid_: allow everything, bypass, per-Bot rule

**Search**:
Lookup across Bots, groups, files and routines that jumps back to the spot in the original session. In v1 it is a local search on this Mac, not another Bot.
_Avoid_: semantic memory layer

**Stop**:
An immediate stop that you issue. It applies only to turns in progress in directs; actions already done are not rolled back. With the UI open, it hits the turn in the **current pane** (which must be a direct). When several sessions are laid out at once, the current pane is the one that has the keyboard, or the one you last clicked or scrolled in. From the menu bar with no UI open, it hits the turn in the most recently active direct. Groups have no Stop: group work already sent out can't be interrupted with a button; to stop it, send a message telling the Bots to stop. Clearing history, archiving, or deleting a group still ends that session's live turns. There is no step-count, roster or group-size circuit breaker.
_Avoid_: stopping the turns in every pane at once, deciding by the topmost floating pane

**Turn**:
A Bot, woken by a message, a mention, a handoff or a routine, working until it produces a reply, an ask or an approval card. A failed completion also ends the turn, and its final state is still completed, not interrupted. In a group, the same Bot has at most one turn in progress at a time; when another Bot mentions it or a check-back it scheduled comes due, that is heard by the current turn, and when you mention it or it judges to join in, the turn is redirected (see "Mention" and "Redirect"). Directs, routines and your explicit "Fork a turn" can still run several turns at once. Transcripts interleave by time. Spend is recorded per call; the messenger has a separate spend view, sessions show no numbers, and nothing is stopped because of spend. When a turn keeps calling tools without delivering a result, every 40 steps the loop asks it whether it is stuck (if it is stuck, it calls no tools and replies directly with where it is stuck and what it needs; if it is making progress, it carries on). At 160 steps its tools are put away, and its next reply is the end of the turn.
_Avoid_: workflow step, Planner step, the same Bot running several turns in a group, a failed completion as a fifth final state, letting a turn call tools forever

**Archive**:
Removes a Bot from the roster's main list; its sessions, profile and routines remain, and it can be restored. Only deleting removes the Bot from the roster (files in the shared workspace are left untouched).
_Avoid_: hide as pause (archiving is not Stop)

**Dangerous action**:
Needs approval before it runs: reading or changing anything outside the workspace, outbound network access (except model calls), adding or changing MCP servers (including command·args / HTTP url·headers), creating an endpoint or changing an existing endpoint's URL, and an unconstrained shell. Reading / writing / deleting inside the workspace, calls to configured MCP servers, the workspace shell, and adding or changing model names on an existing endpoint's list simply go ahead. Deleting an MCP server is not a dangerous action. The default endpoint's URL and key cannot be changed, and it cannot be deleted.
_Avoid_: gate, ConsentGate

**Outside the workspace**:
A path that, after `realpath`, does not fall under the workspace root prefix. A symlink inside the workspace follows its target: if the target is outside the workspace, so is the symlink.
_Avoid_: string prefix only, judging by inode / hard link

**Workspace shell**:
A `shell` run that passes the pre-launch path check: its cwd is inside the workspace, and no path visible in the command leaves the workspace. It makes no difference what characters a path name is written in; URLs (except `file://`) and devices such as `/dev/null` and the standard streams don't count as paths. It just runs. It is not a kernel jail.
_Avoid_: whole-machine shell, sandbox, seatbelt, App Sandbox container as the workspace root

**Unconstrained shell**:
A `shell` spawn judged to go out of bounds. That process and its descendants skip the workspace path check; the next `shell` is judged afresh.
_Avoid_: permanent lift, kernel jail release

**Terminal**:
A shell session you open yourself on this Mac, held by the daemon. It has the same rights as Terminal.app: its cwd starts in the workspace by default, but it is not confined to the workspace and needs no approval. Approval governs Bots' dangerous actions, and you don't need to ask yourself for permission. It is for running your own work, including processes that stay up, such as starting a project. Closing the window doesn't stop it. Which directory it is in is whatever the shell itself reports (zsh does this out of the box, once before each prompt): after a `cd` the tab name follows; if it has never reported, it is the directory it was opened in. When you quit or the daemon itself stops, the processes inside stop with it, but its directory and what was on screen are kept, and the next launch opens a new one in that directory. Only "End session" forgets it. The screen lives in the daemon too: when you reattach, you get it as it is now, full-screen programs included. Questions a program asks the terminal are answered only by the daemon, never by panes, so even when several panes watch one session, each question is answered once. The shell's environment is set up the way Terminal.app sets it up, but only an allowlist gets through; the daemon's other environment variables (including keys) are not passed in. When the desktop and a phone watch one session at the same time, its rows and columns follow whichever end you most recently looked at or typed in. Paired devices have the same rights: you can see it and type into it on your phone. Bots can't see it, can't use it, and don't know it exists. On the desktop, one terminal tab is one session: opening a new terminal tab starts a new shell, and a tab no longer holds a row of sessions to switch between. Closing a tab only removes it from the window; the processes keep running. Sessions not shown in any tab can be brought back with "Reattach" from "+" or from an empty pane. Phones and narrow screens have no panes; all sessions are gathered on the Terminal page as its tabs. To stop one, you must explicitly choose "End session" and confirm. The daemon's session list is the real one; sessions opened in the same folder are numbered in the order they were opened, and they carry the same names in desktop tabs and on the phone.
_Avoid_: treating it as the workspace shell, a terminal for Bots, approval cards for terminal commands, killed when the window closes, closing a tab kills the process, pane tabs as the session list, a row of sessions inside one terminal tab, two tabs pointing at the same shell, surviving a daemon restart, cloud computer

**Command stream**:
The live push of stdout / stderr while a Bot runs a `shell`, so the call can be seen while it runs. It is visibility only and doesn't change what the call is: stdin is still closed, the timeout is still ten minutes, and paths are still judged per call. It is not a terminal, has no input, and stays out of the main transcript: while running it hangs under that message bubble, when done it folds into one line, and to look back at it you use the turn view in the work dir.
_Avoid_: input for the command stream, treating it as a terminal session, letting it change approval granularity, putting it in the main transcript, a new message kind

**Ask**:
A Bot asks you about something that needs your judgment (not a tool approval). The question appears in the transcript, and the turn continues once you answer. When the possible answers can be listed, the Bot offers options: single choice when only one can hold, multiple choice when several can hold at once, with the recommended one first; you can always skip the options and write your own answer, or pick one and add a sentence. Your answer is recorded on the ask itself, not sent as a separate message from you: the card keeps what you picked and what you wrote, and later turns, the organizer and search all read it from there. Each ask is answered only once.
_Avoid_: making the ask an approval card, sending the answer as a separate message from you, adding an "Other" option, changing the answer after answering

**Interrupted**:
When the daemon dies, is killed and relaunched, or when you quit, shut down or log out, the turns in progress are marked interrupted. In the transcript that line carries an avatar and name like any other Bot message, and "Continue" sits right after the "Interrupted" bubble: it opens a new turn whose trigger is that interrupted line, and does not retry the call that was cut off; that Bot's next turn (in any session) sees "the last turn was cut off", once only. Closing the lid or system sleep is not an interruption: the turn freezes and carries on after wake. Time asleep does not count as being stuck, nor toward a command timeout; a request cut off by sleep waits after wake for the network to come back (about a minute), then is resent in full. An app window crash is not an interruption: the daemon keeps going. Completion timeouts, stalled streams and endpoint 4xx/5xx errors are not interruptions. A health check that fails temporarily while the daemon process is still running is not an interruption either: the window does not launch a second copy, and a second copy that cannot get the port does not touch the database.
_Avoid_: resuming tool calls from the break point, treating sleep as an interruption, treating shutdown as sleep, treating a window crash as an interruption, keeping "the last turn was cut off" on the profile forever, treating a completion timeout as an interruption, treating an endpoint error as an interruption, treating a health-check timeout as an interruption

**Completion**:
One streaming HTTP Chat Completions request to the endpoint within a turn. A turn's tool loop can make several completions. A failed completion is not an interruption, and it does not replay earlier tool calls.
_Avoid_: treating one completion as a turn, treating a completion timeout as an interruption

**Redirect**:
On a turn already in progress, abandon its unfinished remaining actions (its status becomes redirected) and open a new turn on the new message. In a group, when the Bot already has a live turn, your mention and a judgement to join in both go through a redirect, like a person turning to hear what you just said; the new turn's first line states the files the old turn wrote, its last few steps and the messages it had not yet read, so it does not start from zero. Mentions from other Bots and check-backs do not redirect; they are heard by that turn (see "Mention"). In a direct, use Stop when you need to halt a turn in progress right away; groups have no Stop, so to stop one you send a message.
_Avoid_: forcing the user to choose redirect or fork by hand on every turn, overwriting the trigger on the same row and carrying on, one user message clearing every live turn in the group

**Fork**:
Open another turn alongside one already in progress; the old turn continues. In a direct, a new user message forks by default (it redirects only when you ask for that explicitly); a routine forks in the direct between you and that Bot. In a group, when the Bot already has a live turn, a mention or a judgement to join in does not spin up another copy of it; it forks only when you explicitly choose "Fork a turn" in the group. A Bot↔Bot direct has no user, so the other Bot's second message is heard by this turn rather than forking, the same as how Bots are handled in a group.
_Avoid_: a manual-intervention scheduling switch, a routine redirecting a turn in a group, a group mention cloning another copy of the Bot

**Pull-in**:
@-mentioning, in a group, a Bot that is not in the group but is on the roster and not deleted: it is added to the group first, then joins in. A name that is not on the roster does not create a new Bot; the message is still sent.
_Avoid_: @-mentioning without joining the group, implicitly creating a Bot for an unknown name

**Artifact**:
A workspace-relative path, or an `http`/`https` link, referenced in a message. The file itself lives in the workspace (or at the remote URL). Files inside the workspace written during a turn appear in its final message automatically. Opening one shows it in the preview panel to the right of the chat (image / audio and video / PDF / text / single-file HTML / Word / Excel / PowerPoint); other kinds (subtitles, archives…) state that preview is not supported: the app window on this machine offers "Open with default app", and phones and browsers offer a download button. Every file opened remotely can be downloaded: on a phone from the right end of the preview's top bar, on wide screens from the row of buttons above the file, and on the flow board's file cards from the card header. Opening remotely, downloading and sending attachments have no file size limit; on desktop this preview can also be dragged out into a pane of its own. The tree on the left of the panel lists every path **this job** has referenced — not only this message's, and not every file in the work dir; "associated" means it has been referenced. The tree is rooted at the work dir, paths this job referenced outside that directory sit flat beside it, and the ones this message itself references are marked; the panel shares one column with the chat, with a drag bar between them to change the width; when one message has several paths, or when you open the workspace, the left side is a file tree, and the split between tree and content can be dragged. Preview column and file tree widths you have dragged are still there after you quit and reopen. Text is edited with Monaco + Shiki (line numbers, find / replace via ⌘F, bracket and tag matching, heading folding, line wrap); the preview itself no longer has find, wrap, copy, save or close buttons. Markdown and single-file HTML show the rendered result by default; a floating button at the top center of the content, which does not scroll with the body, switches between preview and source. PDFs are rendered with the built-in pdf.js (paging, zoom, fit width / whole page, in-page find), not the system PDF viewer. UTF-8 text inside the workspace can be written back to the same path with Cmd+S / save; switching files or closing the panel with unsaved changes asks for confirmation first. On desktop the preview has no title bar of its own: the file name and close are on the workbench tab; narrow screens and phones keep a strip with back and the file name. Right-clicking any item in the file tree offers "Show in Finder" and "Open with default app", which take effect only in the app window on this machine. In a handoff, the path goes into the message to the other party; there is no separate kind. The kind is inferred from the extension at preview time. Artifacts inside the workspace can be annotated (see "Annotation").
_Avoid_: asset library, Artifact table, snapshot copy, per-Bot artifact folder, `@file`

**Annotation**:
A remark you write about one spot in an artifact. It is attached to a workspace-relative path, an anchor, and the message that delivered the artifact. It starts as a draft the Bot cannot see; drafts collect into a batch that is sent all at once, combined into one reply that quotes the delivering message and @-mentions the Bot that delivered it. Once sent it is "Pending", and a Bot or you mark it "Resolved"; a resolved one can be reopened. As soon as it is marked resolved it comes off the file — the box on an image, the dot in the code margin, the mark in Markdown, the box on a PDF page, the number on HTML, the marker on a timeline — so what stays on the file is what is still unresolved; the list keeps listing them all. They are drawn back only when "Show resolved" is checked in the preview column, and only for that preview; clicking a resolved one in the list to locate it draws that one while it is located, and clicking it again to deselect takes it down; clicking its card in the conversation only opens the list at that item and does not draw it back on the file. When the file has changed and the anchor no longer matches, it is marked "Text changed" and its status stays the same; when the file is gone, it is marked "File gone". An annotation is not a snapshot of the artifact: it records only the quote, position and file hash at the time and does not keep the old file (when the selection is longer than the quote limit, it also records the whole span's length and fingerprint, used to tell whether that span is still there and whether it has changed). What it attaches to: a preview opened from a message attaches to that message and the Bot that delivered it; when the delivering message is in a Bot↔Bot direct you are not in, the batch goes to your direct with the delivering Bot, and the message records the origin. Only files inside the workspace can be annotated; link artifacts cannot. Each Bot that an annotation message wakes keeps the work dir of the turn in which it delivered the artifact (its most recent delivery in this batch), even if the session has been quiet long enough for that job to have closed — it is changing the same deliverable; when that job belongs to another session (it was delivered in a Bot↔Bot direct), this turn only works in that directory and does not reopen that job, and what each of the two sessions is carrying on with is unaffected. It is an ordinary follow-up message: it lands on the delivering turn and joins the correction chain, with no extra weight. A batch holds at most 50 annotations, and each body at most 2000 characters. In a group, one batch can go to several Bots at once: in the context, every annotation states which Bot it is for (the Bot that delivered that artifact, or "a deleted Bot" if it has been deleted), and `list_annotations` includes this too; each Bot handles only the ones for itself and leaves the ones for other Bots to those Bots, though it may mention them; ones for a deleted Bot have no one to take them, so the Bots this batch woke handle them. What a Bot can do: work through the ones for itself one by one; mark the ones it changed as resolved with `resolve_annotation`, with one sentence on how it changed them (any Bot can mark one — a Bot is not a permission boundary — and who marked it is recorded); check what is still unresolved with `list_annotations` (paths resolve the same way as in `read_file`, and a path outside the workspace is an error right away); and it gets a reminder when `read_file` reads a file that still has pending annotations. What a Bot cannot do: reopen, delete or create annotations. Clearing history or deleting a session deletes the annotations attached to those messages along with them; deleting a file does not delete its annotations. Anchor kinds: text / code line range, a selection in rendered Markdown, a box drawn on an image, a region on a PDF page, an HTML element, an audio / video time point.
_Avoid_: comment (kept for a possible multi-person future), review, a new message kind, annotations storing old versions, waking once per annotation, a Bot annotating for you

**Attachment**:
A file **you** drop into the chat, copied into the workspace's `inbox/`, with a link to that copy kept on the message. A remote connection also has a session just for sending files: files sent there also go into `inbox/`; you can send text there too, and the text stays only in that session; that session has no Bot and wakes no one. A file sent in an ordinary session still wakes that session. When a Bot attaches a file already in the workspace as an artifact, it uses the same attachment rows, but nothing is copied and nothing goes into `inbox/`. The workspace is the computer; attachments are not a second file system. Raster images that enter a turn's window are sent to the model as pixels, but a turn carries at most 20 images and 20 MB: they are taken from newest to oldest starting at the trigger message, and older images that do not fit keep only their path; a large image is first scaled down to 1568 on its long edge, and an opaque one is converted to JPEG before it is sent. When a Bot itself reads a PNG / JPEG / GIF / WebP in the workspace with `read_file`, the image is scaled the same way and attached as an image after that step's tool result: at most 12 images and 8 MB per step; these images take their share of the turn's 20 images and 20 MB first, and the transcript window gets what remains; when later-read images do not fit, earlier-read ones are moved out in the order they were read, keeping only their path, and to see one again the Bot reads it again. Other files are given only as paths; reading them goes through `read_file`.
_Avoid_: a ghost file that exists only on the message

**Profile**:
A Bot's name, role description, boundaries and avatar. A Bot can change its own name, role, boundaries and avatar, and no profile-change line is inserted into the transcript when it does; you can change them again at any time. Names of Bots that are not deleted must be unique. The avatar is a generated image or a raster image, not memory. Changes in the Bot panel save automatically (they are written once you pause for a moment, and anything unsaved is sent before you switch or close the panel); there are no save or close buttons, and the panel has only a single ✕ in the top-right corner. In settings, the workspace, endpoints, and MCP names / notes are likewise written as soon as you change them; adding an MCP server or changing its command / args / URL / headers still needs confirmation, and there is no Always allow.
_Avoid_: writing memory into the profile, a save button on the profile panel, a save button in settings

**Catch-up**:
After the daemon comes back (on wake, relaunch after a crash, reopening after quitting, or startup), each missed routine runs only its most recent due run once, without running every missed cycle back to back. After waking from sleep it waits a minute before catching up: with the lid closed the system wakes itself for a few seconds, and the network is often not back yet at that point.
_Avoid_: skipping whatever was missed, running once for every missed run, catching up after sleep but not after quitting

**Context window**:
What the model actually sees in a turn: the profile, the catalog of enabled skills, the system instructions, the "MCP this turn" section, this Bot's memory, the situation block (in a group it has the present members, live turns, who woke the Bot and the user's latest message; every turn has this job's plan (Goal, Done when, Rules, Process, Progress), the ticket list, this turn's ticket, precedents of the same kind, the files already handed over, the trace, and the Bot's own pending check-back; when no plan has been organized yet it falls back to the original request, and the first turn is marked "This is the first turn of this job"; all of it is read from rows already in the database, and the turn itself does not ask the model for a summary), the most recent stretch of the transcript (including the pixels of raster attachments, only the newest ones within a single budget; a user message with annotations expands, after its body, each annotation's id, which Bot it is for, path, position, quote or cropped image, and remark (page text and text you wrote is folded onto one line or indented line by line, so it cannot pose as the next item); cropped images and raster attachments spend the same budget and are sent to the model as pixels, and once the budget is used up, a cropped image leaves only the annotation's text), and this turn's tool loop. The full history exists only in the database, for you to browse and for search; it is not stuffed into the model wholesale. Judgement calls use a separate, shorter window without images. For an oversized tool result, the full JSON is first saved in the workspace, and the window holds only a bounded preview and full_result_path; the Bot can go on to extract the fields it needs or decode the file with the shell, and a truncated preview is not treated as the original result being lost.
_Avoid_: automatic summaries into the profile, a semantic-retrieval memory layer, a background distiller, estimating by token count, feeding earlier turns' tool results back in

**Spend**:
An append-only ledger of calls on this machine. Seven kinds of endpoint call each record one row per call: turn completion, judgement, model routing before a turn opens, correction-chain review, each learning step after a review, input suggestions, and organizing. Model routing and organizing belong to decision routing; review and learning steps together make up feedback routing; judgement is listed on its own, and input suggestions fall under "Other"; neither input suggestions nor organizing belong to any Bot. Each row stores the actual model, endpoint and thinking level, plus the session and Bot names at the time it was written; rows are kept when you delete a session, clear history or delete a Bot, deleted objects show their name snapshot marked "Deleted", and rows whose model could not be found during migration show "Unrecorded model". Tokens come only from the endpoint's `usage`; when missing, they show "—". When the provider returns `cost_in_usd_ticks`, the call is recorded as reported; with no reported cost, it is estimated when both input and output tokens are present and a billing price is configured. Estimates follow the currently configured prices: setting, changing or clearing a model's price recomputes all of its calls on that endpoint that have no reported cost, and a model removed from the list keeps its existing estimates. Cached input uses the cache price (left blank, it falls back to the input price; missing cached tokens count as 0); reasoning tokens are already included in output and are not added again. Reported and estimated amounts are totaled separately, and incomplete coverage is noted. The messenger has a separate spend view: a pane tab on desktop, an overlay on narrow screens and phones; you can filter it by time, model, session, Bot and call category, and see trends and per-call details; a detail row can jump back to its trigger message. The session top bar, list rows, settings and the model choice log show no spend figures. The time range and dimensions are saved only on this machine.
_Avoid_: budget circuit breaker, daily limit, automatic shutdown, treating estimates as reported or merging them into one amount, estimating missing tokens with a tokenizer, folding judgement into turns, MCP tools' own bills

**Local API**:
The HTTP + WebSocket interface the daemon serves on `127.0.0.1` for the app window, protected by the local token. Changes go over HTTP; the transcript stream goes over a receive-only WebSocket. Through it the window reads and writes the roster, sends messages and subscribes to the transcript stream.
_Avoid_: treating the UI process as the runtime, cloud API, two-way command channel, workspace files as HTTP resources, putting the local token in the URL

**Local token**:
A random secret the daemon mints fresh every time its process starts, used to authenticate requests to the Local API. HTTP sends it as `Authorization: Bearer`; the WebSocket sends it in the first message after connecting, never in the URL. A window crash does not change it; after the daemon exits or crashes, the next process mints a new one. It is not the endpoint API key, and it goes into neither SQLite nor the repository.
_Avoid_: API key, a long-lived key installed once, writing it into .env, putting it in the WebSocket query

**Judgement log**:
The record of join-in / sit-out decisions, visible in the current conversation's settings. It does not go into the main transcript.
_Avoid_: treating judgements as turns, flooding the main transcript

**Model choice log**:
The model and thinking level picked when a turn opens, which category the message counts as, how the turn ended (a failed completion carries its failure kind), how long it took and how many steps it made, plus the model feedback that later lands on that turn, the review of its correction chain, and the lessons recorded. It sits on that turn's card on the flow board and no longer has a separate entry point or page: a line at the bottom of the Bot card shows the model, thinking level and category, with a separate mark for feedback, for blame placed on the model, and for a failed completion; clicking that line expands everything below the card, and clicking a piece of feedback jumps back to the original words. The flow board toolbar can light up the cards that have feedback or whose review blamed the model and dim the rest, without changing the shape of the whole job. It is viewed by job, not by session: when a job spans several sessions, all of its choices are on the same board. It does not go into the main transcript and shows no tokens or spend; the Local API can still list it per session.
_Avoid_: routing log, a separate model choice log page, a log button on the session top bar, going into the main transcript, stuffing it into the current conversation settings, putting spend statistics here, treating criticism of the content as model feedback
