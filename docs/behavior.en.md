# Behavior

[简体中文](behavior.md)

This holds the behavior details that used to live in [`CONTEXT.md`](../CONTEXT.en.md)'s glossary entries; CONTEXT.md is the glossary, stating only what each term is and how it relates to the others, with nothing lost — the detail moved here. The sections below follow the order the terms appear in CONTEXT.md, one section per term.

<a id="plan"></a>
## Plan

The one thing currently being moved forward in a session, pieced together by the app itself; you do not have to define it first. The code keeps the `tasks` table and `task_id` (historical names; comments call it a plan). It is written up as **the plan**, with these fields: Kind (used to find precedents), Goal (what exactly is to be done now), Done when (how completion is judged), Rules (the standards, constraints, and improvement notes you have set; they come only from your own words), Process (the process and who does what), Progress (done / to do / stuck), and Status (in progress / done / parked); it also keeps the verbatim text of the request that opened it (the original request). The organizer updates the plan after each of your messages and after the plan goes quiet; every revision leaves a record (which message or turn caused it, or that you made it), and you can also edit it directly on the flow board. A session has only one current plan at a time: when the organizer judges that you have moved on to a different thing, it opens a new plan and parks the old one; when it judges that you have returned to an earlier thing, it picks that plan back up; when it judges the plan done or parked, the slot is left empty. No clock switches things for you. When you stop the work, the plan is parked, and it goes back to in progress only when you say to continue (or change it on the flow board). A line pushing for it to stop ("you haven't stopped", "it's still going") is never read as continue, and the filing after the plan goes quiet does not set it back to in progress, nor does a turn a check-back or annotations wake working in it: opening a turn never changes a plan's status. Every turn's situation carries the plan, the ticket list, the ticket for this turn, and precedents of the same kind, and so does a turn handed off to another Bot or another session or woken by a check-back, so the original goal does not depend on whether that line is still in the transcript window. The first turn is marked in the situation; it is the only turn that can still align on the request before starting work.

<a id="ticket"></a>
## Ticket

The smallest unit with a deliverable under a plan: number, title, description and Done when (what to hand over and how it is judged done; no progress notes and no don'ts a Bot set for itself), status (To do / In progress / In review / Done / Parked), who is on it (filled in first from "Process" when the organizer opens the ticket, then updated from what is observed; it is a record, not an assignment), and artifacts. Both the organizer and you edit tickets. The organizer refers to existing tickets by id and writes only the fields that changed (leaving out the title, status, or who is on it means that field is unchanged); it opens new tickets as new-N; it cannot delete a ticket, only mark it Done or Parked. You change status on the flow board. The app itself also moves a ticket forward one step based on what it sees, without calling a model: when a turn filed under the ticket starts writing files or running commands, To do becomes In progress; when that turn hands over files, it becomes In review; if no one is on it, that Bot is recorded. It only moves forward, and it never marks anything Done or Parked on anyone's behalf. The organizer waits until the plan goes quiet before organizing, so this step keeps the flow board showing truthfully who is doing what even while several Bots work back to back. Each ticket has its own folder `NN-<title>/` under the plan folder; turns filed under the ticket work in it by default, and turns not filed under any ticket land in the plan folder. When a Bot is woken by a handoff, if the ticket handed over belongs to someone else while the Bot is on exactly one ticket in this plan that is not yet closed out, the turn lands on the Bot's own ticket instead of following the waking turn into someone else's ticket; if the handed-over ticket is its own, or no one is on it yet, the turn follows the handoff. Artifacts belong to tickets: a message carries a `ticket_id`, and the files it references are that ticket's artifacts; no files are moved. The ticket list sits beside the flow board, and clicking an entry lights up its cards.

<a id="organizer"></a>
## Organizer

A short, tool-free call that organizes the plan and tickets on a session's behalf, running on the default model of the default endpoint. It runs at two points. First, after your message enters the session and before any turn opens, it judges whether the message continues the current plan (continue), moves on to a different thing (new), returns to an earlier one (resume), or is about a job the Bots here are pushing forward in another session (join: say you tell a Bot in your direct about the job it is doing in a group; a job opened elsewhere stays there, and this session's current plan is unchanged), updates the plan and tickets, and marks which ticket the message is about; once the message is stamped with a plan and ticket, every turn it opens (mentions, joining in after a judgement, forks) lands in the same place. Second, 30 seconds after all of the plan's live turns have ended and it has gone quiet, it organizes again (a turn you Stop does not lead to this: a Stop asks the work to stop, and the call-back after organizing would have it carry on; a Stop also cancels the organizing an earlier turn of the same plan had lined up but not started, and the plan's own wait before looking at it again, and an organizing already under way calls nobody back when it ends; other plans are not affected): it files what those turns handed over under tickets and updates ticket status, who is on it, and Progress. It reads the current plan's fields and tickets (each ticket with the files that landed in its folder and have been referenced), what has happened since the last revision (who said what, what was handed over, the trace, and the commands those turns actually ran with their exit codes), the plans this session moved forward earlier, the jobs the Bots here are pushing forward elsewhere (the whole plan, its tickets, where it was opened, who is working on it where, and the lines of this session filed under it earlier), the existing Kind tags, and precedents of the same kind. It also reads every line you said about the job: the earlier ones beyond what happened since the last revision, and your answers to questions (a repeated line counts once; when there are too many it keeps the first few and the latest, within a length cap), and which parts of the goal, Done when, rules and ticket descriptions you typed on the board yourself (these count as your words too, and cleanup leaves them alone). Every line is marked as said by you, by a Bot, or by the app, and an answer to a question counts as yours. Rules only come from your words: what you said, what you answered, what you typed on the board. What a Bot decides is not a rule, and goes one of three ways: a hold it put on itself (pausing, freezing, no retries, doing only part of it) goes under Process with who decided it, and what is held back because of it goes under Progress as stuck, with what would unblock it; something that waits on you (an authorization, a key, a go-ahead to spend) goes under Progress as stuck, with what you need to do; a working constraint (don't overwrite the original file, where the delivery goes) goes under Process. When something new you say overrides an existing rule, the old rule is rewritten or dropped rather than kept beside the new one. Once you say keep going or don't stop, a hold a Bot put on itself is lifted wherever it was written (Rules, Process, Progress, Done when, or a ticket's description) and what it held back moves back to to do; a hold that waits on you is lifted only once you give what it waits for, and a working constraint stays. Only on a line of yours, and only when it can see every line you said, does it move out old rules it finds no source for in your words, and widen a goal a Bot narrowed back to what you asked for. Under Progress, to do lists only what is not done yet; something handed over and only waiting for you to look at it does not count. Precedents are only for reference; their rules are not copied into this job. A ticket's description says what to hand over, not progress. When the plan goes quiet and you have said nothing since the last revision, organizing leaves the Goal, Done when, Rules and each existing ticket's description exactly as they were and does not park the plan (the app sends such changes back); it only records what was handed over, how far things got and who is on what. If the plan changes while that call is running (a line of yours was filed into it, or you edited it), nothing from that call is applied. A Bot saying "done" or "tests pass" does not count as evidence: marking a ticket In review requires files handed over by that ticket, and marking it Done also requires a record of a run. Done when states results you can check yourself; when the job is to build something usable, it must include "runs on this machine by following the start instructions and goes through the main flow"; when several parties each build a part that only works once combined, a separate "Integrate the parts and give the start instructions" ticket is opened. If the organizer judges the plan done while tickets are still To do or In progress, the plan does not count as done: its other changes this time are still accepted, and the plan stays in progress (marking it done yourself on the flow board is not subject to this limit). A failure changes nothing: if no default model is configured, the endpoint refuses, the answer is malformed, or the database rejects the change, the plan stays as it was and turns open as usual. An answer that returns to an earlier plan or joins a job elsewhere, when by the time it is read that plan is no longer one it could pick (say the turn on it elsewhere ended while the call was out), files nothing either, and the message stays as it was: the answer was written for that plan, so landing it on the current plan would write over the current plan's fields, and with no current plan it would open a copy nobody asked for. An answer that names this session's current plan is the exception: that is a continue in other words, and it lands as one. No turn runs during the few seconds of organizing, but the Bots this message will wake (in a direct, that one Bot; in a group, those mentioned, or every present member if no one is mentioned) already show "Thinking" under it, and in the list and the header as well; once organizing finishes, each hands over to its own turn or judgement without a gap. Its spend is a separate category, "Organizer", under decision routing, and it belongs to no Bot.

<a id="work-dir"></a>
## Work dir

A plan's folder, under the workspace's `work/`, named after the first 12 code points of the Goal (or of the opening request) plus a short id, with no date and no `@` (it becomes `-`, so citing a file inside does not read as a mention; older folders with a date or an `@` are left as they are); under it, each ticket has its own `NN-<title>/`, with any `@` in the title replaced the same way. A turn's work dir is the folder of the ticket it is filed under, or the plan folder if it is not filed under a ticket; the shell runs in it by default, while file tool paths stay relative to the workspace root. Who inherits it: handoffs, mentions, joining in after a judgement, Bot↔Bot directs, resuming an interrupted run, and check-backs all use the plan and ticket of the waking turn, so one piece of work stays in one place across Bots and sessions; your message is stamped with a plan and ticket by the organizer, and every turn it opens lands there. Folders are not switched by the clock: a session's current plan stays open until the organizer judges that the work has moved on to a different thing, returned to an earlier one, or is done or parked. A routine has its own standing plan and opens a new ticket each time it fires. The folder is created only when it is first actually used, so turns that only talk leave no empty folder behind. Deliverables are not forced into it: if you named a path, they are written there; if you did not, they land in this turn's ticket folder. Both levels have reserved subfolders: `tool-results/` holds large tool results saved by the daemon (cleared automatically once the plan has been closed long enough), and `scratch/` holds purely intermediate files; neither is ever attached as an artifact. `map.md` and `ticket.md` are the app's mirror files and likewise do not count as artifacts. Deleting a work dir is up to you; the app only clears `tool-results/`. In the app, you read the work's trace from top to bottom along who woke whom; each card shows which ticket it worked on, artifacts hang on the turn that handed them over, and clicking one opens it in the preview.

<a id="closing-check"></a>
## Closing check

A check made before a turn hands its deliverables to you. When it happens is unchanged: the message a Bot is about to send cites workspace files, or says it is still doing something unfinished ("working on it", "results to follow"), you are in the target session, and the turn belongs to a job. Since 2026-09-29 (ADR 0037) it makes no model call; it applies three fixed rules, and if any of them fails the Bot gets an app note back: one, the job has acceptance checks (ADR 0036) that are not passing — file checks are judged again on the spot, so a file fixed in this very turn is not bounced on an old result, and command checks use their latest run, skipping one this turn already ran successfully; at most three are listed, with the reminder to fix the deliverable rather than the check, or to say in the closing why it cannot be done now; this rule applies only to replies that deliver (cite files). Two, it says the rest comes later but has neither booked a check-back here nor handed the rest to someone by name — once the turn ends nobody picks it up, so finish now, book a check-back, or name who takes it. Three, it says something was run, tested or verified while this turn ran no command at all (unless it says it was not verified). Through send_message the call does not run and returns the note; a direct reply gets the note as a line in the loop. A turn is checked once and not stopped a second time; a send-back is not a tool error and the chain review does not count it as a failure; with no model call there is no spend row. A Bot↔Bot direct without you is not checked, nor a reply that cites no files and does not say it is still working. The earlier step that had the default model compare the delivery with the plan's spec line by line is gone: in the golden-path ablation switching it off cost no completion and saved about a quarter of the spend and time, and the machine-checkable part of the done-when now runs as acceptance checks.
<a id="acceptance-check"></a>
## Acceptance check

A plan's Done when is a list of results you could check yourself; acceptance checks hand the ones a machine can decide to the daemon, which runs them itself instead of trusting a Bot's claim or a model's reading of its closing. Four kinds: a file exists (and is not empty), a file contains some text (or, reversed, does not), a file matches a regex (or does not), or a command (an expected exit code, 0 by default, and optionally the expected output, compared without trailing blanks and trailing empty lines). File paths, and commands with no directory given, are relative to the workspace root, as the file tree shows it; paths outside the workspace and commands that reach outside cannot be saved, are judged again when they run, and are recorded as blocked and not run if they reach outside — the app never approves anything on your behalf. A command runs under `/bin/sh` in its own process group, killed whole when it ends or times out (120 seconds by default, 600 at most), with only the terminal's environment whitelist (without `SSH_AUTH_SOCK`, and nothing of the daemon's own). Each run records its outcome (passed, failed, blocked, error), a one-line detail in the app's language and the tail of its output; a check keeps its last 5 runs. When they run: when the plan goes quiet the stale ones run first (never run since defined, or the job has had turns since), and the ones the organizer just added run after it files; a check you create or change runs at once; Run checks on the flow board runs them all at any time. One run per plan at a time, one command check at a time on the whole Mac, at most 15 minutes of checks per quiet stretch. Who writes them: you add, edit and remove them on the flow board; editing one the organizer added makes it yours, and the organizer cannot touch it again; the organizer may add, change and remove its own in its answer (at most 3 new ones a time, 10 per plan), a command only if a turn of this job ran it successfully (exit code 0) in that directory or you wrote it yourself in a line filed under the job, and never one you removed; Bots have no tool to write checks and only see them in the situation block and in `map.md`. A check belongs to one line of the Done when, matched by its text: when you or the organizer reword that line the check follows it, and when the line goes, the check is listed under checks that match no line, still run and still counted. Where the results go: on the flow board each line carries its checks' results, which open to the detail, the last run and the output; the organizer sees every check's last result, cannot mark the plan done while one fails (or has not run since it was defined) and cannot mark its ticket done, and records blocked and errored ones under Progress · Blocked as no evidence either way; closing a plan by hand is not held back. When a plan goes quiet with tickets open or checks failing, the app calls a Bot back once, quoting up to 3 failing checks and the tail of their output and asking it to fix the deliverable, not the check; a further call-back needs progress first (a ticket handed over or closed, or a check that existed before the last call-back passing for the first time), otherwise it says once that the job stopped; between two of your lines there are no more call-backs than tickets plus checks. Every turn's situation block lists the job's checks and their results.

Seams (`continuity`) is the fifth kind, for work that several Bots make in parts and that only counts as one delivery once the parts come together: each Bot reviews its own part, and nobody sees the seams. The parts come, in order, from one of three places: a command that prints them one per line (the most precise); a glob (every match in natural order, C2 before C10; only when every match is a video and no command is given is it taken for a master that keeps being re-cut, and the newest one is used); or one file split up — Markdown and plain text at level-one and level-two headings, HTML at h1 and h2, a video at the cuts scene detection finds (it misses cuts between similar shots: 6 of 11 on a real episode). Each seam gets evidence from both sides: for video, the last frame of one shot and the first of the next; for images, the two images; put side by side in one picture under the plan folder's `checks/<check>/` (a reserved folder, never an artifact), which needs a model that reads images; for text, about 700 characters from the end of one part and the start of the next, which does not. Text also gets one whole-set pass: each part's heading, opening and the numbers-with-units and proper names in it, as one digest, to see whether the same thing is named and counted the same way in every part. The judge is the default model of the default endpoint, with the acceptance line, the plan's rules and one general list: agrees with the rules; follows on (a missing transition is named); the same thing stays the same (characters, products and proper names, terms, numbers and units, orientation and direction); the same style (for pictures, the look, rendering, palette and character design; for text, tone, format and numbering); repeats or gaps (not called when the evidence cannot show it). Nearly identical frames or images across a seam are good news: the seam is invisible. It answers in JSON only and is asked again once if the answer does not parse. It passes only when every seam and the whole set hold; otherwise the detail reads "K of N seams have problems: 02-market→03-channels: …" and the output lists every seam (with its image path when there is one), then the whole-set line. These calls are billed as their own spend kind, acceptance checks. Code does not use it: the seams between modules are checked by an integration or start-up command. The organizer may propose one too, but only on parts this job delivered or with a list command the job actually ran successfully.

<a id="pane"></a>
## Pane

One content area in the desktop window. A pane is a group of tabs; a tab can be a session (its artifact preview and flow board go with it; its own settings slide out from the right of the conversation in that tab, with an overlay that covers only this pane, and take no tab of their own), or a terminal (one shell session per tab), the routine calendar, the workspace, or spend. The window can be split horizontally and vertically into any number of panes, and both the dividers and the points where they meet can be dragged; tabs can be dragged to reorder within their own tab bar, dragged between panes, dropped on an edge to split in place, or dragged out while holding ⌥ to become a pane floating on top. Right-clicking anywhere in a pane splits off an empty pane in place, up, down, left or right; things that already have their own context menu (messages, the code editor) and input boxes keep theirs, and ⌥-right-click gives the web view's native menu; a floating pane does not split in place, and its right-click menu offers docking it back into the layout and closing the pane. When there are other panes, an empty pane can be closed directly from its top-right corner (not shown on the only tiled pane: closing it would just leave another empty one, and with nothing else on its tab strip the strip folds away); each pane's context menu can also close the whole pane and its tabs, asking first when the workspace or an artifact preview has unsaved edits. Closing the last tiled pane leaves one empty pane. **A window split into several panes is still the same window process**, and a floating pane is not a second system window either. Only one pane is the current pane at a time — whichever has the keyboard, and clicking or scrolling in a pane also makes it current: Stop hits that pane's turn, and clicking a notification first looks for a pane that already has that session open. When more than one pane is showing, the current one is outlined in the accent color so you can tell at a glance which it is; with only one pane there is no outline. Clicking a session in the sidebar: with only one pane, it replaces the session that pane is showing (a terminal, the workspace and the like are not pushed out; the new session opens in a tab beside them); with more than one pane, the pane that already has it open comes to the front, and if none does, a new tab opens in the current pane, replacing nothing any pane is showing. Session settings are open on only one session at a time, and opening them elsewhere closes them where they were; there is only one routine calendar at a time. Each session has only one artifact preview and one flow board: opening another file or another job from this session, from its preview's file tree or from its flow board turns that one over to it rather than opening another. The names of these two tabs are fixed and follow the session title, "<name> flow" and "<name>'s artifacts"; they do not change with the open file or the job. Switch away from a flow board tab and back, and it stays where you left it: where you dragged it, the zoom, which turns are folded or unfolded, the filters and the highlighted tickets all stay as they were; the same holds when you switch to another job in its switcher and back; it moves only when a message newly asks it to go to a card. A session pane no longer draws its own top bar: the avatar (with a status dot while a Bot is working, waiting on you or has failed, none when idle) and the name are always on the tab, and the top bar's second line has become the tab's tooltip; ⋯ appears only when the mouse is over the tab and holds pin, trace and settings, and right-clicking a session tab also offers these items ahead of the split options. Right-clicking any tab (also found in a session tab's ⋯) lets you close that tab, the other tabs in the same pane, the tabs to its right, or all tabs; closing all is the same as closing the last tab: the pane closes with it, asking first when the workspace or an artifact preview has unsaved edits. Other tabs (terminal, workspace, routines, spend, flow, artifacts) also always carry their own icon before the name. On narrow screens (≤680px) and phones there are no panes; it is still one screen at a time, stacked layer on layer.

<a id="model"></a>
## Model

A completion name that a given endpoint recognizes. Each endpoint has its own list and its own default, and a name on the list can carry a routing reference price, an optional billing price, the thinking levels it supports, and what it is good at. The routing reference price is a relative number the app uses when it picks a model. The billing price is in USD per million tokens: input and output are set together, cached input can be set separately, and when left blank it uses the input price. The billing price is used to estimate spend when no reported amount is available; probing the model list does not fill in prices automatically. When the user's message starts a turn, the app picks the model and thinking level only from the list of the endpoint the Bot is pinned to (the default endpoint if it has none pinned); adding another endpoint in Settings does not bring its models into other Bots' choices. If the Bot has pinned a name that is still on that list, the model name is held to it; a pinned name that exists only on another endpoint is used as pinned. A Bot can also pin a thinking level (the completion's `reasoning_effort`): the level names follow that model's list (commonly none / low / medium / high, plus xhigh, max and so on when the endpoint advertises them). When probing `/models`, if an object carries thinking levels they are written into that model's `thinking_levels` automatically, and you can still edit them by hand in Settings. The thinking level is pinned together with the model and never exists on its own: either neither is pinned and the app picks both the model and the level for each message, or a model is pinned and its level is set along with it. Pinning a model without a level falls back to that model's default level (the app's order of preference for ordinary messages); switching to a model that doesn't support the current level falls back to the new model's default level; clearing the model clears the level with it; giving a level without a pinned model is rejected. You can change these with one click in the Bot panel, and a Bot can change its own with a tool. An empty pin does not mean "always use the endpoint's default model"; it means the app may pick from that endpoint's list. To use another endpoint, you must pin the endpoint explicitly. Who picks: each time a turn starts, an agent first picks once. It looks at the message, this Bot's profile, the candidate list, this Bot's recent review conclusions (each with the message and category it came from, ignored when they don't match) and recent examples that finished cleanly, and answers with a model, a thinking level and a one-sentence reason. The agent itself always runs on the default endpoint's default model; if it can't answer, or answers with something that doesn't exist, the choice falls back to rules, so the user is never stuck on model routing. Everything the user says afterward is kept verbatim (not filtered by keyword) and attached to the quoted turn, to the latest turn of the Bot that was `@`-mentioned, or to the latest visible turn in the session. Consecutive turns about the same thing form one correction chain. When the chain ends (the topic changes or things go quiet for a while), it is reviewed once; a turn with no follow-up is also reviewed once if the endpoint refused it, its reply was incomplete, or it hit at least two tool errors. The review looks at the whole chain plus what the turn actually did: was it the model falling short, the task itself being hard, or the request being unclear? Only a verdict that the model fell short is kept as this Bot's experience, together with which way to adjust: stronger / lighter / faster / cheaper. What is kept is a conclusion, not a score: there are no weights, offsets or caps. A conclusion that has been followed twice and still hasn't led to a cleaner result drops out of model routing, though its record stays. The experience belongs to the Bot itself and is deleted along with the Bot. What each turn chose, how it ended, how much it did and what feedback it received are all recorded. The user does not pick for each turn. The judgement call and the turn's completions use the same resolved result.

<a id="hold"></a>
## Hold

A stop of yours, recorded as a row. **Scope**: everything; one Bot (following it into every session it is in); one session (and the plans that session is home to, even where the work goes on in a Bot↔Bot direct — work in that direct is still the group's job); one plan (tickets included); one ticket; one Bot's work in one plan; or one turn (covering the check-backs that turn booked). It may also carry more it covers, fixed when it was made — the directs holding the work that Bot handed on, say — which does not change afterwards. Only you lift it: with a line of yours, or a button; no other caller has a way to lift one, neither a Bot nor the organizer. The record is never deleted: clearing a chat or deleting a group only blanks the line it points at, and the hold itself stays. A plan a hold names (a hold on that plan, on one Bot's work in it or on one of its tickets, or with any of those among its targets, lifted or not) stays when the chat is cleared too, so no hold points at a job that is gone. Deleting a group takes its surviving plans (the ones a turn or a line in another session still belongs to) out of it, and with that out of reach of a hold on the group; so each one that hold keeps parked first gets a plan hold of its own (source `migration`), carrying how to put it back. So does one stopped the old way before the hold (parked in its status and its spec): lifting its hold puts it back in progress, as the boot import of such plans does. One already under a hold on the plan itself needs none.

**When it is made**: in the same write that records it, every running turn it covers ends as stopped; once the write is in, the turn's model call, its MCP calls (the server is told the call is cancelled) and its commands' process groups (asked to exit, killed 3 seconds later) are aborted. Where each had got to — the files it wrote, its last few calls — is recorded on the hold (`effect.stopped_turns`), with the other Bots' turns still working in the same plans that it does not cover (`working_beside`) and anything it covers still running afterwards (`still_running`, empty unless something went wrong). A stop you say or press also covers the work the covered Bot handed on and has not had back: a turn of another Bot opened by a line of a covered turn — or by a line of such a turn, up to three handoffs down — that is still running or still has a check-back to come. Each becomes a target on that one turn, which covers the turn, what it booked and whom its lines would wake, and not the other Bot's own work; nothing upstream is stopped. A read-only turn a hold let open is left to finish its answer. The work log gets a `control.hold` row.

**Plan status**: a hold on a plan or a session sets the in-progress plans it covers to parked, in the status and in the spec's status both — the flow board sends the spec's status back with every edit, and the organizer revises the spec too, so changing only one of them would get the plan set back to In progress. The plan stays the session's current plan: it is stopped, not pushed aside by another job. A plan already pushed out of the current slot by a newer one (parked in its status, In progress in its spec) has its spec set to parked as well, and lifting puts it back to being pushed aside — In progress in its spec, parked in its status — rather than In progress, so that a plan out of the slot is not called back to work. While the hold stands, the organizer or a resume asking for In progress leaves it parked and only notes that lifting the hold should bring it back; one pushed out of the current slot meanwhile by a plan opened or resumed there goes back to being pushed aside when the hold is lifted; a plan opened in that session is parked from the start; marking it Done still goes through. Setting the spec to parked and setting it back on the lift are each a version of the spec: a flow board still on the version before has its edit refused (`409 revision_conflict`) instead of sending back the status the hold just changed — undoing the stop, or stopping again after the lift. Neither version counts as yours or as organizing: the organizer still reads what was said before the stop, and the revision history marks both `cause: "hold"`. Lifting the hold puts it back as it was, and back into the session's current slot if that is free; if another hold on the plan or its session still has it, it stays parked, and that one keeps the note of how to put it back. A hold on a Bot, a ticket or a turn leaves plan status alone, and the plan's other Bots carry on; one on everything leaves it alone too (it would otherwise rewrite every plan there is), and a plan's `held_by` lists the holds over the plan as a whole (on the plan, on its session, on everything).

**The old way of setting status**: once the engine level has reached holds, setting a plan's status to parked (`PATCH /v1/tasks/:id/spec`, as older clients and the phone do) is a hold on that plan; setting it back to In progress, or marking it Done, lifts the holds on that plan. With a hold on its session or on everything still standing, setting it back to In progress leaves it parked (the session's) or as it was (everything's), and `held_by` says which. Whether an edit sets the status is judged against the spec's status, which is what the flow board shows and sends back: an edit of only the goal sends it back unchanged and neither stops nor resumes anything. A plan pushed aside reads parked in its status column and In progress in its spec, so judging by the column would take such an edit for a resume. Below that level, parked is only the status.

**Check-backs**: a pending check-back a hold covers is set aside, and marked voided at the same time so that an older build that knows nothing of holds never fires it; one booked while the hold stands is set aside too. Once lifted, with no other hold over it, it is pending again, and one whose time has already passed fires once shortly after. If, while it is set aside, the session is cleared or deleted, the Bot is deleted, or — before holds are on — the turn that booked it is Stopped, it is voided for good and lifting does not bring it back; if the Bot books another in the same session, the new one is the one that counts, and the old one does not come back.

**Wakes and tools**: nothing a hold covers is woken. Your line (it opens only a read-only turn, below), another Bot's line (naming it, or any line in a Bot↔Bot direct), a check-back of its coming due, the report-back when a Bot↔Bot direct it opened goes quiet, a quiet plan's call-back, a routine coming due, Continue on an interrupted turn: none opens a turn, and a running turn a hold covers hears no new line either: one about work beside the hold opens a turn of its own next to it, without cutting the held one off, and one of yours in another conversation that is filed under the job does not reach it. A held Bot's own line wakes nobody, and a Bot↔Bot direct whose other side is held calls nobody back when it goes quiet; nothing is kept for later, since that side's next turn in the direct after the lift makes it go quiet again, and that calls the opener back. When you say something in a group without naming anyone, a held Bot is not asked whether it is its to answer (that judgement call is not made). Each wake a hold turns away is recorded in the work log (`wake.suppressed` in `work_events`), with what would have woken the Bot — your line, a Bot's line, a check-back, a plan call-back, a routine, a Continue — and which holds turned it away. A check-back turned away is set aside and comes back when the hold is lifted, and so is the report-back to a held Bot that opened the direct. Lines a running turn heard but ended without reading are put to the holds one by one: each one about held work is recorded as a wake turned away and stays in the transcript for after the lift, and the newest check-back among them is set aside to fire then; the rest open one more turn on the newest of them as usual, and only those ride along into it; a quiet plan's call-back is not kept, and the plan is looked at again the next time a turn on it ends and it goes quiet; a routine that comes due is recorded once, counts as not yet run, and runs once for its latest due time after the lift; Continue answers `409 held`, and the phone gets the same code. A turn a hold covers makes no call with an effect — each comes back `held` without running: the shell, writing or deleting files, sending a message, booking a check-back, asking you a question, changing a profile, skills, memories, routines, endpoints or MCP servers, and any MCP tool not marked read-only. Reading still works (reading files, listing folders, the `list_*` tools, `read_skill`, `end_turn`, and MCP tools their server marks `readOnlyHint`, such as looking up a video job). A call that was waiting on your approval does not run either if the hold came before you allowed it. The database adds a last layer: triggers on the turns table refuse to write a live turn a hold covers — including a row with no `mode` written by an older build that knows nothing of holds, since a stop comes before compatibility — and refuse moving a live turn into a hold's cover in place or changing its `mode`. The one turn they let through is the read-only one a line of yours opens (`mode = readonly`): a line of yours to a held Bot — in its direct, or naming it in a group — opens one beside whatever it was doing, bound to no plan, shown only the tools that change nothing, and opening on a line that says you stopped this work (with your words) and that this turn can only answer. Its reply is posted as usual and wakes nobody; another Bot naming it meanwhile opens a turn beside it, not cutting it off.

**Your lines**: a line of yours is read for a stop or a go on right after the status question check (see Control line in CONTEXT). A line that is only control is carried out and goes nowhere else — no filing, no turn, no model call:
- A stop makes a hold per scope it names (source `user_text`, the line as its `source_message_id`), and the app posts a receipt in the conversation you said it in: a `system` line kept from the Bots, carrying `control: {kind: "receipt", verb: "stop", hold_ids, offer, scopes}` for its buttons (undo; stop every Bot; drop the job, when you said 算了 with it). Every fact in it comes from the holds' record: the turns ended, each with its plan, its conversation and its last step; the check-backs set aside; the plans parked; the other Bots still working in those plans; what is running now.
- A go on lifts the holds the words name — for a Bot, its own, on all its work or on part of it; for a plan, the hold on it and those on a Bot's work in it; said in a direct, either also lifts any other hold made by a line said there, except one on another Bot; for a group, the hold on it and every hold made by a line said there; for everything, every hold you made, not the ones taken over at boot. Never wider than the words: "@X continue" in a group lifts X's own holds, not the group's. Each turn a lifted hold ended opens again in its conversation, on a system line with your words, its plan and ticket, the files it wrote and its last calls; the line says what happened and asks for nothing. In a direct with you it opens beside whatever the Bot took up there meanwhile; in a group or a Bot↔Bot direct, where a Bot works one turn at a time, a turn it already has there hears the line instead (a read-only one answering you does not). One the Bot has since taken up there does not open again. One another hold still covers does not either: it is handed to that hold (`held_over`) — to one that is not a Stop's, when there is one — and opens when that one is lifted. The receipt names what was lifted, what opened again, the check-backs back on and the plans put back. With nothing held, a go on is an ordinary line and goes to the Bot. Held only by something the words cannot lift (a hold on everything; or, when you name one Bot in a group, the hold on the group or on the plan its turn would land in), the app answers with a status line offering to let just this one go on or all of it (`continue_only`, `continue_all`); the receipt offers the same when such a hold is still there after a lift. A Stop's hold goes with your next line about its job: when it is all that holds the work back and the "continue" lands on that job, "continue" is an ordinary line about the job, goes to the Bot and lifts the Stop's hold the way any such line does (below). A "continue" said to a Bot (in its direct, or naming it in a group) is also about its work a Stop holds elsewhere, such as the job it was doing in a direct with another Bot: you cannot speak there, so this line lifts that hold. A go on that names everything ("all Bots continue", "all of it, continue") is about every Stop you pressed before it, wherever you pressed it, and is used up by them even when nothing else is held; its receipt goes where you said it. When a go on is used up this way, or by lifting other holds, the Stops it is about go with it, and their work opens again on the same system line, since that is the only way your words reach it. A "continue" said to one Bot is about that Bot's Stops only: other Bots' Stops on the plan its line lands on stay until you next speak to them about that job.
- "Has it stopped?" and "you haven't stopped" — and a status question about a held Bot that the plan's status answer does not take — get the app's answer: each hold over what was asked about, with the line that made it, and what of it is running now (`control.kind` `status`). First, anything still running under one of those holds is ended and recorded as a violation (`effect.violations`, `hold.violation` in the work log); there should never be any. Said with nothing held, the answer ends with a stop button; so does the answer to asking whether it can stop ("can it stop?", "stop, OK?" — with no "you", "for now", "for a moment" or "please" it asks, it does not request). The status answer about a plan lists the stops over the plan and the Bots that worked in it the same way, after the same check.
- A line with a control word and more in it is delivered as usual and carries `control: {kind: "possible_control", offer, scopes}` for the buttons; nothing in it is carried out. 算了 / 不做了 / 取消 on its own is the same, offering to stop or to drop the job.

**Stop on a turn's card**: once holds are on, it is a hold on that Bot's work in the turn's plan (on the turn alone when it has none), source `user_button`, lifted by your next line (`lift_on_next_user_message`). The turn ends under it as above, the check-backs it booked are set aside instead of voided, and a receipt goes into the turn's conversation when you are in it. Your next line about that job — filed under that plan, or landing on it — lifts it before it wakes anyone, and the Bot goes on from that line; nothing opens again on a note, since Stop meant "not this". Only a line said after the Stop counts: one sent just before, still being filed when you pressed it, does not. "Continue" on its own is such a line; a "continue" to that Bot lifts it even when said away from that job, and the stopped turn then opens again on a note (above). A line that reads like control and carries the buttons, or a hold of any other scope, never lifts it that way.

**At boot**: once the engine level has reached holds, every boot checks again. A plan parked before holds existed — status and spec's status both parked, which is how you or the organizer stopped one — becomes a plan hold of source `legacy`, so from then on only you can put it back in progress; a plan only pushed out of the current slot by a newer one (its spec still says In progress) is left alone. Then any plan a hold covers that is not parked, and any check-back it covers that is not set aside, is put right, and daemon.log says so.

**API**: `GET /v1/holds` (holds in force by default, `?status=all` for lifted ones too, newest first), `GET /v1/holds/:id`, `POST /v1/holds` (a stop you make from a button or a menu, recorded as `user_button`; the turns it covers end at once, as above), `POST /v1/holds/:id/lift` (the turns it ended open again as with a go on, a Stop's excepted; one already lifted comes back unchanged); the phone can do the same. Parking a plan with `PATCH /v1/tasks/:id/spec` ends what runs in it the same way. `POST /v1/turns/stop` is the Stop above. A line the app read or wrote about your stops carries `control` (`MessageControl`). Making a hold, lifting it and recording what it did each reach clients as a `hold.upsert` event. A plan's `held_by` is as of when it was read: a hold that changes nothing on the plan's row, such as one on everything, sends only `hold.upsert` when it is made and when it is lifted, so a client that shows `held_by` reads the plan again on that event.

<a id="terminal"></a>
## Terminal

A shell session you open yourself on this Mac, held by the daemon. It has the same rights as Terminal.app: its cwd starts in the workspace by default, but it is not confined to the workspace and needs no approval. Approval governs Bots' dangerous actions, and you don't need to ask yourself for permission. It is for running your own work, including processes that stay up, such as starting a project. Closing the window doesn't stop it. Which directory it is in is whatever the shell itself reports (zsh does this out of the box, once before each prompt): after a `cd` the tab name follows; if it has never reported, it is the directory it was opened in. When you quit or the daemon itself stops, the processes inside stop with it, but its directory and what was on screen are kept, and the next launch opens a new one in that directory. Only "End session" forgets it. The screen lives in the daemon too: when you reattach, you get it as it is now, full-screen programs included. Questions a program asks the terminal are answered only by the daemon, never by panes, so even when several panes watch one session, each question is answered once. The shell's environment is set up the way Terminal.app sets it up, but only an allowlist gets through; the daemon's other environment variables (including keys) are not passed in. When the desktop and a phone watch one session at the same time, its rows and columns follow whichever end you most recently looked at or typed in. Paired devices have the same rights: you can see it and type into it on your phone. Bots can't see it, can't use it, and don't know it exists. On the desktop, one terminal tab is one session: opening a new terminal tab starts a new shell, and a tab no longer holds a row of sessions to switch between. Closing a tab only removes it from the window; the processes keep running. Sessions not shown in any tab can be brought back with "Reattach" from "+" or from an empty pane. Phones and narrow screens have no panes; all sessions are gathered on the Terminal page as its tabs. To stop one, you must explicitly choose "End session" and confirm. The daemon's session list is the real one; sessions opened in the same folder are numbered in the order they were opened, and they carry the same names in desktop tabs and on the phone.

<a id="completion"></a>
## Completion

Every hop's request carries `max_tokens`: the model's `max_output` in its endpoint's list, or 32,768 when unset, reasoning tokens included. Without a cap, on 2026-09-29 three hops each wrote one sentence up to the endpoint's default of 128,000 tokens (one of them for 17 minutes, the same sentence 3,457 times), and each was posted as the turn's closing line; in a Bot↔Bot direct it also woke the other Bot, whose next hop read the whole thing again. 32,768 comes from the spend records: a normal hop's output peaked a little over 30,000, and the only hops past 32,768 were those three repetitions, so anything lower would cut normal hops that write a large file. An endpoint that rejects `max_tokens` with a 400 naming `max_completion_tokens` instead (as OpenAI's reasoning models do) gets the request again at once with that field, and that model gets it from then on. A model that writes less than that (DeepSeek's deepseek-chat at most 8,192, OpenAI's gpt-4o at most 16,384) has its endpoint refuse the cap with a 400: when the error states the model's own limit, the request goes again at once with that number; when it states none, without a cap; and that model gets the same from then on. These requests went through before hops had a cap, so a refusal like this must not fail the turn, and the cap cannot be changed in Settings. When the prompt and the cap together are over the model's context (the error says "32768 in the completion", or names the cap while talking about the context length, as vLLM does), the request goes again without a cap, that time only: the next hop sends the cap first again.

While a reply streams, the app reads only its prose, not tool arguments, code blocks or tables: over the last 6,000 characters it splits sentences (at full stops, question and exclamation marks, semicolons, ellipses and line breaks, and at an English full stop followed by a space) and compares each by its letters and digits alone, ignoring case; digits still count ("shot 11" and "shot 12" are two sentences). When the same sentence (8 characters or more) comes a fifth time in a row, or fewer than a fifth of at least 20 recent sentences are distinct, the completion is cut off on the spot as a repetition, usually within seconds. "In a row" means nothing new came between two copies, only sentences seen before: a loop has nothing between its copies but more of itself, while a per-item verdict list ("Shot 03: passed. The frame is stable, no rework needed." on every line) has each item's own name between two copies of the comment, and is not a repetition. The share of distinct sentences counts sentences of any length, so twenty identical lines of "- [x] done" that never say which item each is still count as a repetition. A finished reply is checked by the same rules again before it is posted.

These completions have failed and are not replies:
- **Repetition**: as above.
- **Refusal**: the endpoint's finish reason is `content_filter` or one of Gemini's like `SAFETY`; or the whole reply is at most 300 characters with no tool call and is a canned refusal (speaking as a language model and saying it cannot, or only "I can't help with that" or "抱歉，我无法协助处理这个请求"). A Bot explaining which step it cannot do and why is not a refusal. Gemini refusals had gone out as a Bot's message twice before this.
- **Incomplete**: the connection closed before the reply was finished (with neither a finish reason nor `[DONE]`; this is what the endpoint or a proxy in between closing the connection partway looks like), the finish reason said it stopped to call tools and no whole tool call arrived, or a tool call's arguments were not whole JSON. The client first tries the same request up to three times, and only when it is still incomplete does it count as failed.
- **Overtime**: one request may take this long from being sent to the end of its stream: the larger of 10 minutes and `max_output` ÷ the model's measured 10th-percentile speed × 1.5. The speed is `stream_tps_p10` in the list; unmeasured, it is 10 minutes. Time waiting for a free slot at the endpoint, time running tools and time asleep with the lid shut do not count.

A failed completion posts nothing, stays out of the loop and wakes nobody. The same model gets one more hop with a note saying why (for a repetition: do not restate it or write a sign-off, do the next step by calling the tool directly); if that fails too, the turn ends as failed, with a "This turn did not finish: …" line in the session and, when you are in it, a failure notification. Any normal hop in between earns the next failure another go. Not reaching the endpoint, a busy endpoint, an endpoint error and a stream that goes quiet partway (the connection stays open but no next piece arrives) are not in this list: the client has already resent the same request, and the turn ends at once. Going quiet only shows once the idle time (3 minutes) has run out, so three tries already take 9 minutes and one more hop would double that; a connection closed partway shows within seconds, so it counts as incomplete, and one more hop costs little. When a stream goes quiet or breaks off partway, its first half used to be posted as the reply or have its tool calls run; now none of it is used.

Finish reasons are read regardless of case, including Gemini's own ones that a proxy passes through as they are: `STOP` is `stop`, and `max_tokens`, `MAX_TOKENS` and Mistral's `model_length` all read as `length`. An empty finish reason is none at all: some endpoints send `""` on every chunk until the last. A finish reason the client has no name for (such as `eos`) means the model says it is done, so the stream is whole: it is not resent as half a stream, and the reply is judged by the rules above like any other. `error` is the exception: OpenRouter ends a stream with it when the model behind it failed partway, so what came is only half, and it counts as incomplete. A stream that goes quiet after its finish reason (the endpoint neither sends usage and `[DONE]` nor closes) is taken as the reply once the idle time runs out: the model has finished, and only the endpoint's last packets are missing.

A reply cut off at the output cap (finish reason `length`) without repeating is carried on for one hop: the cut part is not posted but stays in the loop to carry on from, with a note to do the next step by calling the tool directly and to put long content in files, written in parts; when the cut falls inside a tool call's arguments, that call is not run and the note asks for it in parts. If the carrying-on hop reaches the cap too, the turn ends as failed for hitting the output limit.

Streamed output no longer counts as the turn making progress: it used to refresh the turn's last activity as each piece arrived, so a hop could write for any length of time without looking stuck. A completion is now bounded by its own time limit, and the stale sweep (20 minutes without any activity) covers only the time outside completions.

`max_output` and `stream_tps_p10` do not show in Settings; saving the list from Settings again keeps both, and only a `null` sent through the API clears one. When either is invalid in the stored list (say 0, or a string), only that value is ignored: the model stays in the list, and the Bots using it are unaffected.

<a id="artifact"></a>
## Artifact

A workspace-relative path, or an `http`/`https` link, referenced in a message. The file itself lives in the workspace (or at the remote URL). Files inside the workspace written during a turn appear in its final message automatically. Opening one shows it in the preview panel to the right of the chat (image / audio and video / PDF / text / single-file HTML / Word / Excel / PowerPoint); other kinds (subtitles, archives…) state that preview is not supported: the app window on this machine offers "Open with default app", and phones and browsers offer a download button. Every file opened remotely can be downloaded: on a phone from the right end of the preview's top bar, on wide screens from the row of buttons above the file, and on the flow board's file cards from the card header. Opening remotely, downloading and sending attachments have no file size limit; on desktop this preview can also be dragged out into a pane of its own. The tree on the left of the panel lists every path **this job** has referenced — not only this message's, and not every file in the work dir; "associated" means it has been referenced. The tree is rooted at the work dir, paths this job referenced outside that directory sit flat beside it, and the ones this message itself references are marked; the panel shares one column with the chat, with a drag bar between them to change the width; when one message has several paths, or when you open the workspace, the left side is a file tree, and the split between tree and content can be dragged. Preview column and file tree widths you have dragged are still there after you quit and reopen. Text is edited with Monaco + Shiki (line numbers, find / replace via ⌘F, bracket and tag matching, heading folding, line wrap); the preview itself no longer has find, wrap, copy, save or close buttons. Markdown and single-file HTML show the rendered result by default; a floating button at the top center of the content, which does not scroll with the body, switches between preview and source. PDFs are rendered with the built-in pdf.js (paging, zoom, fit width / whole page, in-page find), not the system PDF viewer. UTF-8 text inside the workspace can be written back to the same path with Cmd+S / save; switching files or closing the panel with unsaved changes asks for confirmation first. On desktop the preview has no title bar of its own: the file name and close are on the workbench tab; narrow screens and phones keep a strip with back and the file name. Right-clicking any item in the file tree offers "Show in Finder" and "Open with default app", which take effect only in the app window on this machine. Files and folders in the tree (several at once when picked with ⌘ or Shift) can be dragged straight onto the composer, which lights up under the pointer; dropped, they wait above the input as attachments and go out with the next message by their workspace path — nothing is uploaded or copied into `inbox/`, the Bot reads them as "附件：path" lines, and pictures still reach the model as pixels. Esc during the drag puts them back. The file-drop session, read-only conversations and a composer that is still sending take nothing; there is no dragging on phones or touch screens. In a handoff, the path goes into the message to the other party; there is no separate kind. The kind is inferred from the extension at preview time. Artifacts inside the workspace can be annotated (see "Annotation").

<a id="annotation"></a>
## Annotation

A remark you write about one spot in an artifact. It is attached to a workspace-relative path, an anchor, and the message that delivered the artifact. It starts as a draft the Bot cannot see; drafts collect into a batch that is sent all at once, combined into one reply that quotes the delivering message and @-mentions the Bot that delivered it. Once sent it is "Pending", and a Bot or you mark it "Resolved"; a resolved one can be reopened. As soon as it is marked resolved it comes off the file — the box on an image, the dot in the code margin, the mark in Markdown, the box on a PDF page, the number on HTML, the marker on a timeline — so what stays on the file is what is still unresolved; the list keeps listing them all. They are drawn back only when "Show resolved" is checked in the preview column, and only for that preview; clicking a resolved one in the list to locate it draws that one while it is located, and clicking it again to deselect takes it down; clicking its card in the conversation only opens the list at that item and does not draw it back on the file. When the file has changed and the anchor no longer matches, it is marked "Text changed" and its status stays the same; when the file is gone, it is marked "File gone". An annotation is not a snapshot of the artifact: it records only the quote, position and file hash at the time and does not keep the old file (when the selection is longer than the quote limit, it also records the whole span's length and fingerprint, used to tell whether that span is still there and whether it has changed). What it attaches to: a preview opened from a message attaches to that message and the Bot that delivered it; when the delivering message is in a Bot↔Bot direct you are not in, the batch goes to your direct with the delivering Bot, and the message records the origin. Only files inside the workspace can be annotated; link artifacts cannot. Each Bot that an annotation message wakes keeps the work dir of the turn in which it delivered the artifact (its most recent delivery in this batch), even if the session has been quiet long enough for that job to have closed — it is changing the same deliverable; this turn only works in that directory: it does not reopen that job or take the session's current plan's place, likewise when that job belongs to another session (it was delivered in a Bot↔Bot direct), and what each of the two sessions is carrying on with is unaffected. It is an ordinary follow-up message: it lands on the delivering turn and joins the correction chain, with no extra weight. A batch holds at most 50 annotations, and each body at most 2000 characters. In a group, one batch can go to several Bots at once: in the context, every annotation states which Bot it is for (the Bot that delivered that artifact, or "a deleted Bot" if it has been deleted), and `list_annotations` includes this too; each Bot handles only the ones for itself and leaves the ones for other Bots to those Bots, though it may mention them; ones for a deleted Bot have no one to take them, so the Bots this batch woke handle them. What a Bot can do: work through the ones for itself one by one; mark the ones it changed as resolved with `resolve_annotation`, with one sentence on how it changed them (any Bot can mark one — a Bot is not a permission boundary — and who marked it is recorded); check what is still unresolved with `list_annotations` (paths resolve the same way as in `read_file`, and a path outside the workspace is an error right away); and it gets a reminder when `read_file` reads a file that still has pending annotations. What a Bot cannot do: reopen, delete or create annotations. Clearing history or deleting a session deletes the annotations attached to those messages along with them; deleting a file does not delete its annotations. Anchor kinds: text / code line range, a selection in rendered Markdown, a box drawn on an image, a region on a PDF page, an HTML element, an audio / video time point.

<a id="context-window"></a>
## Context window

What the model actually sees in a turn: the profile, the catalog of enabled skills, the system instructions, the "MCP this turn" section, this Bot's memory, the situation block (in a group it has the present members, live turns, who woke the Bot and the user's latest message; every turn has this job's plan (Goal, Done when, Rules, Process, Progress), the ticket list, this turn's ticket, precedents of the same kind, the files already handed over, the trace, and the Bot's own pending check-back; when no plan has been organized yet it falls back to the original request, and the first turn is marked "This is the first turn of this job"; all of it is read from rows already in the database, and the turn itself does not ask the model for a summary), the most recent stretch of the transcript (including the pixels of raster attachments, only the newest ones within a single budget; a user message with annotations expands, after its body, each annotation's id, which Bot it is for, path, position, quote or cropped image, and remark (page text and text you wrote is folded onto one line or indented line by line, so it cannot pose as the next item); cropped images and raster attachments spend the same budget and are sent to the model as pixels, and once the budget is used up, a cropped image leaves only the annotation's text), and this turn's tool loop. The full history exists only in the database, for you to browse and for search; it is not stuffed into the model wholesale. Judgement calls use a separate, shorter window without images. For an oversized tool result, the full JSON is first saved in the workspace, and the window holds only a bounded preview and full_result_path; the Bot can go on to extract the fields it needs or decode the file with the shell, and a truncated preview is not treated as the original result being lost.

<a id="spend"></a>
## Spend

An append-only ledger of calls on this machine. Seven kinds of endpoint call each record one row per call: turn completion, judgement, model routing before a turn opens, correction-chain review, each learning step after a review, input suggestions, and organizing. Model routing and organizing belong to decision routing; review and learning steps together make up feedback routing; judgement is listed on its own, and input suggestions fall under "Other"; neither input suggestions nor organizing belong to any Bot. Each row stores the actual model, endpoint and thinking level, plus the session and Bot names at the time it was written; rows are kept when you delete a session, clear history or delete a Bot, deleted objects show their name snapshot marked "Deleted", and rows whose model could not be found during migration show "Unrecorded model". Tokens come only from the endpoint's `usage`; when missing, they show "—". When the provider returns `cost_in_usd_ticks`, the call is recorded as reported; with no reported cost, it is estimated when both input and output tokens are present and a billing price is configured. Estimates follow the currently configured prices: setting, changing or clearing a model's price recomputes all of its calls on that endpoint that have no reported cost, and a model removed from the list keeps its existing estimates. Cached input uses the cache price (left blank, it falls back to the input price; missing cached tokens count as 0); reasoning tokens are already included in output and are not added again.
