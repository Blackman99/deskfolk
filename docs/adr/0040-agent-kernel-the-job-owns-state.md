# 以「一件事」为中心的确定性内核

2026-09-29 按八个目标审了一遍现有机制：边干边收消息、叫停就停、没做完不停下、记住你反复说的问题、自我反思、按规划整理产物和归属、模型选择依据真实反馈、流程图准确。结论是五个达不到、三个只做到一部分，而且问题出在结构上，不在某个 bug：

- **没有「一件事」这个实体。** 执行单位是一条消息开的一轮，只属于一个会话。同一个 Bot 在两个会话里的两轮互相看得见，却管不了对方。09-27 同一组镜头因此被两条私聊各渲了一遍，视频导演三天里有 29 对重叠轮落在同一个任务上。
- **叫停不是状态。** 叫停只是模型写的 `parked` 标签。至少三处代码能把它翻回去，七条以上推进路径都不看它，点 Stop 还会触发整理，再触发规划叫回。09-29 你叫停后，Bot 在别的私聊里接着送审；11:02 规划叫回又让它交了一个新镜头。
- **你的要求存在一份模型能整份重写的 JSON 里。** 70 版修订里，整理跳丢过 15 条规则。「机械臂是左手」「片长约 2 分钟」丢掉后再也没回来；规划做完之后再推翻，就只能开新规划，规则跟着清零。
- **「做完 / 做好」没有可验证的定义。** 放行靠同一类模型自评。审片员五次整片放行都被你推翻，107 秒的母带被判成「约 2 分钟」。
- **反馈和学习归因错位。** 反馈挂在「同一会话的下一句」上，Bot 之间私聊里的工作一行反馈都收不到。复盘只问模型选得对不对，270 次里 259 次是「没问题」。
- 另有：一跳的输出没有上限，12.8 万 token 的复读被当成收尾发出；调度状态有七份放在进程内存里，重启就丢；文档写的行为和代码对不上。

[ADR 0037](0037-cut-the-core-loop-by-the-benchmark.md) 的基准说明，旁路模型调用在小活上量不出好处。但它没有长活、叫停、反复投诉，群也不大，而上面这些翻车全出在这几种场景里。

## 现在

**原则。** 模型负责理解、提议和干活；状态只由确定性代码写入，并且可审计。

1. 规划（`tasks` 表，历史名）是唯一持有状态的实体：谁在做、球在谁手里、在等什么、做完没有、被没被叫停。
2. 执行单位是**工作项**，即「Bot × 规划 × 任务」。
3. 叫停是一张 `holds` 表，只有你能解除。所有开轮入口、叫醒路径和有副作用的工具调用都要过它。
4. 你的原话收到时就复制一份，清空聊天不删。需求台账只增不删，模型只能提补丁，引文由代码核对。
5. 放行要过三道：守护进程自己跑的检查、逐条带证据的审查、你的验收。
6. 流程图、局面块、`map.md` 都从同一组表投影出来，不由模型整理。
7. 每一跳都有输出上限和复读检测；截断、复读、拒答一律算失败，不算收尾。
8. 模型选择按「钉住 → 角色默认 → 能力过滤 → 确定性升级」的顺序定，不再每轮调模型选路。
9. 教训绑定检测器和动作（例如调用前拦下），不再只是注入一段文字。

**库层不变量**，代码和测试按编号引用：

| 编号 | 内容 |
|---|---|
| I1 | 同一工作项任意时刻最多一段活的执行（部分唯一索引） |
| I1b | 同一 Bot 在同一件事上最多一段 |
| I2 | 被叫停覆盖的范围里开不出活的执行段（turns 上的 INSERT 和 UPDATE 触发器）；唯一的豁免是你提问时开的只读段 |
| I3 | 有副作用的工具调用前检查叫停和租约 |
| I4 | 需求只有一条删除路径：你的「彻底删除」 |
| I5 | 执行段进入终态时必须写明结束原因 |
| I6 | 标记为等待的工作项必须有打开的等待记录 |
| I7 | 解除叫停、验收、作废，只接受带用户动作 id 的调用 |
| I8 | 一个执行段的工作目录最多变一次：从「未归属」变为任务目录 |
| I9 | 任何一次整理之后，未关闭的需求集合不会变小，没有例外：连同一数值维度被你更晚的话换了新值，也只生成待你确认的替代 |
| I10 | 每个子进程在 spawn 交回 pid 的同一拍登记进程组，退出后删除；叫停和重启清理都按这张表杀。P1 先覆盖 Bot 的 `shell`，验收检查、ffmpeg、MCP 服务器等其余子进程之后补上 |

**版本闸。** 设置里有三个键：
- `schema_min_compatible`：打开这个库至少要多高的 `SCHEMA_LEVEL`；
- `engine_level`：线性开关，只能按顺序往上调；
- `last_shutdown`：clean 或 crash，下次启动时按它决定怎么续跑。

守护进程发现库要求的级别高于自己，就拒绝开库，并提示先更新。安装版和开发版共用同一个数据目录，所以闸的读取代码要先随一次发布铺开，之后的阶段才能把级别调上去。目前的级别：1 叫停（P2，[ADR 0041](0041-control-plane-holds-and-restarts.md)），2 工作项（P4b，[ADR 0043](0043-work-items-and-attribution.md)），3 委派与结束契约（P4c，[ADR 0044](0044-delegation-and-end-contract.md)），4 监督器（P4c，[ADR 0045](0045-supervisor.md)），5 交付与审查（P4e，[ADR 0046](0046-submissions-and-reviews.md)）；每一级启用时把 `schema_min_compatible` 抬到同一个数。开发者越过旧安装版的放行只覆盖它接受时的那一级，之后的级别要再接受一次。

**自动抬升的上限**（`schema-gate.ts` 的 `ENGINE_LEVEL_BY_DEFAULT`，2026-10-02 第四轮评审）。`ENGINE_LEVEL` 是这次构建最高支持到哪一级，不等于它会自己抬到哪一级：高于 `ENGINE_LEVEL_BY_DEFAULT`（目前等于监督器那级，4）的级别算实验性的，还没在真实工作里跑够、审过（如今是交付与审查，5 级，见 [ADR 0046](0046-submissions-and-reviews.md)；外部作业，6 级，见 [ADR 0047](0047-external-jobs.md)；默认模型代替每轮选路，7 级，见 [ADR 0048](0048-default-models.md)，同级的按能力挑模型与失败提档见 [ADR 0049](0049-capability-filter-and-escalation.md)；质量事件和教训代替事后复盘，8 级，见 [ADR 0050](0050-quality-events-and-lessons.md)）。没有开发者认领时，`raiseEngineLevel` 不论有没有旧安装版共享数据目录、不论那个旧版本读不读闸，一律只抬到 `min(ENGINE_LEVEL, ENGINE_LEVEL_BY_DEFAULT)`——打包应用自己的数据目录、或源码跑在独立数据目录上（`installed === null`）都不例外。开发者的认领（`acceptOlderApp`：`scripts/engine-level.ts --accept-older-app`，或 `POST /v1/capabilities/raise`，两处记的都是这次构建的 `ENGINE_LEVEL`）把上限抬到 `min(ENGINE_LEVEL, max(ENGINE_LEVEL_BY_DEFAULT, optIn.level))`——认领只会把上限往上抬，早先版本记下的低级别认领（或没写级别的认领）不会把库压在默认级别以下；这条路不需要真的有旧安装版，这就是开发者显式打开一个实验级别的办法。只有在共享数据目录的安装版真的早于闸时，上限才是 `min(ENGINE_LEVEL, optIn.level)`：开发者只认领过越过那份旧版到这一级，没说过更高也安全。

**迁移分三类。**
- **A 类**（纯新增）：新表、可空新列、只看新列的索引和触发器。不提闸。
- **B 类**（旧二进制会违反或误解的语义）：turns 上的触发器、挂起的等待、叫停的扣押语义。所在阶段提高 `schema_min_compatible`。
- **C 类**（改 CHECK、改名、删列）：一律放到最后的收缩阶段。在那之前，新取值放新列，旧列写最接近的旧值。

**阶段。**

| 阶段 | 内容 |
|---|---|
| P0 | 回放夹具、基线、可观测性、版本闸读取 |
| P1 | 止血：输出上限与失败形状、Stop 不再触发整理和叫回、问进度不再顺带叫回、开轮不再改规划状态、修掉悄悄新开规划的竞态、按进程组杀、中性化叫醒文案、全盘递归搜索守卫 |
| P2 | 控制面：叫停、叫醒闸、控制句、回执、重启分类（[ADR 0041](0041-control-plane-holds-and-restarts.md)） |
| P3 | 原话、需求台账、从原话派生检查（读出的数只出提议卡片，再说一次就带着次数再出；提议对上文件照样量、结果给你和审查者看，但不拦；只有你点「确认」才成为门禁；生效的检查从不自己变，后来说成目标的不同数只出替换卡片，旧的照样生效，直到你选）、投影板面、整理跳不再写规则和验收、settle 只记交接、花费按用途细分（[ADR 0042](0042-requirements-ledger.md)） |
| P4 | 分五步，每一步单独发布：P4a 收件箱落库 → P4b 工作项与归属 → P4c 委派、结束契约与监督器 → P4d 外部作业 → P4e 交付、审查与分件 |
| P5 | 模型选择与学习 |
| P6 | 收缩 |

每个阶段都能单独发布，系统全程可用。

**进入 P4b 之前的门槛。** P4b/P4c 引入的结束契约三个动词（`end_turn`/`submit`/`work_on`）落地前，协议依从探针（`eval:protocol-probe`）要先在 grk-4.7-build-fast 和 gemini-3.8-flash-high 上把退回率（首次尝试就没依从的用例占比）压到 10% 以下；量的是模型面对这样一份契约会怎么应，不是已经落地的引擎行为。

**回放夹具。** 真实事故写成 `apps/daemon/src/scenarios/` 下的场景测试，断言的是目标行为。所在阶段还没做完的标 `test.failing`，做完的那个阶段改成普通测试；一起事故分几个阶段落地的，每个阶段一条用例。

## 取舍

- **推翻多条旧决定，按阶段写明。**
  - [ADR 0016](0016-group-one-live-turn-per-bot.md) 的「群里不能停」：P2 起群里能停（[ADR 0041](0041-control-plane-holds-and-restarts.md)，连同 [ADR 0031](0031-heard-in-the-live-turn-and-plans-closed-on-evidence.md) 把搁置当成停下的做法）。
  - [ADR 0020](0020-bot-direct-per-trigger.md) 的「每次交接新开私聊」：P4 起按「两个 Bot × 规划」复用一条线程。
  - [ADR 0028](0028-job-brief-check-back-and-clarification.md) 的「交接即结束本轮」：P4 起发言不结束本段。
  - [ADR 0031](0031-heard-in-the-live-turn-and-plans-closed-on-evidence.md) 的「不让 Bot 报任务号」：P4 起由 Bot 声明、应用校验。
  - [ADR 0039](0039-plans-with-work-left-are-called-back.md) 的规划叫回：P4 起由监督器按持球者叫醒取代。
  - [ADR 0018](0018-per-bot-route-learning.md)、[0019](0019-agent-routing-and-review.md)、[0024](0024-route-execution-and-learning-hop.md) 的选路和复盘：P5 删除。
  - [ADR 0030](0030-plans-tickets-and-organizer.md) 的整理跳：P1 起 Stop 结束的轮不引起整理，还取消这个规划已经排着的整理和叫回前的再看，P3 起不再写规则和验收（连同 [ADR 0031](0031-heard-in-the-live-turn-and-plans-closed-on-evidence.md) 要做出能用的东西时写进验收的那条「照着启动方式能在本机跑起来」），settle 只记交接，先例删除（换成原话层和需求台账，工艺类要求由同一会话的新规划继承），P4 删除。
  - [ADR 0038](0038-rules-are-only-your-words.md) 守「规则只收你的话」的办法（提示词、`user_lines`、`holdSettle`）：P3 起整理跳不写规则，`holdSettle` 删除，你的要求记在库核对引文的需求台账里（[ADR 0042](0042-requirements-ledger.md)）。
  - [ADR 0025](0025-annotations-are-anchored-quote-replies.md) 的「批注叫醒时把关了的那件事重新打开」：P1 起开轮从不改规划的状态，只把关了的规划的关闭时间挪到现在。
  - [ADR 0032](0032-every-line-says-which-job-and-reaches-its-turns.md) 的「对不上候选的 resume、join 当 continue」：P1 起什么都不落。

  各阶段落地时再写各自的 ADR，并回头在被取代的 ADR 里注明：P2 是 [ADR 0041](0041-control-plane-holds-and-restarts.md)，P3 是 [ADR 0042](0042-requirements-ledger.md)，连同它们和本文的出入。
- **先铺夹具再改。** 每一起事故先在测试里复现，改完的阶段把它翻绿。文档里写了、代码没实现，是之前一次次排查走偏的原因。
- **省钱不是目的。** 旁路调用每天大约省 8–12 美元，大头仍是轮次本身。真正的收益是开轮前的等待从约 33 秒降到约 0.1 秒，以及少出事。

## 不做

- 不做纯事件溯源：状态表是事实来源，事件表只追加，用于审计和推送。
- 不新增会话类型：Bot 之间的线程仍是私聊。
- 不给 Bot 叫停工具，也不让 Bot 直接写需求台账。
- 不按 ADR 0037 小样本的完成率论证去留：那组数据只能说明花费和延迟。
