# 远程屏幕借 macOS 的屏幕共享，WebRTC 直连放在独立 helper，连不上退回中继

远程访问能用会话、工作区、终端和文件，但碰不到 Mac 的图形界面：系统弹窗、钥匙串确认、浏览器里的页面、锁屏，都得回到 Mac 前。人不在 Mac 前的时候，屏幕通常是锁着的。所以要的是：在手机上看到并操作这台 Mac 的屏幕，锁着也行。

## 决定

- **画面和输入用 macOS 自带的屏幕共享**（screensharingd，本机 5900 端口上的 RFB）。手机上用 noVNC 画，它的认证（ARD type 30，或者 VNC 密码）在两端之间进行。Mac 账户密码在手机上输一次，连上后存在手机上（和配对密钥同一处），屏幕共享拒绝时忘掉。守护进程只连这一个本机端口，端口不是参数：发布包里没有任何办法让它连到别处，测试改端口只能在构造时传，helper 只在 debug 构建里读覆盖变量。
- **传输先试 WebRTC data channel 直连**。信令走现有的 Noise 远程链路（非 trickle 的一次 offer / answer），SDP 里的 DTLS 指纹因此出自这台已配对的设备，不需要另一套信任。ICE 服务器只取 Mac 设置里的，默认空：同一网络、IPv6 能直连，其余要你自己在中继旁跑 STUN（或 TURN）。
- **直连在独立的 `real-bot-rtc`（Rust，webrtc-rs）里**，守护进程按需拉起，stdio 帧和 pty helper 同一种格式。它只接一个叫 `rfb` 的通道，开了才连屏幕共享，靠 SCTP 的发送上限向屏幕共享反压。依赖的 rtc-sctp 0.21.0 换成仓库里一份只改了一个常量的副本（`apps/rtc-helper/vendor/rtc-sctp`）：重传超时下限从 RFC 的 1 秒降到 200 ms（和 Linux TCP 一样）。屏幕的一次更新是一串几 MB 的包，末尾丢了包，后面没有包能触发快速重传，只能等超时；原版写死 1 秒、不能配置，切一次窗口就多停一秒多（本机回环实测 7.45 MB 的整屏更新：中位 1194 ms，改后 240–390 ms）。
- **连不上就退回中继**：守护进程自己连屏幕共享，字节装进新的 type 9 帧，两端都不超前对方确认的 48 KiB。不部署 TURN。
- **开关只在 Mac 窗里**（`/v1/remote/screen`，本机接口、不在远程白名单），默认关；会话绑在它所在的链路上，撤销设备、关开关、Mac 上点断开、链路断、45 秒没有保活，都当场结束。
- **手机上的操作分两种**：默认点哪里就是在哪里点，交给 noVNC 的手势；「触摸板」模式下页面自己读触摸、自己按 RFB 把指针事件写进通道。noVNC 没有把指针放到手指以外地方的接口，它的手势还要滑过 50 像素才算拖动，短于这个的滑动会被当成点按。ARD 只加密凭据，之后是明文 RFB，这些六字节的消息夹在 noVNC 自己的消息之间没问题；将来换成加密整条流的认证方式，要先改回经 noVNC 发。
- **「流畅」降的是 Mac 的分辨率**：手机上开「流畅」时，守护进程让 helper（`real-bot-rtc display-hold`）把主显示器换成一个像素一个点、形状和现在一样、按点算不小于现在的模式（16 寸 MacBook Pro「更多空间」4112×2658 → 2336×1510），断开后恢复。屏幕共享没有让服务端缩放的标准办法，苹果的 ZRLE 每块都发原始像素再 zlib，传的字节和手机上的 JavaScript 解压都跟像素数成正比；本机实测一次整屏从 7.45 MB 降到 2.82 MB，解码约三分之一。模式按进程设（`kCGConfigureForAppOnly`），helper 不论怎么结束 macOS 都放回原模式，守护进程或 helper 崩了也不会把 Mac 留在低分辨率。代价是这期间 Mac 本机屏幕发虚，所以做成手机上的开关，默认关。
- **打开时不再验 passkey**：屏幕共享每次连接都要 Mac 账户密码，已经是第二道门；终端也有整台 Mac 的权限，没有加。

## 为什么不是别的

- **自己抓屏、注入输入**（ScreenCaptureKit + VideoToolbox + CGEvent）。画面更流畅、更省流量，但要录屏和辅助功能两项 TCC 授权。发布包是 ad-hoc 签名，每次更新身份都变，授权就掉，得回 Mac 前重新给（和 ADR 0034 的钥匙串是同一个问题）；macOS 15 起还会定期在 Mac 上弹录屏确认。更要紧的是锁屏：普通进程看得到锁屏、却解不开，第三方远程桌面都靠装 root 常驻进程才做得到。屏幕共享是系统自己的，锁屏、登录窗口和安全弹窗都能操作，也不要 Deskfolk 的任何授权。
- **WebRTC 栈放进守护进程**（N-API 绑定）。编译态守护进程开着 hardened runtime，库校验拒绝加载 ad-hoc 签名的动态库，ADR 0033 正是在这里卡住的。独立可执行文件静态链接，没有这个问题，崩了也不连累守护进程。
- **只走中继**。中继所有设备合计约 1.5 MB/s，超过不是变慢而是断开；屏幕帧又大又连续，同一网络里白绕一趟服务器也不值。直连时完全不占中继。
- **TURN 兜底**。要再部署一个服务，而且 TURN 的流量同样经过那台服务器；退回中继能达到同样效果，不用新部署。想要也可以自己填。
- **复用终端的 type 3 流事件**。那条路为终端选择了丢字节而不是反压（理由见 remote-protocol.md），RFB 是有状态的字节流，丢一个字节就乱了；它还每帧 base64 一次，限速 160 KB/s。type 9 是二进制、不丢、按确认放行。

## 代价

- 要你在系统设置里打开屏幕共享，它同时在局域网上开了 5900 端口（可以只允许你自己的账户）。
- 经中继时画面慢，Retina 屏全屏刷新要几秒；屏幕共享给第三方客户端的编码比视频流费流量。
- 合盖又没接外接显示器、睡眠、重启后没人登录时连不上：守护进程按用户跑。
- 局域网直连要 macOS 的「本地网络」授权，归在 Deskfolk 名下（`Info.plist` 写了用途说明）；这一项同样受 ad-hoc 签名影响。
- 多了一个约 3 MB 的二进制和一个 MPL-2.0 的前端依赖（noVNC，未修改）。
- 记住的 Mac 密码在手机上（2026-10-03 起按用户要求：连过一次就不再输入）：能读到这台手机配对密钥的人本来就能用终端，多出来的是能登进 Mac 的屏幕、用 sudo。不存在 Mac 或中继上：那样守护进程得替手机完成屏幕共享的认证，两条路都要改。

真机上蜂窝网络直连、真的屏幕共享（ARD 认证、Retina 帧缓冲、中文输入）和 iOS Safari 都还没验收；本地端到端（假 RFB 服务器、Chromium 仿手机，直连和强制中继各一遍）已通过。
