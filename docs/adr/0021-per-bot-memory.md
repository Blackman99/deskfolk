# 记忆按 Bot 归属，Bot 自己写，写满了报错

Bot 每轮只看得到当前会话最近 40 条转录。你在私聊里说过的口径，换个会话它就不知道；纠正过的结论，下次还得再说一遍。唯一能跨会话留下来的是手写的技能和人设，而两者都不是放事实的地方。

做法是给每个 Bot 一张 `memories` 表：一个 subject + 一句结论，启用中的全部进入它每一跳的 system。没有检索、没有相关度排序、没有向量——仓库里既没有 FTS5 也没有任何 embedding 代码，为了这个特性从零建一套检索基础设施，成本远大于「把二十条结论全放进去」。

**Bot 自己用工具写，没有后台蒸馏器。** `remember` / `forget` 两个工具，照 `create_skill` 的样子：只能动自己的行，`bot_id` 和来源都从本轮 turn 上取而不是工具参数，所以 Bot 既不能写进别人的记忆也不能伪造来源。不加 `list_memories`——启用集已经逐字在提示词里，列表工具只会花一跳返回模型已经读得到的东西；这正是和技能的结构性差别，`read_skill` 存在是因为它取的是**不在**提示词里的正文。也不加 `update_memory`：同一个 subject 再 `remember` 一次就是覆盖，这既是纠正路径，也是主要的增长控制。

**写满了直接报 422，不静默淘汰。** 上限压力是唯一能让模型在自己的推理里权衡「什么值得记」的机制——没有任何后台进程知道哪条更该留。错误里点名最久没更新的那条，让它下一跳能直接动手。代价是多花一跳；收益是不会有记忆在你从没见过它存在的情况下消失。因为 upsert 不占新名额，重新确认一条已有结论不会把 Bot 逼到上限。

**不加 `last_used_at`。** 每条记忆每一跳都被注入，所以每条都「被用过」，这个字段无法诚实填写，而且会变成每跳 N 行的写放大。要挑「最该丢的」只能看最久没被**写**过，所以 `updated_at` 就是那个信号。

**渲染在系统提示词最后。** 记忆是变动最频繁的块，而带自动前缀缓存的端点按最长公共前缀命中。放最后，轮次中途一次 `remember` 只作废它自己那一小段；放在系统指令之前会让 3.6K 的规则文本在该轮后续每一跳都失效。同理年龄按周分桶而不是渲染时间戳，否则前缀每天都会变。选取分两步：按最近写入截到预算，再把幸存者按 subject 排序渲染，让文本顺序不随每次写入重排。渲染预算是从计数上限的最坏情况推出来的，比它略高，所以它是一道**永不触发的兜底**，只在日后有人调大参数却没重算时才会静默截断——有测试钉住这个推导。

**删 Bot 一并删掉，归档保留。** 沿用 ADR 0018 对选路结论的判断：记忆装的是用户说过的话，比技能敏感得多，删掉这个 Bot 就该带走它。这让 `memories` 成为第二张在软删 Bot 时被硬删的表。方向是：按 Bot 的**结论**硬删，按 Bot 的**产物**（技能、日程、消息）留存。

**来源不加外键。** `deleteSession` 和 `clearSessionMessages` 会硬删消息，带 FK 的列会让「清空历史」直接抛错。照 `profile_revisions.message_id` 和 `sessions.origin_message_id` 的做法置 NULL：记忆活下来，凭据没了，面板显示「来源已不在」。

**词表的立场收窄了，没有取消。** `CONTEXT.md` 原来在三处把「独立记忆层」列为反面。禁令真正要挡的是自动摘要进人设、语义检索记忆层、后台蒸馏器——这三样这次一样都没做。留在 `_Avoid_` 里的正是它们；「独立记忆层」这个措辞换成了具体的反面清单，并新增了「记忆」词条。

明确不做：检索、后台蒸馏、跨 Bot 共享、分类与重要度、TTL 与定时 GC、把记忆加进判断/选路/建议草稿的载荷、记忆写入的转录条、用户手动新建。撤除的成本也压到最低：渲染只在 `formatMemoryDigest` 一个函数和 `context.ts` 一个调用点，撤掉它们表就静置，数据不丢。
