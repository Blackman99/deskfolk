# 验收检查由守护进程自己跑

[ADR 0029](0029-closing-check.md) 让交付前核一次，[ADR 0031](0031-heard-in-the-live-turn-and-plans-closed-on-evidence.md) 要求「完成要有执行记录」，[ADR 0030](0030-plans-tickets-and-organizer.md) 的整理跳按依据标待验收和已完成。三处判「做完没有」的，都是模型在读 Bot 的收尾和执行记录：Bot 说测过了，要么被信了，要么被一个模型怀疑了，应用自己从来没有亲手核过一次。

2026-09-28 的黄金路径基准给了反例：任务集里每件事都带确定性检查（交付文件在不在、内容对不对、`bun test` 过不过、命令的输出和退出码），脚本在团队离场之后自己跑，45 次运行里它们从没和评判模型吵过架，而且最快、最便宜、最说得清。产品里却没有这样一块：「盯到交付」的依据仍然是模型的意见。

## 现在

**检查是规划的一部分，另存两张表。** `acceptance_checks` 一行一条检查，挂在规划的某一句验收上（按文字对应，`item`），四种：`exists`（文件在且非空）、`contains` / `matches`（文字或正则，可以反过来）、`command`（`/bin/sh -c` 一行，期望退出码，默认 0，可选期望输出）。`acceptance_check_runs` 记每次运行：原因（settle / user / edit）、结果（pass / fail / blocked / error）、一行说明（按应用语言写）和输出末尾。不放进 `tasks.spec`：整理跳每次整份重写要点，塞进去的检查会被冲掉。验收那一句被改写时 `rebindCheckItems` 让检查跟着走；删掉了，检查照跑照算，单列成「对不上验收条目」。改了定义就清掉旧的运行、重置 `first_passed_at`：运行只为它跑时的那个定义作证。

**怎么跑。** 路径和没写目录的命令都相对工作区根，和文件树一致。写入时和运行时各判一次 `classifyPath` / `classifyShell`，越界的写不进来，跑的时候越界记 blocked 不跑。命令在自己的进程组里跑，结束或超时（默认 120 秒，最长 600）整组杀掉，超时走 `wake.awakeTimeout`；环境是终端那份白名单，去掉 `SSH_AUTH_SOCK`，加 `CI=1`、`NO_COLOR=1`、`TERM=dumb`。正则放进 Worker，2 秒超时，文件不超过 1 MB。一个规划同时只跑一次，命令检查整台 Mac 一次一条，一段静默最多 15 分钟；启动时没跑完的记成 error。

**什么时候跑。** 静默段的顺序是：先跑过期的（定义后没跑过，或之后又有轮动过）→ settle 整理 → 跑整理跳刚加的 → 如果整理跳的「做完」只是被没跑过的检查拦住，再补一次只看证据的 settle（这次不收它新写的检查，一段静默最多一次）→ 对账。你新建或改了一条就跑那一条，流程图上随时能跑全部；手动跑的不触发对账。

**谁写。** 你在流程图上增删改；改了整理跳加的那条，它就归你（`source = 'user'`）。整理跳在答案里有一个可选的 `checks` 数组，只能动 `organizer` 来源的，每次最多新加 3 条，一个规划最多 10 条；命令只能是 `commandSeenInPlan` 认得的：这件事里某一轮在同一目录跑成功过，或你在归到这件事的消息里原话写过。这条由 store 执行，不靠提示词，所以 Bot 在转录里写下的一行字换不来一条会被执行的命令。你删掉的定义留墓碑，整理跳加不回来。Bot 没有写检查的工具，只在局面块和 `map.md` 里看得到。

**结果回到循环里。** `TaskDetail.checks` 带着每条的最近一次运行，新表的变更日志发 `('tasks', task_id)`，沿用 `task.upsert`。整理跳读到每条检查的最近结果：有没过的、或定义后还没跑过的，规划就不能被它标成做完（和 `heldOpenBy` 一样留在进行中），对应任务也不能标完成；blocked 和 error 不算依据，写进进展的卡住。你用 `PATCH /v1/tasks/:id/spec` 手动收口不受限。对账（`reconcilePlan`）在有没收口的任务或没过的检查时叫回，叫回的话里带着最多 3 条没过的检查和输出末尾，写明修交付物、不改检查。每一轮的局面块列出这件事的检查和结果。

**防空转。** 上一次叫回之后，必须有进展才再叫：有任务进了待验收或已完成，或者有一条在那次叫回之前就定义好的检查「定义以来第一次通过」；否则说一次「这件事停下了」就不再叫。另有硬上限：你最近一句话之后，叫回次数不超过任务数加检查数。进展只增不减（任务不会自己退回，一个定义只能第一次通过一次），所以不需要比较失败输出的指纹，输出里带时间戳也转不起来。

## 取舍

- **按文字挂到验收，而不是按下标。** 整理跳会调整验收的顺序和措辞；按下标挂，调一次顺序就全挂错。按文字挂，改写时跟着走，真对不上就单列，比悄悄挂错好。
- **命令走 `/bin/sh -c` 和 `classifyShell`。** 和 Bot 的工作区壳是同一条线（[ADR 0005](0005-workspace-shell-convention.md)）：约定加启动前检查，不是囚笼。检查比 Bot 的壳更严的一处是环境：它没人看着跑，不带 `SSH_AUTH_SOCK`，也不带守护进程自己的变量。
- **整理跳只能提升见过的命令。** 让模型自己写命令最省事，但那样一段被 Bot 写进转录、又被整理跳照抄的文字就能让应用在没有批准的情况下执行它。要求「这件事里跑成功过」或「你原话写过」，检查就只是把已经发生过的事固定下来。
- **只挡整理跳，不挡你。** 检查是依据，不是闸门：你知道这条检查写错了，或者决定不要了，照样能收口。
- **一份叫回预算。** 叫回任务和叫回检查共用一个计数，而不是各有一份；两份加起来会让一个卡住的规划叫回更多次，而多出来的那几次什么都改变不了。

## 不做

- 不给 Bot 写或跑检查的工具：Bot 想确认，就用自己的壳跑同一条命令。
- 不让应用替谁收口，也不因为检查没过就把任务退回。
- 不自动批准工作区外的检查；以后可以加一种「你点一下才跑」的区外检查，点那一下就是批准。
- 不做 HTTP 检查（要不要访问网络是另一个决定）。
- 收尾自检不调模型：[ADR 0037](0037-cut-the-core-loop-by-the-benchmark.md) 把它改成确定的规则之后，「这件事有验收检查没过」就是它的第一条规则，不另做一套模型对照。

## 补充（2026-09-29）：衔接一致

第五种检查 `continuity`（衔接一致）是唯一要调模型的一种，管的是多 Bot 协作最容易漏的地方：几个 Bot 各做一部分，每个只审自己那块，合起来的接缝没人看。起因是一件真实的视频活，用户退回的问题全在镜头之间（画风从 3D 跳到 2D、人物面孔和义肢左右变了、门的方位前后矛盾、缺过渡动作），审片的 Bot 一镜一镜看，结构上就看不到；同样的事也发生在几个 Bot 分写的报告章节（术语、人名、数字口径前后不一）、分镜和海报（画风与角色设定漂移）、幻灯片之间。所以它不按视频做，而按「有顺序的几部分」做：部分来自清单命令、通配路径或把一份文档按标题切开；每条接缝取两边的证据（视频抽帧、图片并排、文字取首尾段落），文字另做一次整体口径检查；交给默认模型按规划的规则和一张通用清单逐条作答，只收 JSON；每条接缝和整体都没问题才通过。代码之间的衔接仍由联调或启动命令的检查来管。它守这份 ADR 的原则：Bot 写不了，整理跳只能在这件事交出过的部分或跑成功过的清单命令上提出，ffmpeg 在工作区里跑、环境走白名单，结果挂在同一张流程图上、同样挡整理跳的「做完」。它不是闸门：判断出自模型，所以结论带着证据（对照图或原文片段），你可以推翻。花费单独记一类 `acceptance_check`。第一次在真实成片上跑时，它把首尾帧对齐的接缝误判成「内容重复」，于是提示里写明两侧几乎一样是好事。

## 补充（2026-10-01）：按你的话加的检查

[ADR 0040](0040-agent-kernel-the-job-owns-state.md) 的 P3 让应用自己也提检查，只提一种：你对一件事说的时长、分辨率、画幅或帧率，按固定规则从原话里读出来（和需求台账读数是同一套规则，不调模型），提议成一条量最终成品视频的检查（`measure`，ffprobe 读一次，「约」和只给一个数上下放宽一成，「以上」「以内」只卡一头）。它守这份 ADR 的原则，另加六条：
- **谁写。** 只有应用按你的原话写，来源记为你（`source = 'user'`，整理跳动不了），`origin = 'derived'` 另说它是读出来的。你能确认、能删、能重跑，不能在流程图上编辑它的数：要改就说改成多少，你的话才是它的依据。你删掉或没选的那个数，你那时说过的话不会再把它提出来。一个规划最多 10 条的上限不算它们：每一项最多一条生效的，外加一条提议。
- **只有你的点击能让它成为门禁。** 读出来的数只出一张卡片（`derived_state = 'proposed'`，附确认、改、不要），你再说一次同一个数，卡片带着「你已经说了 N 次」再出一张。门禁（`active`）只由你点「确认」得来。这条是试出来的。第一版由规则判断「这个数是不是在要求」，两轮评审都在找误读。第二版改成「读出来先是提议，同一个数在两句话里说过就生效」，又只让「说成目标的数」（同一小句用「片长」「分辨率」这类词、或前面紧挨「剪成」「改成」）凑两次。两轮对抗评审分别造出 20 条和 30 条错门禁：同一种句式会被同样误读两次（「素材总时长约 20 分钟」「不要剪成 90 秒」「帧率 24 改成 60」「预算控制在 2k」、转述客户的话、前一小句点了镜头、「最长」「打底」这类词）。所以任何让你的话自己生成门禁的规则都不留，读数只管出卡片，读错的代价就只剩一张卡片。F-f 那种情况靠卡片解决：卡片出两次，第二次写着说了两次，107 秒的母带量出来不过，你点一次确认就拦下。
- **提议照样量，但只是信息。** 提议也对上文件、当场量（和门禁一样），结果写在流程图（「待确认 · 没过」「未确认的检查：107.00 秒，你说的是约 2 分钟（待你确认）」）、Bot 的局面块和 `map.md` 里，给你和审查者看；它不拦整理跳的「做完」，不进收尾自检，也不叫回谁。审查者要不要逐条回应，等 P4e。
- **门禁从不自己变。** 生效的检查不会因为你后来说了别的数被改掉、放一边或替换：后来说成目标的不同数只出一张替换卡片（用新的、改、留原来的），旧的照样拦，直到你选；没说成目标的数连替换卡片都不出。你确认时站的那句原话另记下来：之后抹掉说同一个数的别的话不影响它，那句话改归别处也不影响；那句话本身被抹掉，它改回提议并告诉你，不悄悄删掉。
- **对上文件看名字、位置和任务。** 它量的是这件事的最终成品：名字里有 MASTER 这个词的视频先于有 final 的，再其次 `deliverables/` 下的，要整个词；名字点了某一镜、另一版或格式（9x16、30s、竖版、douyin）、片头片尾、预览或代理的不算，footage/、raw/、ref/、素材/、参考/ 下的不算，归在镜头任务或另一版任务下交的也不算；名字的先后只在同一类地方比，`deliverables/` 或这件事自己目录里的先于别处的。新旧按文件第一次被交出的时间算。
- **库里写最近的旧值。** `kind` 的 CHECK 不改（改 CHECK 要重建表，旧版本共用数据目录时会读错，按 ADR 0040 的迁移分类放到最后的收缩阶段）：它记为 `exists`，量什么写在新列 `measure` 里，另有 `quote_id`、`bind_kind`、`bind_glob`、`derived_state`。旧版本读到的是一条检查文件在不在的检查，还没对上文件时是一条没写路径的检查，跑出来算出错，不拦东西。

它不管审查者：审片员对着没过的检查放行时被拦下，要等 P4e 的交付和审查（夹具 F-f 的第二条）。

2026-10-02：引擎 5 级起有了（[ADR 0046](0046-submissions-and-reviews.md)）。提议照旧什么都不拦，交付不拦、放行也不拦，你说过多少次都一样；拦的是另一条规则：你在需求台账里说过两次以上的要求是必查条目，和生产者同一个模型的审查对它判 pass，而它的原话上没有一条量出来通过的检查时，这次放行等你——审片员对着 107 秒的母带 `review(approve)` 被拒，理由和问你的卡片里都写着这条提议量到的「107.00 秒，要时长 108–132 秒」；你在卡片上确认这条检查，它成为门禁，量出来不过，母带退回给导演。
