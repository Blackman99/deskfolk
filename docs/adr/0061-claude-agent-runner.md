# Claude Agent：由你本机的 Claude Code 跑 Bot / Claude Agent: Bots run by your own Claude Code

Status: implemented 2026-10-05. A per-Bot choice, at every engine level (no level gates it: an older build ignores the column and runs the Bot on its endpoint). Builds on [ADR 0040](0040-agent-kernel-the-job-owns-state.md) (the kernel), [ADR 0044](0044-delegation-and-end-contract.md) (delegation and endings), [ADR 0046](0046-submissions-and-reviews.md) (hand-overs and reviews) and [ADR 0058](0058-the-app-asks-only-when-it-needs-you.md) (asking).

2026-10-05，你想在 Deskfolk 里用上自己的 Claude 订阅。应用只认 OpenAI 兼容的 `/chat/completions` 端点和端点密钥；Claude 订阅不是密钥，是 claude.ai 的登录，Anthropic 只让它用在 Claude Code 和自家应用里。直接拿订阅的令牌去调接口（一些第三方工具、代理就是这么做的）违反条款，也被 Anthropic 一直在拦。

On 2026-10-05 you wanted Deskfolk to use your Claude subscription. The app only speaks OpenAI-compatible `/chat/completions` with an endpoint key; a Claude subscription is not a key but a claude.ai sign-in, which Anthropic keeps to Claude Code and its own apps. Calling the API with a subscription's token (as some third-party tools and proxies do) breaks the terms, and Anthropic actively blocks it.

条款给的路是 Claude Code 本身：用户用自己的订阅登录原版的 Claude Code，产品去运行它。于是这里不是「再加一种端点」，而是让一个 Bot 的每一轮由你本机装好、登录好的 Claude Code 来跑，用它自己的循环和工具干活，应用把它包在每一轮都有的东西里：工作区边界和你的批准、Stop 和停住、副作用账、收尾契约、交付和审查。

The terms' way in is Claude Code itself: users sign in to the unmodified Claude Code with their own subscription, and a product runs it. So this is not one more endpoint: a Bot's turns are run by the Claude Code you installed and signed in to, with its own loop and tools, wrapped in what every turn has — the workspace boundary and your approvals, Stop and holds, the effect ledger, the end contract, hand-overs and reviews.

## 合规边界 / The compliance boundary

条款原文（code.claude.com/docs/en/legal-and-compliance，2026-10-05 读）： / The terms as read on 2026-10-05:

- "Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow."
- "Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code …"
- Running Claude Code in a product: "The Claude Code binary must not be modified … customers may not remove, disable, or restrict any authentication method built into it … Each end user must authenticate with their own Anthropic API key, Claude subscription plan credentials, or 3P inference provider credential."
- "Advertised usage limits for Pro and Max plans assume ordinary, individual usage of Claude Code and the Agent SDK."
- Agent SDK overview: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK."

应用因此只做这些：运行你自己装的、原版的 `claude`（通过 Agent SDK，`pathToClaudeCodeExecutable` 指向它）；不提供任何 Claude 登录，不读、不存、不转发令牌和钥匙串，登录只在你的终端里由 Claude Code 自己完成；环境变量原样传过去（`ANTHROPIC_*`、`CLAUDE_CODE_OAUTH_TOKEN` 都不碰），只去掉嵌套会话标记和应用自己的 `REAL_BOT_*`，环境里没有代理变量时补上系统代理（决定 10）；设置里明确写出它用的是哪种凭据（订阅、长期令牌、API key、第三方平台）。界面上叫「Claude Agent」，正文只说「由你本机的 Claude Code 运行」，不拿 Claude Code 当功能名（Agent SDK 的品牌要求）。应用自己的判断（读句、归档、谁来接话、收尾自检）照旧用端点：Claude Code 从不被当成应用自己循环的补全通道。

So the app only does this: it runs the unmodified `claude` you installed, through the Agent SDK with `pathToClaudeCodeExecutable` pointing at it; it offers no Claude sign-in and never reads, stores or forwards tokens or keychain items — signing in happens in your terminal, in Claude Code; the environment passes through untouched (`ANTHROPIC_*` and `CLAUDE_CODE_OAUTH_TOKEN` included), less the nested-session markers and the app's own `REAL_BOT_*`, with the system proxy added when the environment names none (decision 10); Settings says which credential it uses. The UI calls it "Claude Agent" and only says in plain text that it runs your own Claude Code (the Agent SDK's branding rules). The app's own judgements (reading lines, filing, who joins in, the closing check) still run on endpoints: Claude Code is never a completion pipe for the app's loop.

没采纳的更保守做法 / A more conservative option not taken: SDK 概览那句「未经批准不得在产品里提供 claude.ai 登录或用量额度」也可以读得更严：发行版只允许 API key 一类凭据，订阅凭据等 Anthropic 确认后再放开。你决定按 Bot 手动开启、随发行版发出；要改成那种做法，在 runner 开跑前按 `accountInfo()` 的凭据拒绝即可，其余不变。 / The SDK note could be read more strictly: release builds take API-key credentials only until Anthropic approves subscriptions. You chose to ship it as a per-Bot opt-in; switching to that reading is a refusal on the credential before the session starts, nothing else.

## 决定 / Decisions

1. **运行方式 / The runner.** `bots.runner`（空：应用自己的循环；`claude_code`：Claude Agent），`bots.agent_model`（别名或完整 id，空即 Claude Code 默认）、`bots.agent_effort`（low…max，空即默认）。端点钉住的模型不动：应用自己关于这个 Bot 的判断（比如群里要不要接话，`targetFor`）照旧跑在端点上。只有你能改运行方式：一个 Bot 改自己或别的 Bot 的运行方式被拒（403），因为它决定这些轮花的是谁的账号；`update_profile` 没有这几个参数。 / `bots.runner` (empty: the app's loop; `claude_code`: Claude Agent), `agent_model`, `agent_effort`. The endpoint pin is untouched, so the app's own calls about the Bot still run on an endpoint. Only you may change the runner (a Bot is refused with 403): it decides whose account the turns spend.

2. **找到你的 Claude Code / Finding your Claude Code** (`apps/daemon/src/claude-code/`)。顺序：设置里填的路径 → 守护进程的 PATH → 常见安装位置（`~/.local/bin`、`~/.claude/local`、`/opt/homebrew/bin`、`/usr/local/bin`、npm 全局目录…）→ 登录 shell（`$SHELL -lic 'command -v claude'`，3 秒）。从 Finder 打开的应用只有 launchd 的 PATH，前两步常常找不到。状态只问它自己：`claude --version`、`claude auth status`；60 秒缓存，开跑前读一次。`GET/POST/PUT /v1/runtime/claude-code*` 只在本机（`/v1/runtime*` 不过中继）。Windows 上应用拿得到你的整条 PATH，`claude` 可能是原生安装的 `claude.exe`，也可能是 npm 的 `claude.cmd`（按 PATHEXT 都找得到），常见位置是 `%USERPROFILE%\.local\bin\claude.exe` 和 `%APPDATA%\npm\claude.cmd`，没有登录 shell 可问；`claude.cmd` 是批处理，只能经 `cmd.exe` 跑，参数按 MCP 服务器 `npx` 那套转义（SDK 只在命令行上放几个短参数，系统提示和工具都走 stdin），不弹控制台窗口。 / Order: your setting, the daemon's PATH, the usual install places, your login shell. Its status comes only from `claude --version` and `claude auth status`, cached a minute; the routes are local-only. On Windows the app has your whole PATH; `claude` is the native `claude.exe` or npm's `claude.cmd` (PATHEXT finds either), the usual places are `%USERPROFILE%\.local\bin\claude.exe` and `%APPDATA%\npm\claude.cmd`, and there is no login shell. A `claude.cmd` is a batch file and runs only through `cmd.exe`, its arguments escaped as for an MCP server's `npx` (the SDK puts only a few short flags on the command line; the system prompt and tools go over stdin), with no console window.

3. **一轮一个会话 / One session per turn.** `query()`（动态加载，打包的守护进程启动时不碰它）：`cwd` 是本轮工作目录（还没归到一件事的 desk 段是工作区根，归档后不换进程，用一行应用提示告诉它新目录）；`additionalDirectories` 是工作区；`settingSources: []`（SDK 文档说的隔离模式：你 `~/.claude` 里的设置、hooks、插件、CLAUDE.md 不进 Bot 的会话）；`strictMcpConfig`；`verbatimPrompts`（转录里的 `/命令`、`@路径` 不会被展开）；`permissionMode: default`；只开 Read、Write、Edit、NotebookEdit、Glob、Grep、Bash、WebFetch、WebSearch、Agent、TodoWrite，关掉 AskUserQuestion；关掉后台任务（`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`）；`maxTurns: 200`。系统提示是 Claude Code 自己的，后面加：人设、技能、一段映射说明（应用的工具都在 `mcp__deskfolk__` 下，读写和命令用 Claude Code 自己的工具和绝对路径，工作区根和当前目录，不碰 Claude Code 自己的设置和凭据），然后是应用给每个 Bot 的系统指令原文、本轮 MCP、记忆。第一条消息是局面块和转录窗口（自己的话标【你】，图片原样带上，工作目录写成主机路径——Claude Code 的文件工具只认绝对路径），连同改道带过来的话和中断旗。 / `query()`, loaded only when such a turn runs. The work dir as `cwd` (a desk segment starts at the workspace root and is told its new dir once it binds a job, without a respawn); the SDK's isolation mode for settings; strict MCP config; verbatim prompts; default permission mode; a short tool list without AskUserQuestion; no background tasks; 200 turns at most. Claude Code's own system prompt, plus the profile, skills, a mapping preface, the app's system text unchanged, the turn's MCP and memories. The first message is the situation block and the transcript window, images included, the work dir as a host path (Claude Code's file tools take absolute paths only).

4. **边界照旧 / The same boundary.** `PreToolUse` 钩子对 Claude Code 自己的每次调用（子任务的也一样）按应用的规则判：工作区内的读写和命令直接跑；出界的读、写和越界命令（`classifyPath` / `classifyShell`）成为一张和应用自己的工具一样的批准卡（`outside-read` / `outside-write` / `unconstrained-shell`，你「总是允许」过的照样放行）；递归搜家目录照样拒；顶层目录都不存在的路径（把工作区路径写成了 `/work/…`）直接拒掉并说明工作区在哪，不为一个笔误出卡——Windows 上是没有盘符的文件路径（`/work/…`、`/c/Users/…`），它打开的是哪个文件要看谁来读；名单外的工具、后台运行、远程或 worktree 隔离的子任务拒掉；Claude Code 自己的设置和凭据（`~/.claude`、`~/.claude.json`、钥匙串、`security find-*-password`）一律拒，不出卡；Windows 上按 Windows 的路径规则判（不分大小写、带盘符，`%USERPROFILE%`、`$env:USERPROFILE` 和 Git Bash 的 `/c/…` 写法都算），Claude Code 的 Bash 在那里是 Git Bash，命令按 Git Bash 读。有效果的调用先过应用的生效闸（`beforeEffect`：desk 段先归到一件事、停住时拒、工作目录记为已用、写进副作用账）。批准卡由 `canUseTool` 接：和应用自己的工具同一张卡（`openApprovalCard`），批准、拒绝、Stop 时作废都一样。 / A `PreToolUse` hook applies the app's rules to every Claude Code call, subagents' included: inside runs; outside becomes the same approval card the app's own tools raise (always-allow rules count); the recursive-search refusal holds; a path under a missing top-level folder (a workspace path written as `/work/…`) is refused with where the workspace is, rather than carded — on Windows, a file path with no drive (`/work/…`, `/c/Users/…`), whose target depends on who reads it; unlisted tools, background runs and isolated subagents are refused; Claude Code's own credentials are refused outright. On Windows the same rules follow Windows' path rules (any case, drives, Git Bash's `/c/…` for the credential check), and Claude Code's Bash — Git Bash there — is read as Git Bash reads it. Effects pass the app's effect gate first. `canUseTool` raises the card through the shared `openApprovalCard`.

5. **应用的协作工具 / The app's tools.** 每个 Bot 平常有的工具（读写文件和命令那五个除外，Claude Code 有自己的），连同你配的 MCP 服务器的工具，以进程内 MCP 服务器 `deskfolk` 交给 Claude Code，标成始终加载（否则会被藏进工具搜索）；每次调用都走 `executeTools`，所以 `end_turn`、`submit`、`review`、`delegate`、`ask_user`、`check_back`、`plan_items`、记忆、技能、批注的意思和别的 Bot 一样。批准卡、提问和这些调用排成一队一个一个来（一轮只有一个批准位、一个提问位）。提问只走 `ask_user`：Bot↔Bot 私聊不能问你、只是请你点头的提问会被退回，这些规则照旧。审图用 Claude Code 自己的 Read：`PostToolUse` 把它读的图记成「看过」，审查通过图片项时照认。子任务只能用不产生效果的应用工具，不能替 Bot 发言、收尾、交付。 / The tools every Bot has (less the five file and shell ones), with your MCP servers', as the in-process `deskfolk` MCP server, always loaded; each call goes through `executeTools`, so endings, hand-overs, reviews and delegation mean what they mean for any Bot. Cards, questions and these calls go one at a time. Questions go through `ask_user` only. Claude Code's own Read of a picture is recorded as seen. Subagents get only the app's no-effect tools.

6. **收尾 / Endings.** 一轮里最后一条不调工具的回复，走和应用自己循环同一条收尾路径（`settleClosingReply`，从 `runTurn` 里搬出来，两边共用）：没有新活的读法、收尾自检、交出引用的文件、收尾契约、发出、叫醒被点名的人。被退回的那句作为下一条用户消息送回同一个会话。一个工具结束了这一段（`end_turn` 被接受、`work_on` 并入或排队、`delegate` 等回复）：打断会话，按应用的方式静默结束；之后 Claude Code 照例还会给一个结果，丢掉。中途有人找它：在一批工具调用之后，用 `PostToolBatch` 的补充上下文告诉它（和应用的收件一样逐条编号）。 / The last reply that calls no tool goes down the same path as the app's loop (`settleClosingReply`, moved out of `runTurn` and shared); a bounce comes back as the next user message in the same session. A tool that ends the segment interrupts the session; the result Claude Code still sends is dropped. Lines that come in mid-turn reach it after a batch of calls, numbered as in the app's inbox.

7. **记录 / Records.** 每轮一行选路（端点为空、模型为 Claude 的、`reason_code` 为 `claude_code`，不进 Bot 默认模型的推断）；花费按会话的累计用量分模型记增量（端点名「Claude Agent」，价钱只写估算——订阅不按 token 收费）；命令记进 `turn_runs`（收尾自检拿它核对「测试通过」这类说法）；写的文件记进本轮写入，命令留下的文件按工作目录前后对比记；有效果的调用记进副作用账；每条助手消息算一跳。Claude Code 进程单独一个进程组、登记在 `live_procs`：Stop 能结束整组，守护进程崩了下次启动也会清掉。Windows 没有进程组：停下时用 `taskkill /T` 结束整棵进程树，SDK 关会话时对它调的 kill 也改走这里——只结束 `claude`（或包着它的 `cmd.exe`）一个，它起的命令会留下来。Windows 也没有信号，所以那里每次停下都是 `/F` 强制结束：和原来强制结束 `claude` 一个一样硬，只是不再落下它起的进程。 / A route row per turn (no endpoint, `reason_code` `claude_code`); spend as per-model deltas of the session's cumulative usage, priced as an estimate; commands in `turn_runs`; written files in the turn's writes; effects in the ledger; one hop per assistant message. Claude Code runs in its own process group, on record for Stop and for the next boot after a crash. Windows has no groups: a stop walks the tree with `taskkill /T`, and so does the kill the SDK sends when it closes a session — stopping `claude` (or the `cmd.exe` around it) alone would leave its commands running. Nor has it signals, so every stop there is a forced `/F` kill: as hard as killing `claude` alone already was, without leaving what it started behind.

8. **失败 / Failures.** 新的失败类型：没找到 Claude Code、没通过认证（`auth status` 说没登录，或请求被拒：带上 Claude Code 自己的那句报错）、用量额度用完（写明什么时候重置；只有请求真被拦下才算——开了额外用量时 Claude Code 越过额度接着跑，那一轮照常）、Claude Code 中途退出（同样带上它的报错）。前三种只有你能解决，监督器不替你自动重试；最后一种算应用这边的问题。步数用完记作「卡住了」。请求失败时 Claude Code 照样给一个 `success` 结果，只是 `is_error` 为真、正文是它的报错：那是失败，不当回复发出去；它中途重试（`api_retry`）只是消息，刷新登录后常常就过了。 / New kinds: Claude Code missing, unable to authenticate (signed out per `auth status`, or its requests refused, with Claude Code's own error line), usage limit (with when it resets; only when a request was really stopped — with extra usage on, Claude Code carries on past the plan's limit and the turn goes on), exited mid-turn (also with its line). The first three only you can clear, so the supervisor does not retry them. A failed request still ends in a `success` result with `is_error` set and the error as its text: a failure, never posted as a reply; an `api_retry` is only news, as a refreshed sign-in often gets through.

9. **打包 / Packaging.** `@anthropic-ai/claude-agent-sdk` 钉在 0.3.289（对应 Claude Code 2.1.289），它按平台带的约 230 MB Claude Code 程序用 pnpm `overrides` 去掉（pnpm 12 不认 `ignoredOptionalDependencies`），永远用你自己装的 `claude`。SDK 是 Anthropic 的专有许可，随发行版分发，见 THIRD_PARTY_NOTICES。 / The SDK is pinned; its per-platform Claude Code packages are dropped with pnpm overrides, and your own `claude` is always the one run. The SDK is under Anthropic's own terms, shipped in releases, see THIRD_PARTY_NOTICES.

10. **网络 / The network.** 守护进程环境里的 `HTTPS_PROXY` / `ALL_PROXY` 原样传给 Claude Code（`NO_PROXY` 能把它要连的主机排除）；一个都没有时，把系统的 HTTPS 代理（macOS 上 `scutil --proxy` 读到的「安全网页代理」；Windows 上当前用户的 Internet 设置，即 设置 › 网络和 Internet › 代理，用 `reg query` 读；浏览器和代理软件的「系统代理」开关改的就是它们）作为 `HTTPS_PROXY` 交给它，再补一个只含本机地址的 `NO_PROXY`。从终端起的守护进程带着这些变量；应用从访达、开始菜单或开机启动时一个都没有，而在只能经代理连上 Anthropic 的网络里，系统设置是唯一的线索——桌面端的更新检查也是这么回落的（`apps/desktop/src-tauri/src/updates.rs`，这里的两套解析都是从那里搬来的；Windows 上环境变量名不分大小写，照 Windows 的规则读）。只设 `HTTPS_PROXY`：Bot 自己 `curl http://localhost:…` 照样直连。设置卡片的「网络」一行和开跑用的是同一份状态，写明直连还是经哪个代理、来自环境变量还是系统，代理里的用户名密码遮掉。`ANTHROPIC_BASE_URL` 指向本机时不补。 / Claude Code's requests take the daemon's `HTTPS_PROXY` / `ALL_PROXY` as they are (`NO_PROXY` can take its host out); with none, the system's HTTPS proxy (`scutil --proxy`'s secure web proxy on macOS; on Windows the current user's Internet Settings, Settings › Network & internet › Proxy, read with `reg query` — what browsers and proxy apps' "system proxy" switch use) is handed to it as `HTTPS_PROXY`, with a local-only `NO_PROXY`. A daemon started from a terminal carries the variables; the app started from Finder, the Start menu or at login carries none, and on a network that reaches Anthropic only through a proxy the system setting is the only clue — the desktop updater falls back the same way (both parsers are ported from `updates.rs`; on Windows variable names are read case-insensitively, as Windows does). Only `HTTPS_PROXY` is set, so a Bot's `curl http://localhost:…` stays direct. The card's Network row comes from the same status the turn starts from: direct or which proxy, from the environment or the system, credentials masked. Nothing is added when `ANTHROPIC_BASE_URL` is a local address.

## 取舍 / Trade-offs

- 隔离模式意味着你 `~/.claude/settings.json` 里的东西（权限规则、hooks、`apiKeyHelper`、环境变量）不进 Bot 的会话；钥匙串里的订阅登录、环境里的 API key 照样用。写在那里 `env` 里的 `HTTPS_PROXY` 也进不来，系统代理的回落兜住常见的情况。加载你的设置（`settingSources: ["user"]`）能把它们带进来，但你的 hooks 和全局 CLAUDE.md 也会跑进 Bot 的每一轮，所以没这么做。 / Isolation leaves your `~/.claude` settings out, `apiKeyHelper` included; the keychain sign-in and an API key in the environment still work. An `HTTPS_PROXY` in that file's `env` stays out too; the system-proxy fallback covers the usual case. Loading your settings (`settingSources: ["user"]`) would bring them in, along with your hooks and global CLAUDE.md in every Bot turn, so it is not done.
- 一轮一个新会话：Claude Code 上一轮读过什么、跑过什么，这一轮只从转录里知道，和应用自己的 Bot 一样。 / A fresh session each turn: what Claude Code read or ran last turn is known only through the transcript, as for any Bot.
- SDK 钉版本，你的 `claude` 每天自动更新：设置卡片在你的版本低于 SDK 时提醒，SDK 随发行版跟上。 / The SDK is pinned while your `claude` updates itself; the card warns when yours is older.

## 实测 / Measured

2026-10-05，在这台 Mac（Claude Code 2.1.289，Pro 订阅）上不发提示词起了一个带全部选项的会话：37 个应用工具全部转成功、`deskfolk` MCP 已连接 37 个工具、钩子已生效、凭据是 Claude Pro 订阅、可用模型有 default、opus、fable、sonnet、haiku。环境里放一个 API key，`accountInfo()` 立刻变成 `apiKeySource: ANTHROPIC_API_KEY`——这就是设置卡片要写明凭据的原因。

On 2026-10-05, on this Mac (Claude Code 2.1.289, Pro plan), a session with every option started without a prompt: all 37 app tools converted, the `deskfolk` MCP server connected with 37 tools, hooks applied, the credential a Claude Pro subscription. With an API key in the environment, `accountInfo()` turned to `apiKeySource: ANTHROPIC_API_KEY` — why the card says which credential is in use.

同一天发了真提示词（haiku、低强度；守护进程在干净环境里起，和从访达启动一样没有代理变量；应用自己的读句和归档用假端点）。不发提示词的检查读的是本地记下的登录，并不验证令牌：第一条真提示词就全部被拒（`403 Request not allowed`，单独跑 `claude -p` 也一样），带上系统代理就通——于是有了决定 10。之后一句话的回答、工作区内写文件、读 `/etc/hosts`（出批准卡、放行）、`ask_user`（出提问卡、作答）、跑 `sleep 40` 时按 Stop（整个进程组结束，`live_procs` 清空）都通过，选路、按模型的花费增量和 `turn_runs` 都有记录。第一次跑时，第一条消息里的工作目录写的是相对工作区的路径，haiku 拿它当成了 `/work/…`，还写过 `/hello.txt`，各出了一张没有意义的批准卡；改成主机路径、并把「顶层目录不存在的路径」直接拒掉并说明工作区在哪之后，同样的提示一次写对。一个会话开头大约 5 万 token 的输入（Claude Code 自己的系统提示、47 个工具、应用的系统指令），之后大多读缓存。

The same day, real prompts (haiku, low effort; the daemon started in a clean environment with no proxy variables, as from Finder; the app's own readings on a fake endpoint). The no-prompt checks read the sign-in Claude Code has on record and never test the token: the first real prompt was refused (`403 Request not allowed`, and so was a bare `claude -p`), and went through with the system proxy — hence decision 10. After that a one-line answer, a write inside the workspace, reading `/etc/hosts` (approval card, allowed), `ask_user` (question card, answered) and Stop during `sleep 40` (the whole process group ended, `live_procs` empty) all passed, with route rows, per-model spend deltas and `turn_runs` recorded. On the first run the work dir in the first message was workspace-relative, and haiku took it for `/work/…` and also tried `/hello.txt`, each raising a pointless approval card; with host paths in the message and a path under a missing top-level folder refused with where the workspace is, the same prompt wrote the right file at once. A session opens on about 50k input tokens (Claude Code's own system prompt, 47 tools, the app's system text), mostly cache reads after that.

## 缺口 / Not done

- 命令的输出不是边跑边推，命令结束后才有结果。 / Command output arrives when the command ends, not as it runs.
- 不跨轮续接 Claude Code 的会话。 / No resuming a Claude Code session across turns.
- 还没在真的 Windows 电脑上跑过。Windows 的路径与凭据规则、代理的解析、`claude.cmd` 的启动方式、停下时改走结束进程树的那层包装，都只在 Mac 上用模拟的 Windows 主机或假的子进程测过；真机上经 SDK 启动 `claude.exe`、`taskkill` 的时序、中文系统里 `reg.exe` 的输出、Git Bash 在不在（Claude Code 在 Windows 上要它），都还没验证。PAC 文件和只开 SOCKS 的代理不认（和更新检查一样）。 / Not run on a real Windows PC yet. The Windows path and credential rules, the proxy parsers, how `claude.cmd` is started and the wrapper that turns every kill into a tree kill are tested only on a Mac, against a fake Windows host or a fake child; starting `claude.exe` through the SDK, `taskkill`'s timing, `reg.exe`'s output on a Chinese-locale system and whether Git Bash is there (Claude Code needs it on Windows) are not verified. A PAC file or a SOCKS-only proxy is not followed, as in the updater.
- 应用的步数节奏（每 40 跳问一次进展、160 跳后收工具）没有搬过来，只有 200 步上限。 / The app's hop pacing is not applied; only the 200-turn ceiling is.
- desk 段在归到一件事之前的第一次写入，落在它当时的当前目录（工作区根）；归档后它可能在工作目录里再写一份。写在哪由 Bot 决定，和应用自己的循环一样，没有拦。 / A desk segment's first write lands in its directory at the time (the workspace root), before the work belongs to a job; once bound, it may write the file again in the work dir. Where to write is the Bot's call, as in the app's loop.
