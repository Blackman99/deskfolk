# 由应用整理规划和任务，产物按任务归目录，不再按时钟切事

[ADR 0028](0028-job-brief-check-back-and-clarification.md) 让每一轮看得到这件事最初的要求，[ADR 0029](0029-closing-check.md) 在交付前核一次。真实群组（几个 Bot 做影视分镜）暴露了它们没碰到的三样东西：

- **一件事的边界靠时钟。** 一个会话静默六小时后的下一轮另开一件事。用户第二天早上问一句「怎么样了」，这句就成了一件新事的「最初的要求」，Bot 拿着「怎么样了」当目标。
- **目标只有一句原文。** 用户随时会换目标、改要求、加口径，自己也说不清目标是什么；一句 brief 记不下这些，也不该由用户去维护一份目标。Bot 参与时该自动知道现在在做哪件事、之前遇到过没有、这类事定下来的流程是什么、规则是什么、怎么算做完。
- **产物散落。** `work/<日期>-<触发>-<id>/` 只区分「哪次触发」，Bot 随手起 `production/sop3_full_cut/shot_…` 这种路径；一件事有哪些任务、每个任务落地到哪、产物是哪些，没有地方能看。

## 现在

**规划（plan）。** `tasks` 表沿用（历史名），加 `kind` / `spec`（JSON 要点）/ `status`（active / done / parked）/ `spec_updated_at` / `routine_id`。要点是类别、目标、验收、规则、流程与分工、进展、状态；`brief` 仍是开头那句原文。每改一版记进 `task_spec_revisions`（哪条消息或哪一轮引起的，或用户改的）。一个会话同时只有一个当前规划（`closed_at IS NULL AND routine_id IS NULL`）；换事时旧的 parked，resume 时接回来。

**任务（ticket）。** 新表 `tickets`：序号、标题、说明、状态（todo / doing / review / done / parked）、worker（观察到的记录）、目录 `<规划目录>/<NN>-<slug>/`。`turns.ticket_id`、`messages.ticket_id`、`check_backs.ticket_id` 记轮次和消息归哪个任务；产物由消息的 `ticket_id` + attachments 推导，不搬文件。

**整理跳（organizer）。** 无工具短调用，默认端点的默认模型。用户消息进会话之后、开轮之前跑一次：判 continue / new / resume，更新要点和任务（已有任务按 id 引用，新任务 `new-N`，不能删），标出这条消息说的是哪个任务，把 `task_id` / `ticket_id` 盖到消息上；`resolveTurnTask` 认这个盖章，所以点名、判断下场、分叉开出的轮都落在同一处。规划的活轮全部结束、静 30 秒后再跑一次 settle：把交出的文件归到任务、更新状态和进展。失败即不改（没配默认模型、端点拒绝、超时、答得不成形、库拒绝），轮照开。花费记新种类 `organize`（决策路由，不归 Bot）。

**先例。** 同类别最近三个已完成规划的目标、流程、规则、结局压成几行进局面，整个名册查；类别标签由整理跳打，能对上已有的就原样用。

**产物归属。** 新规划目录 `work/<slug>-<id4>/`（去掉日期前缀；旧目录不动），任务目录 `NN-<slug>/`。壳默认 cwd、`tool-results/`、`scratch/` 和没点名路径的交付物都落本轮任务目录（没有任务时落规划目录）。`isReservedTaskPath` 两层都认。

**镜像文件。** 每次整理或用户改过要点后，守护进程用 `atomicWrite` 重写 `<规划目录>/map.md`（要点 + 任务索引）和 `<任务目录>/ticket.md`。保留名，不算产物；Bot 可读不可改不可交出。

**局面块与提示词。** 每一轮的局面有 `规划 / 验收 / 规则 / 流程与分工 / 进展 / 任务清单 / 本轮任务 / 先例 / 已交出 / 经过` 和 `本轮任务目录（规划目录）`；还没整理出要点时退回「最初的要求」。判断和输入建议的载荷 `job` 改成 `plan`，判断多看 `tickets` 和 `message_ticket`。收尾自检先对照本轮任务的要点，再对照规划的验收和规则，最后才是 brief。

**日程。** 每条日程一个常驻规划（`tasks.routine_id`，不占当前规划），每次到点 `createTicket` 一个 `NN-<日期>` 再开轮，不调模型。

**接口与信使。** `GET /v1/tasks/:id`（整个规划）、`/tickets`、`/spec-revisions`，`PATCH /v1/tasks/:id/spec`（整份要点 + `if_revision`）、`PATCH /v1/tickets/:id`；变更日志发 `task.upsert` / `task.removed` / `ticket.upsert` / `ticket.removed`。流程图标题读目标，下面是可折叠可编辑的要点面板（`PlanSpecPanel.svelte`），旁边是任务栏（`TicketList.svelte`），卡片带任务序号，点任务点亮它的卡片；板内文件预览删掉，文件走宿主的预览。

**去掉。** 六小时静默切事、`TASK_QUIET_MS`、`joinableTask`、`newTask`、带日期的目录名（新规划）、板内 `TraceOutput`。

## 取舍

- **由应用整理，不由用户定义，也不让 Bot 改。** 用户随时换目标、说不清目标；Bot 改自己的任务表会把「做了什么」写成「该做什么」。整理跳是唯一写要点和任务的地方，用户可以在流程图里改，改动记成一版。
- **先整理再开轮，而不是并行。** 轮晚几秒开，换来它开在正确的规划和任务里、局面里已有这条消息的归属。消息本身立刻可见，只有 Bot 在等。
- **默认模型。** 和选路、复盘、收尾自检一样，避免递归，也不需要强模型。
- **失败即不改。** 整理跳是提醒和归档，不是闸门：任何失败都不拦轮，规划照旧。
- **settle 去抖 30 秒。** 一次 fan-out 的几轮先后结束，归档一次而不是每轮一次。
- **镜像文件建目录。** 要点一存在就有 `map.md`，Bot 用 `read_file` 就能看整件事；代价是规划目录在没有产物时也存在。
- **routine 常驻规划、每次到点新开任务。** 日程是重复工作，一次到点一个任务能独立看落地情况，又不让每天一次的汇总把会话的当前规划顶掉。
- **resume 只认本会话最近的规划。** 跨会话 resume 会把别人的规划接进来；先例已经把别处的经验带进局面。
- **每次整理最多开 10 个新任务、一个规划最多 40 个。** 超过就是整理跳在重写规划，不是在归档。

## 不做

- 不做调度器分派、DAG、优先级、截止日期：任务的 worker 是记录，不是指派。
- 不做语义检索先例：按类别标签查最近三个已完成的。
- 不搬文件：产物归属由消息的 `ticket_id` 推导，目录只是默认落点。
- 不让整理跳发言、调工具或删任务。
