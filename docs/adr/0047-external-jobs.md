# 外部作业：守护进程代为轮询、按参数去重、分件锁 / External jobs: the daemon polls, submits are deduplicated, parts are held

Status: implemented at engine level 6 (`ENGINE_LEVELS.jobs`), ADR 0040's P4d. Like level 5, level 6 is experimental and opt-in only: no build raises a data folder past `ENGINE_LEVEL_BY_DEFAULT` (4) on its own; a developer's opt-in (`apps/daemon/scripts/engine-level.ts --accept-older-app`) takes it to this build's top level, or with `--level 5` (`level` on `POST /v1/capabilities/raise`) only as far as asked — level 5 can be tried without level 6.

[ADR 0040](0040-agent-kernel-the-job-owns-state.md) §5.5 和 §3.3 要让「等一个渲染」不再花 Bot 的轮次。在这之前，视频生成是 MCP 服务器上 `submit_video` 提交、`check_video` 查询的一对工具：每次查询都是 Bot 的一轮、一次模型调用，只为得知「还在渲」；视频导演在两个私聊里同时等同一个作业，一个查了 17 次、一个查了 7 次（09-28，`job-double-polling.test.ts`）；两条 Bot↔Bot 私聊把 C07、C08 各重渲了一遍，服务器收了四次钱（09-27，事故 F-c）。线上库里 `check_video` 调用 102 次，`submit_video` 只有 34 次。

ADR 0040 §5.5 and §3.3 want waiting on a render to stop costing Bots their turns. Before this, video generation was a media server's `submit_video` / `check_video` pair over MCP: every check was a Bot's turn and a model call, made to learn that the render was still running; 视频导演 waited on one job from two directs at once and checked 17 and 7 times (09-28, `job-double-polling.test.ts`); two Bot↔Bot directs re-rendered C07 and C08 once each and the server billed four renders for two shots (09-27, incident F-c). The live database counts 102 `check_video` calls against 34 `submit_video`.

## 决定 / Decisions

1. **版本边界 / Version boundary.** `ENGINE_LEVELS.jobs = 6`，`SCHEMA_LEVEL = 6`，启用时兼容地板抬到 6。6 级的库里登记着媒体服务器接下的作业（`external_jobs`），由守护进程轮询、完成时叫醒等它的 Bot；5 级的二进制会让每个 Bot 再自己去轮询、把同一个渲染交两次、作业完成时也不叫任何人——而 Bot 在 6 级被拒掉的回看又不会替它们等。表在打开库时建（放在处理草稿遗留表之后，所以总是这一版的），带 `task_id` 和 `state`，规划休眠读的就是这两列。 / `ENGINE_LEVELS.jobs = 6`, `SCHEMA_LEVEL = 6`, and the floor goes to 6 when it turns on. A level-6 database keeps the renders a media server accepted (`external_jobs`), polled by the daemon, which wakes the Bots waiting on them; a level-5 binary would have every Bot poll the server itself again, submit the same render twice, and wake nobody when a job finishes — while the check-backs level 6 turned away are not there to wait instead. The table is made at open, after a draft's table of that name is set aside, so it is always this build's; it carries `task_id` and `state`, the columns plan dormancy reads.
2. **按名字认一对工具 / The pair, by name.** 同一个 MCP 服务器上的 `submit_<x>` 和 `check_<x>` 是一对（`engine/job-adapter.ts`），所以 westlake-cpa 的 `submit_video` / `check_video` 和任何同形状的服务器一样处理；查询工具把作业 id 放在哪个参数里，从它的参数表里按 `job_id`、`request_id`、`task_id`、`id` 的顺序认。提交的回答里作业 id 和查询的回答里状态都从文本内容的 JSON 里读（顶层，或 data / result / job 之下）；`completed`、`succeeded`、`done` 这类算完成，`failed`、`error`、`cancelled` 这类算失败，其余都算还在跑；结果里的地址、时长、花费原样带给等它的 Bot。 / `submit_<x>` and `check_<x>` on the same MCP server are a pair (`engine/job-adapter.ts`), so westlake-cpa's `submit_video` / `check_video` works like any server of that shape; which argument the check takes the job's id in is read from its parameter list, trying `job_id`, `request_id`, `task_id`, `id`. The job id in a submit's answer and the state in a check's answer are read from the JSON in its text content (at the top, or under data / result / job); `completed`, `succeeded`, `done` and the like are done, `failed`, `error`, `cancelled` and the like are failed, anything else is still going; the result's url, duration and cost are passed on as they are.
3. **提交 / Submitting.** 一次提交成功拿到 id，就登记成一个作业，Bot 读到的回答后面附一句「作业已登记，应用自己去查，完成后会叫你——不用轮询，也不用为它约回看」。半小时内同一个服务器、同一个工具、参数相同（不计键的顺序）的提交，返回已经开的那个作业（`deduped`），不再发给服务器——这一层不看归属，F-c 那样归到别的规划的第二段也拦得住；作业还在跑时，被去重的这个 Bot 也记为等待方，完成时一起被叫醒；作业已经结束的，直接给它结果。提示词里只点到一个分件号（`Shot 05`、`C07`、`第七镜`）时，这个分件有作业还在跑，或者有完成了却还没交出去的结果，再提交就被拒（`job_pending`）；确实要重交，带上 `resubmit_reason` 说明理由——理由记在作业上，不作为参数发给服务器。 / A submit that gets an id back is registered as a job, and the answer the Bot reads ends with a note that the app polls it and wakes it when done, so there is no need to poll or book a check-back. The same server, tool and arguments (key order aside) within half an hour get the job already started (`deduped`) instead of reaching the server — this layer does not look at filing, so a second segment filed under another plan, as in F-c, is caught too; while that job runs, the Bot deduplicated becomes a waiter and is woken with the result as well, and a job already finished hands it its result at once. When a prompt names exactly one part number (`Shot 05`, `C07`, `第七镜`) and that part has a job still running, or a finished result not handed over yet, the submit is refused (`job_pending`); to submit again anyway, `resubmit_reason` says why — it is kept on the job and not sent to the server as an argument.
4. **查询与轮询 / Checking and polling.** Bot 查询一个登记过的作业，读到的是守护进程最后一次查到的状态（`cached`），不打到服务器；查询的 Bot 记为等待方（每个 Bot 在每个会话记一次）。守护进程在调度器每一拍（15 秒）里问到期的作业，不在任何一轮里、不调模型，间隔逐次拉长：30 秒、1、2、4 分钟，之后每 5 分钟；服务器没回答（停了、删了、工具改了名）就过了间隔再问，和一直不报完成的作业一样按年龄放弃。完成或失败时，结果存下，每个等待方——提交的 Bot 和查过的 Bot——都在各自的会话里被叫醒、读到结果（被叫停的照常进收件箱，解除后读到）；三个小时还没完成就记为丢失，同样告诉等待方。重启后从表里接着轮询。 / A Bot's check on a registered job reads what the daemon last heard (`cached`) without reaching the server, and the Bot is recorded as a waiter (once per Bot and conversation). On each scheduler tick (15 s) the daemon asks about the jobs due, outside any turn and with no model call, with a growing gap: 30 s, 1, 2, 4 minutes, then every 5; a server that does not answer (stopped, removed, a tool renamed) is asked again after the gap and given up by age like a job that never reports done. Done or failed, the result is kept and every waiter — the Bot that submitted and every Bot that checked — is woken in its own conversation with the result (one under a stop gets it in its inbox, read once the stop is lifted); a job still pending after three hours is given up as lost, and the waiters are told so. After a restart the poller picks up from the table.
5. **回看只用来真等 / Check-backs are for real waits.** 6 级起 Bot 自己约的回看最短 5 分钟（原来 1 分钟），每个工作项每小时最多 6 个（被叫停挂起的不算）；备注点名了一个守护进程正在轮询的作业，就被拒（`job_polled`）。 / From level 6 a check-back a Bot books itself is at least 5 minutes (it was 1), at most six per work item per hour (one a stop suspended does not count), and one whose note names a job the daemon is polling is refused (`job_polled`).

## 缺口 / Not done

- **天花板还没挡生成作业**（[ADR 0046](0046-submissions-and-reviews.md) 的 26c）：卡在能力天花板上的分件不再收交付，但它的 `submit_video` 还没被挡。
- **分件号只从提示词里认**：提示词没点分件号、或点了好几个时，不加分件锁，只剩半小时的参数去重。
- **等别人交付**用委派（ADR 0044），不归这里；`wait_for` 没有单独的工具，用 6 级规则下的回看。

## 取舍 / Trade-offs

- **按名字认对，不要求服务器声明。** 一个服务器若把查询叫别的名字就认不出、一切照旧；换来的是不需要任何配置，westlake-cpa 现在就能用。
- **去重按参数摘要，不按语义。** 换一个标点就是新作业；但半小时内一字不差地重交，正是两条私聊各做一遍的样子。
- **轮询不受叫停影响。** 查询是只读的；叫停挡的是被叫醒的那一轮，结果留在收件箱里。
