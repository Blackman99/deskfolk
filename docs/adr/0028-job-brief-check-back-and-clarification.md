# 一件事记着最初的要求，Bot 能约自己回看，需求没说清也学习

三件事都缺同一样东西：一件事的目标没有成为上下文里的一等公民，也没有人回头核对它。

- **目标只在转录窗里。** `tasks` 只有 40 字的 `title` 和目录名；Bot 每轮看到的关于这件事的全部信息是「本轮工作目录」一行。转录窗是最近 40 条：群里三个 Bot 来回几轮，用户最初那条要求就滚出去了；Bot↔Bot 私聊里接收方的窗口只有这条私聊自己的消息，目标能不能传过去全看发起方开场消息写得够不够。系统指令要求「验证原始目标是否达成」，但模型手里没有那个原始目标的文本。
- **没有人回头。** `send_message` 结束本轮；Bot 消息不带 `@` 不叫醒任何人；判断只对用户的无点名消息跑。工人做完没 `@` 回去，这件事就静默停住。Bot 没有任何把自己延后叫醒的手段，日程只有 daily / weekly。`no-work.ts` 那串过滤「本轮结束」的正则是症状处理：模型说这些话，是因为它不知道还有什么该做。
- **意图纠正被扔掉。** 复盘判 `fault: prompt`（需求没说清）的结论一律不留（[ADR 0019](0019-agent-routing-and-review.md)），学习跳只在归咎模型或工具报错后跑（[ADR 0024](0024-route-execution-and-learning-hop.md)）。「用户其实要 X 不要 Y」这类最有价值的纠正，系统识别到了，然后扔掉了。

## 现在

**一件事记着开它的那条要求。** `tasks.brief` 存开这件事那条消息（或日程 instruction）的原文，裁到 4000 码点；旧库按每件事第一轮的触发消息回填。交接、点名、判断下场、Bot↔Bot 私聊、中断续跑和回看都沿用工作目录，所以 brief 跟着工作目录走，不需要发起方在开场消息里复述。

**局面块每一轮都带这件事。** 原来只有群才有局面（在场成员、活轮、谁叫醒、用户最近一句），私聊只有一行工作目录。现在每一轮都在群事实之后、工作目录之前加上：「这件事最初的要求」（brief 折成一行，最多 1200 码点）、「这件事已交出」（这件事的消息引用过且还在盘上的文件，最多 20 个）、「经过」（`taskTrace` 每轮一行：谁、最后一句或正在等什么，最多 12 条，不含本轮）、「你约的回看」（自己在本会话待回看的那一次）。第一轮不引自己，改标「这是这件事的第一轮」。全部从库里已有的行读出——流程图早就算好了这些，只是没给模型看——没有一次模型调用，不会和记录漂移。判断的 JSON 和输入建议的 JSON 也带同一份 `job`。

**Bot 可以约自己回看。** `check_back(after_minutes, note)`：一分钟到七天，一句备注。`check_backs` 表记 Bot、会话、约它的那一轮和那一轮的 task。调度器每次 tick 找到期的，`claimCheckBack` 是 compare-and-set，两次 tick 不会叫醒两次。到点在同一会话插一条 `system` 行「回看：<备注>」，作者是这个 Bot，挂在约它的那一轮上（流程图画成 Bot 叫醒自己），同一个事务里把这行的 id 记到 `check_backs.message_id`，然后走 `startTurn`：群里改道进它的活轮，和点名一样；私聊分叉。轮次显式带 `taskId`，所以就算约它的那一轮已经不在了也落在同一件事里。一个 Bot 在一个会话里同时只有一次待回看，再约就是替换——这是唯一的增长控制，没有跳数熔断。作废：约它的那一轮被 Stop（Stop 的意思是「不要这个」，之后再自己回来就违背了它）、会话清空或删除、Bot 删除。Bot 离开了群或被归档，到点只消掉不叫醒。守护进程睡过去或重启后，到期未响的在下一次 tick 补响一次，和补跑一致。

**需求没说清也学习。** `verdictIsClarification`：`fault: prompt`、纠正不少于两轮、把握度够。命中时也发学习跳，但工具只给 `remember` / `forget`，不给 `update_skill`——工序没错，错的是一开始没对齐；提示词让它只记「做 X 这类事时，先按 Y」这种下次开工前就该按它做的口径，不记这一件事本身的细节。

**系统指令补了三段。** 局面里的「最初的要求」是核对方向和验收标准的依据，不是叫醒你的那一句；「已交出」先看再做；第一轮先对齐——猜错会浪费整件事的（交付形态、范围、给谁看）用 `ask_user` 问一个带默认选项的问题，能给默认值的把假设写进第一条消息然后继续做；有交付物的事，最后一条消息按最初的要求逐项说明。回看那段讲何时约、醒来先看什么、没动静怎么办。

**评估。** `scripts/goal-coverage-eval.ts` 在数据库副本上取一件事的 brief、交出的文件开头和 Bot 最后几句，让评判模型逐条判 covered / partial / missing 并给依据。纯函数在 `src/goal-coverage-eval.ts`。

## 取舍

- **局面块每跳都发，不缓存。** 它在系统指令之后、转录之前，端点按最长公共前缀命中缓存时只作废它之后的部分；块内容在一轮里基本不变（本轮写的文件要到发消息才被引用）。多出来的是几条 SQL 和一两百 token，换的是每一轮都有目标可核对。
- **brief 折成一行。** 带列表的要求折成一行会丢排版，但局面是事实块，一行一件事；第一轮时原话完整地在转录里。
- **`system` 行而不是 `bot` 行。** 回看的备注若插成 Bot 消息，会走参与（备注里的 `@` 叫醒别人）、计进未读、被 `no-work` 过滤；`system` 行只是一条触发，模型看到「【系统】（本轮触发）回看：…」。
- **这一行只给被叫醒的那一轮。** 它是 Bot 给自己的备忘，不是对谁说的话：列消息（会话、手机、别的 Bot 的转录）、整理跳读的新消息、搜索、未读、最后一条、事件流都按 `check_backs.message_id` 把它排除（`notCheckBackLine` / `isCheckBackLine`），只有被叫醒那一轮的触发和流程图照常读它。转录窗口里它按时间落在前后消息之间，而不是顶到最前面。标记记在 `check_backs` 上而不是新加消息种类：改 `messages` 的 CHECK 约束要重建整张表。旧库里已经响过的回看，按「同会话、同作者、正文是 `回看：`/`Check-back: ` 加备注」回填。
- **不放开「send_message 结束本轮」。** 这条规则减少废话，和主动性直接冲突；回看是不动它的补法。以后若放开，最小的放法是发到别的会话不结束本轮。
- **判断 `first_turn` 的定义。** 判断没有轮次，以「这件事还没有任何轮」算第一轮。

## 不做

- 不做任务表、计划 DAG、负责人：局面里的经过是读回来的记录，不是分配。
- 不做事件触发的回看（文件出现、对方回复）：纯定时够用，事件触发是下一步。
- 不让模型摘要目标：brief 是原文。
- 不为 prompt 结论改技能，也不把它送进选路窗口：它讲的是用户要什么，不是模型行不行。
