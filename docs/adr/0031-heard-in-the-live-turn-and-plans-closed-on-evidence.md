# 队友的话听进活轮，任务按看到的推进，完成要有执行记录，规划停下有人对账

部分被 [ADR 0039](0039-plans-with-work-left-are-called-back.md) 取代（2026-09-29）：叫回次数不以任务数为界，任务退回再交出就能再叫；改为你最后一次在这个规划里说话或回答提问之后最多叫回 5 次。没有待做、进行中，进展却还记着没做完或卡住的群规划也会叫回。

部分被 [ADR 0041](0041-control-plane-holds-and-restarts.md) 取代（2026-09-30）：引擎级别到了叫停这一级后，群里有 Stop，你的话不再是群里唯一的停法；停下是一条只有你能解除的叫停记录，不再是整理跳写的「搁置」。规划对账被叫停挡下时不改叫别人，只记一条挡下的叫醒。

部分被 [ADR 0040](0040-agent-kernel-the-job-owns-state.md) 的 P3 取代（2026-10-01）：整理跳写的验收不再落到规划上，所以要做出能用的东西时那条「有启动方式，照着能在本机跑起来并走通主流程」也不再写进规划的验收。Bot 系统说明里「交付要运行的东西附启动方式并自己先起一遍」和整理跳另开的「联调并给出启动方式」任务照旧。

[ADR 0016](0016-group-one-live-turn-per-bot.md) 定了「群里一人一轮，点名听进已有活轮」，实现却沿用了 [ADR 0007](0007-redirect-is-terminal-plus-new-turn.md) 的改道：旧轮进终态、新开一轮、工具回路清空。[ADR 0029](0029-closing-check.md) 的收尾自检只看交出的文件和各轮最后一句，[ADR 0030](0030-plans-tickets-and-organizer.md) 的整理跳只在规划静下来时整理任务。2026-09-26 的「软件产研协作开发团队」把这几处一起碰穿了：你说了一句「开发一个 web 版的视频编辑软件」，七个 Bot 首尾相接干了 41 分钟，产品经理宣布「正式准予发布结项」，规划被判成已完成，流程图上六个任务从头到尾都是待做，而你手里没有一个跑得起来的东西。

- **队友的 @ 杀掉正在干的活。** 前端开发工程师被改道三次：UI/UX 交稿时 @ 它一次；续跑那轮写了 19 个文件、调了 40 次工具，后端一句「接口已就绪 @前端」又把它改道；新一轮 26 跳，QA 的全员 @ 再改道一次。新轮只看得到转录，看不到被改道那轮写了什么、做到哪。它始终没发出一条交付消息。
- **完成靠自称。** QA 的报告写「21/21 全链路 PASS、音画偏差 ≤33ms、Chrome 里 WebCodecs 导出正常」——Bot 没有任何浏览器工具，报告落盘时前端的测试文件还没写出来，后端的 `tsc --noEmit` 其实报错。收尾自检把 QA 自己写的报告当成「看得见的证据」；整理跳的 settle 按产品经理的「结项」判规划做完。
- **任务状态没有人实时维护。** 23 轮全部盖着任务 1：你的消息被标成任务 1，此后每次交接都继承唤醒方的任务。settle 要等规划所有活轮都结束再静 30 秒，41 分钟里一直没静过；最后那一次把规划标成已完成，任务一个没动——解析器把没写 `title` 的任务条目整条丢掉，而提示词正让它「只改变了的字段」。也没有「规划做完 ⇒ 任务都收口」的约束。
- **停下来没人管。** 每个 Bot 都以为自己那块交了；没有待回看，规划已关，什么都不会再叫醒谁。

## 现在

**听进，不改道。** 每个活轮有一个收件箱。别的 Bot 点它（群里的 @、Bot↔Bot 私聊里对方的下一句）、它约的回看到点，而它在这个会话里已有本进程在跑的活轮时，`hearOrStart` 把这条消息放进收件箱，不结束这一轮；循环每一跳开头（和节奏提醒同一个口子）把收件箱排空成一行 `user` 提示「（应用提示）你这一轮干活时有人找你」，接着干。回看行只给被叫醒的那一轮看，所以提示里带着备注全文。轮在等批准或提问时，消息留在收件箱，恢复后读到。轮以完成告终时收件箱里还有没读到的（最后一跳开跑之后才到），就按最后一条再开一轮，更早的回看行跟着进新轮的收件箱；Stop、改道、中断时不补开。你的消息仍改道（群里没有 Stop，你说话是要它马上转头），但 `startTurn` 改道时把旧轮的 `writtenPaths`、最后几次工具调用（壳写出命令）和没读到的收件箱合成新一轮回路的第一行（`redirectCarryNote`），不再从零开始。0007 的「改道是终态加新轮」对你的消息仍成立；0016 的「点名听进已有活轮」对 Bot 的点名和回看现在是字面意思。有你的私聊默认每句另开一轮（你可以同时问两件事），回看在那里只听进做同一件事的活轮（`fireCheckBack` 看这个 Bot 在这个会话的活轮里有没有同一规划的），讲别的事的回看照旧另开一轮；`hearOrStart` 在一个 Bot 有几轮时先给做这件事的那一轮，谁都听不了时在这种私聊里另开而不是改道，不会停掉你开的那一轮。

**任务落到对的人，按看到的推进。** `resolveTurnTask` 知道被叫醒的是谁：交来的任务是别的 Bot 的，而这个 Bot 在规划里恰好只做一个没收口（待做 / 进行中 / 待验收）的任务，就落在它自己那个（`ownOpenTicket`）；交来的是它的或没人做的，照交来的。触发消息回盖的仍是它自带的任务，不是这个 Bot 碰巧在做的那个——一句话会叫醒一整队人。整理跳提示词明写建任务时按「流程与分工」先填 worker（它事实上一直这样填），词表跟着改。`observeTicketWork` 不调模型地往前推一格：归到任务的轮第一次调 `write_file` / `delete_file` / `shell` 或 MCP 工具，待做→进行中；它写了文件并发出消息，待做 / 进行中→待验收；worker 为空时记上这个 Bot。只往前，不标已完成或搁置；变更照常走 `ticket.upsert`，镜像文件重写。

**整理跳按 id 局部更新，规划做完要任务收口。** 解析器对已有任务不再要求 `title`：缺标题、状态或 worker 都是「不变」，不再丢条目、不再把缺状态读成待做、也不再把缺 worker 读成清空（`OrganizerTicketInput` 这三项变成可选；新任务仍要标题，缺状态为待做）。`applyOrganizerResult` 在应用完任务后，若答案把规划标成 done 而还有待做或进行中的任务，就把规划状态留在 active，其余改动照收，返回 `heldOpenBy` 并记日志；待验收算已交出。你用 `PATCH /v1/tasks/:id/spec` 手动标完不受限。

**记下真正跑过的。** 新表 `turn_runs`：每次 `shell`（命令、退出码、失败时的错误）和每次 MCP 调用（服务器.工具 + 参数），在调用结束时写，所以被改道、被中断的轮也留着；每轮最多 80 条，命令截 300 码点；删会话、清空历史一并删。整理跳载荷多了 `since_last_revision.commands`（上一版之后最多 40 条）和每个任务的 `files`（按消息的 `ticket_id` 或路径落在任务目录里归属）；提示词加了依据规则：Bot 自称不算，标待验收要有文件，标已完成还要在 commands 里找得到成功的执行；验收写你能检查的结果，要做出能用的东西时必须有「照着启动方式能在本机跑起来并走通主流程」，几个人各做一块时另开「联调并给出启动方式」的任务。

**收尾自检对照执行记录。** 载荷加 `ran`：这一轮的记录在前，这件事之前的轮在后，共 40 条。提示词多一类要列的：收尾或这一轮交出的文件里说已经跑过、测过、构建过、在浏览器里验证过、量出过数字的，在 `ran` 里对不上（没有对应执行或那次失败了）就列出来；要浏览器、真机或人工才能验证、记录里又没有这样的调用的，算对不上；写明「未验证」和原因的不列。退回提示同时告诉它：没跑过的现在去跑，跑不了就写明未验证。仍然一轮只退一次。它和判断调用的答案上限不再用短调用默认的 256：推理模型把额度全花在思考上，开头七次判断有三次空答被当成旁观。现在判断 1024、收尾自检 1536，判断截断会记日志。

**Bot 的系统说明。** 加一段「说做过的必须真做过」：通过 / 成功要附命令和结果，没法验证的写未验证和原因，不替别人的产物宣布通过；交付要运行的东西附启动方式并自己先起一遍，常驻进程用带时限的命令起再另起命令验证；几个人各做一块时要有人接起来跑通。点名那句改成「对方正在干活时不会被打断，它下一跳就会读到」，并说明回路里那行「有人找你」怎么对待。

**规划停下有人对账。** 整理跳的 settle 计时到点、settle 结束后（不论有没有整理出东西）调 `onQuiet`，引擎的 `reconcilePlan` 核：规划进行中、会话里有你、没有活轮、规划里没有待回看、还有待做或进行中的任务，就替第一个没收口任务的 worker（在场、没归档；没有就用最后在这个规划里说话的 Bot）约一次立刻响的回看（`check_backs.kind = 'plan_nudge'`，显式带规划和任务，所以落在那个任务目录），备注列出所有没收口的任务并点出它那一个。上一次叫回之后没有任务变成待验收或已完成，就不再叫，改在会话里插一条系统行「这件事停下了……」（挂在被叫回的那个 Bot 名下，不叫醒任何人），并建一条 `failure` 通知（`fail_kind = 'stalled_plan'`，标题「<会话> · 停下了」），同一次叫回只告诉你一次。每次再叫都要先有任务收口，所以叫回次数不会多过任务数。顺带修了回看的任务：`fireCheckBack` 现在把 `check_backs.ticket_id` 交给新轮，回看落回原任务目录而不是规划目录。

## 取舍

- **Bot 的话听进、你的话改道。** 群里没有 Stop，你发消息是唯一的停法；把你的话也排进收件箱，你要它停就得等它当前那次工具调用跑完（壳最长十分钟）。Bot 之间的话大多是交接和通知，不值得杀掉一段进行中的工作。改道带过去的第一行补上了你转向时最痛的那部分。
- **收件箱在内存里。** 守护进程重启时活轮本来就中断，你按「继续」时新轮的转录里有那些话；回看行例外，它不进转录——这种情况概率低，不为它加一张表。
- **听进的话不画新卡片。** 流程图按叫醒关系画，听进的那句没有开新轮，所以卡片上看不到「B 叫醒了 A」这条边，只看得到 A 后来的回复。以后若要画，给收件箱加一张记录表即可。
- **按人落任务，而不是让 Bot 报任务号。** Bot 在消息里写「任务 04/05」常常一句提好几个；按 worker 落不用 Bot 做任何事，只要分工填了就对。代价是你点名让 X 去做 Y 的任务时，X 会落在自己的任务目录里——文件路径仍由它自己决定。
- **应用只往前推，不替谁收口。** 进行中和待验收是看得到的事实（开始写了、交了文件）；已完成要判断，仍归整理跳和你。
- **执行记录只记壳和 MCP。** 读写文件不是「跑过」；Bot 声称的验证几乎都落在这两类上。命令截断、条数封顶，载荷有界。
- **对账只叫一次、以任务收口为再叫的条件。** 私聊叫回已经是应用替 Bot 约的回看，这里是同一条规则扩到规划；用「有任务收口」而不是「有新消息 / 新文件」当条件，是因为一个说「我卡住了」并附上旧文件的 Bot 每次都会满足后者，两边会一直空转。
- **停下的告知是系统行加通知，没有做侧栏角标。** 会话标签和侧栏的状态需要新的协议字段，眼下系统行在转录里、通知在通知中心，已经能让你看到；角标以后再加。

## 不做

- 不做调度器派活：叫回只找已经在那个任务上的人，不替任务挑人。
- 不给 Bot 开浏览器工具：要在浏览器里验，给名册加一个浏览器类 MCP；没有就老实写未验证。
- 不让 Bot 改任务状态或报任务号。
- 不把判断和整理跳换成 Bot 自己的模型。
