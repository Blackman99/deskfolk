# 交付前核一次收尾，退回一次，不拦第二次

[ADR 0028](0028-job-brief-check-back-and-clarification.md) 让每一轮都看得到这件事最初的要求，并要求收尾按它逐项说明。但那只是提示词：模型说「已完成」，守护进程不会替它再验一遍，用户看到的仍可能是漏了一项的交付。

## 现在

**交付给用户之前打一次无工具短调用。** 条件三个都满足才核：Bot 准备发出的消息引用了工作区文件（本轮写的、正文点到的或 `paths` 里给的）；目标会话里有用户；这件事有 `brief`。调用打在默认端点的默认模型上，和选路、复盘一样，不用 Bot 自己的模型核自己。载荷是 `brief`、这条收尾、这件事已交出的文件及开头（本轮的排前面）、以及局面里那几行「经过」。答案只有一个数组：既没有在文件里看到做到、收尾里也没有交代去向的要求。

**退回一次，方式跟着发出的方式。** 走 `send_message` 的，那次调用不执行，结果是 `{ ok: false, error: { code: "closing_check", message } }`，模型看到清单后自然会补做或改写再发；直接以正文收尾的，清单作为一行 `user` 消息进回路，再跑一跳。`live.closingChecked` 保证一轮只核一次，第二次发不再拦——这是提醒，不是闸门，最终说什么仍由 Bot 决定。

**退回不算工具错误。** 复盘读 `tool_errors` 判模型行不行；一次收尾提醒不是工具坏了，`executeTools` 对 `closing_check` 不计数、不记进重复失败。

**放行的情况都写死了。** 没有 `brief`、没配默认模型、正在排空、端点拒绝、答得不成形、目标是没有用户的 Bot↔Bot 私聊、回复没引用文件，一律不核或直接放行。核的那次调用记在这一轮的花费上（kind 仍是轮次补全，行上记的是它实际跑的模型）。

## 取舍

- **默认模型而不是 Bot 的模型。** 核的是「看得见的证据够不够」，不需要强模型；用默认模型也避免选路递归，和 ADR 0019 的选路调用一致。
- **只核交付。** 每一跳都核会把成本翻倍，也会把寒暄都拦下来；引用了文件才算交付。
- **只退回一次。** 两次以上就成了闸门，而且判错时会把 Bot 困住。一次退回加上收尾要说明去向的规则，已经足够让漏项在收尾里被写出来。
- **不给它工具、不让它改写收尾。** 它列的是缺什么，不是替 Bot 写收尾；改写会绕过 Bot 的人设和记忆。
- **Bot↔Bot 私聊不核。** 那里的消息是中途交接，不是给用户的收尾，按整份 brief 核只会误报。

## 不做

- 不加新的花费种类：一次收尾核对是这一轮里的一次补全。
- 不进主转录：退回只存在于回路里，用户看到的是最终那条。
- 不记成模型选择记录里的字段：要看它有没有起作用，用目标覆盖评估脚本量最终交付。
